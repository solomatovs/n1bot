# Роли из БД и users без meta

Новые схемы создаются обычной командой `migrate`. В существующих схемах AID,
MCP и истории агента нужно остановить приложения и выполнить `identity.sql`
в транзакции, подставив имя схемы как SQL identifier. UUID пользователей и
ролей, сессии, история и grants сохраняются. Затем пакет `boba.access_postgres`
добавляет `role_tools` в схемах, где используются права ресурсов.

Перед обновлением права `[roles.<name>].tools` переносятся в `role_tools`
только для уже существующих ролей. После переноса корневой `[roles]` удаляется
из compose/debug. Правила `auth.*.roles.*` остаются: они назначают существующие
роли, но больше не создают их. Ссылки на роли в профилях и endpoint'ах тоже
остаются фильтрами доступа, а не объявлениями ролей.

`users` хранит `id`, `identifier`, `created_at`, `realm`, `login`.
Неподтверждённые старые пользователи имеют пустые `realm/login` и требуют
явного сопоставления прежней командой `boba.runtime.identities`. Старые JSON
снимки этой команды несовместимы с новым форматом: план нужно создать заново.

Роли создаёт администратор:

```sql
insert into app.roles (role) values ('reader');
insert into app.role_tools (role_id, tool)
select id, 'query' from app.roles where role = 'reader';
```

Вместо имени инструмента можно задать `'*'`. Пустая `role_tools` не разрешает
ни одного инструмента. Роль с именем `*` задаёт общую политику для любой
существующей роли; пользователь без ролей прав от неё не получает. Таблица `role_tools` читается при запросе списка и при
вызове: изменение прав не требует перезапуска MCP.

Ручное членство не удаляется очередным автоматическим входом:

```sql
insert into app.user_roles (user_id, role_id)
select u.id, r.id from app.users u cross join app.roles r
where u.identifier = 'office:alice' and r.role = 'reader'
on conflict (user_id, role_id) do update set managed = false;
```

Автоматически назначенные членства помечаются `managed = true`. Вход обновляет
только их. Пустой каталог ролей не мешает запуску. При входе `require_roles`
применяется после пересечения правил с каталогом и добавления ручных членств.
При `false` пользователь входит без ролей; профили и инструменты ему не
выдаются. Доступ к персональным ресурсам по UUID по-прежнему определяется
их собственными grants.

В `users` больше нет произвольных настроек (`theme` и подобных ключей),
провайдера последнего входа и снимка профилей. Сессионные данные, поколение
и зашифрованный SSO-билет остаются в JWT. Адаптер Chainlit отдаёт ему нужный
словарь metadata без JSONB-колонки; локальный патч Chainlit объединяет
сессионные поля JWT с сохранённой личностью и членством, отдавая БД приоритет
для этих полей. Пустое членство явно передаётся как `roles = []`.


Состояние dev-стенда 2026-11-04: схемы `aid`, `boba` и `mcp` в базах `aid` и
`aid_ss` обновлены. В `users` оставлены только `id`, `identifier`,
`created_at`, `realm`, `login`; старые UUID и членства сохранены. В обеих
базах в `mcp.role_tools` для существующих ролей `read` и `wrt` сохранено
разрешение `*`. Текущие контейнеры остановлены до сборки и установки новых
образов. После запуска пользователю нужно войти заново: OAuth не расширяет
области уже выданного токена при добавлении роли.
