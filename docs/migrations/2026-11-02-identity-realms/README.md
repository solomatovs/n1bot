# Переход на идентификаторы пользователей с пространствами

Ключ пользователя теперь имеет вид `realm:login`. Backend входа задаёт
`identity.realm` и необязательные `identity.aliases`; бизнес-код получает
готовый идентификатор. Правила одинаковы у AID, MCP и службы агента.
Старый логин сам по себе не определяет пространство. Этот перенос требует
соответствий администратора и не запускается при старте приложения.

Текущий выпуск применяется на dev-стенде. По решению пользователя обязательные
бэкапы и сохранение прежних сессий службы не требуются. Обновление выполняйте
при остановленных экземплярах со старым кодом.

Для users AID/MCP ниже оставлен необязательный перенос, если нужно сохранить
тестовую историю, личные grants или UUID workspace. При чистом dev-развёртывании
можно пересоздать схему приложения. Таблицы создают отдельные команды `migrate`;
автоматического перехода на `users.id` при запуске больше нет.

## Users AID и MCP

Административный CLI включён в `boba-mcp identities`; из исходников он
доступен как `python -m boba.runtime.identities`. Он читает обычные TOML через
OmegaConf. `--config` передаётся перед подкомандой; повторяйте параметр для
наложений в том же порядке, что при запуске сервиса. Из `[app]` используются
только `postgres`, `schema`, `instance`; приложения и инструменты не стартуют.
Можно передать файлы AID для переноса users AID той же командой MCP.

Пример соответствий `aid-identities.toml`:

```toml
[migration]

[[migration.users]]
user_id = "11111111-1111-4111-8111-111111111111"
previous_identifier = "alice"
identity = { realm = "office", login = "alice" }

[[migration.users]]
user_id = "22222222-2222-4222-8222-222222222222"
previous_identifier = "bob"
identity = { realm = "aid-local", login = "bob" }
```

`user_id` берётся из существующего users.id, а не генерируется заново.
При смешанном старом логине нельзя определить владельца по последнему
`provider` в metadata: разберите такую запись вручную. Автоматического
объединения двух users нет. При совпадении целевого ключа с чужим UUID
план будет отклонён.

```sh
umask 077
boba-mcp identities --config /etc/boba/config.toml \
  plan aid-identities.toml aid-identities-plan.json
boba-mcp identities --config /etc/boba/config.toml \
  apply aid-identities-plan.json
```

`plan` читает данные и создаёт новый JSON с правами 0600, не меняя users.
JSON содержит исходные metadata, поэтому храните его в закрытом
каталоге и не публикуйте. `apply` проверяет исходные строки и выполняет весь
план одной транзакцией. Меняются identifier и поле identity в metadata;
UUID, created_at, настройки, роли и ссылки grants сохраняются. Повторный
`apply` того же плана допустим. Если строки изменились после подготовки,
применение и откат останавливаются целиком: подготовьте новый план.

MCP получает собственную users в `[app].schema`, без таблиц чата:

```sh
boba-mcp migrate --config /etc/boba/mcp.toml
```

До этого MCP вычислял владельца workspace как
`uuid5(NAMESPACE_URL, "boba-mcp:<старый канонический логин>")`.
Для каждого существующего владельца укажите именно этот UUID в отдельном
плане MCP и добавьте `[migration] seed_missing = true`: CLI создаст запись
users с прежним UUID. Имена каталогов workspace и ссылки журналов сохранятся.
Если пропустить этот шаг, первый вход создаст новый UUID и прежние файлы не
будут видны. Идентификаторы AID и MCP могут совпадать; их UUID принадлежат
разным хранилищам и не обязаны совпадать.

Откат users при остановленных приложениях:

```sh
boba-mcp identities --config /etc/boba/config.toml \
  rollback aid-identities-plan.json
```

Он возвращает исходные строки; созданные `seed_missing` строки удаляются.
После входов в новую версию metadata могут измениться. В таком случае
нужен отдельный перенос; для текущего dev можно пересоздать схему.

## История службы Boba: UUID пользователя

Служба использует собственную схему `[agent.history].schema` и подключение
`[agent.history].postgres`. Общий пакет `boba-identity-postgres` создаёт
`users`, `roles` и `user_roles`. После любого способа входа AuthServer сохраняет
пользователя через тот же UsersTable, который используют AID и MCP. UUID
из этой строки попадает в access token и в `session.user_id`.

Связи в базе:

- `user_roles.user_id → users.id`, `user_roles.role_id → roles.id`;
- `session.user_id → users.id`;
- `session_records.session_id → session.id`.

У `session_records` нет дублирующего user_id: пользователь определяется
через сессию. Удаление сессии удаляет её записи. Пользователь с историей
защищён внешним ключом от удаления. Обновление личных данных не меняет UUID.

Схема создаётся отдельной командой:

```sh
boba migrate --config /etc/boba/agent.toml
```

Команда требует пустую схему, проверяет каждую имеющуюся таблицу до DDL
и отказывается работать при наличии любых таблиц. Прежняя схема с owner
автоматически не исправляется. Для текущего dev пользователь разрешил
пересоздание схем без сохранения прежних данных. Обычный запуск приложения
и первое обращение к истории DDL не выполняют. В новой схеме локальные
stdio-сессии без сетевой личности имеют user_id NULL.

Старый `history.owner` из JSON-настроек процесса удалён. Для явного владельца
Postgres-истории используется `history.userId`, UUID существующего users.
Служба выставляет его из проверенного токена; у обычного локального stdio
этого поля нет. Старый `history-users.sql` со строковыми соответствиями
удалён: он не относится к новой схеме.

## Проверка перед запуском

Настройте одинаковые правила realm/aliases для связанных backend'ов.
В доверенных клиентах MCP/службы агента укажите разрешённые `realms` и
соответствующие proxy-бэкенды. Для разных raw HTTP proxy-пространств AID
задайте разные path и ключи подписи.

Запустите новую версию, войдите заново, проверьте прежние треды, файлы,
личные grants и историю службы агента. Старая cookie и старые токены
недействительны; требуется повторный вход. Проверьте также отказ доступа
одноимённому пользователю из другого пространства.
