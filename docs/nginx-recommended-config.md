# Nginx: как устроен наш периметр и почему настройки именно такие

Этот документ описывает конфигурацию nginx из `/app/docker/compose/nginx` —
единственную точку входа, через которую снаружи доступны все сервисы стенда.
Он написан так, чтобы человек, впервые открывший эти файлы, понял не только
«что написано», но и «какую проблему это решает» и «что сломается, если
убрать». В конце собраны рекомендации: что стоит поменять и почему.

Содержание:

1. Задача и общая картина
2. Один порт наружу: мультиплексор четвёртого уровня

## 1. Задача и общая картина

Стенд состоит из нескольких десятков контейнеров: базы, веб-приложения,
инструменты разработки, медиасервисы, доменный контроллер. Наружу при этом
смотрит один хост и практически один порт. Всё, что должно быть доступно
снаружи, обязано пройти через nginx, и именно там сходятся три задачи,
которые обычно решают разные системы: терминирование TLS, маршрутизация по
именам хостов и единый вход по доменной учётной записи.

Из этого вытекает структура каталога. Она намеренно разбита на маленькие
файлы, каждый из которых отвечает за одну вещь, а повторяющиеся куски
подключаются директивой `include` вместо копирования.

| Путь | Что внутри |
|---|---|
| `nginx.conf` | глобальные настройки: воркеры, логи, сжатие, таймауты, подключение модулей и обоих блоков — `http` и `stream` |
| `conf.d/streams/` | четвёртый уровень: публичный вход на 443 и «стрипперы» для не-HTTP протоколов |
| `njs/rdp.js` | скрипт, который по первым байтам соединения решает, какому протоколу оно принадлежит |
| `conf.d/servers/` | виртуальные хосты, по файлу на сервис |
| `conf.d/locations/` | куски маршрутизации, общие для нескольких хостов (пути приложения boba) |
| `conf.d/options/` | повторно используемые наборы директив: TLS, заголовки безопасности, проксирование |
| `conf.d/passwords/` | файлы паролей для Basic-аутентификации |
| `docker-compose.yml` | запуск: rootless-контейнер, ограничения, тома |
| `krb5.conf`, `nginx.keytab` | доменные настройки и ключи для Kerberos-аутентификации |

Путь обычного запроса из браузера выглядит так:

```
браузер
  │  TLS ClientHello на порт 443
  ▼
stream-блок, listen 443            ← njs смотрит первый байт соединения
  │  это TLS → отправить на 127.0.0.1:8443, добавив PROXY-заголовок
  ▼
http-блок, listen 8443 ssl proxy_protocol
  │  расшифровка TLS, выбор server по SNI/Host
  ▼
location → proxy_pass → контейнер сервиса во внутренней сети docker
```

А запрос, скажем, от psql — так:

```
psql --host=postgres-18.loshara.com --port=443
  │  первые байты: длина + SSLRequest
  ▼
stream-блок, listen 443            ← njs распознал протокол postgres
  │  проверка адреса клиента по списку разрешённых
  ▼
127.0.0.1:15432 (стриппер)         ← снимает PROXY-заголовок
  ▼
postgres-18:5432                   ← в базу приходит чистый протокол
```

Дальше разбираем каждый слой по порядку.

## 2. Один порт наружу: мультиплексор четвёртого уровня

### Проблема

Наружу опубликованы только 80 и 443. Это не прихоть: в типичной офисной или
гостиничной сети остальные порты закрыты, а провайдеры домашнего интернета
часто блокируют входящие соединения на нестандартные порты. При этом снаружи
нужны не только веб-сервисы, но и RDP к виртуальной машине, LDAP и Kerberos к
доменному контроллеру, SMB к файловой шаре, прямое подключение к PostgreSQL.
Раздать им отдельные порты нельзя, а гонять всё через веб-туннели неудобно.

### Решение

Порт 443 слушает не HTTP-сервер, а `stream`-блок nginx, то есть прокси
четвёртого уровня, который не знает ничего про HTTP. Перед тем как решить,
куда отправить соединение, он отдаёт первые пришедшие байты скрипту на njs
(`njs/rdp.js`), а тот определяет протокол по сигнатуре:

| Первые байты | Протокол | Куда уходит |
|---|---|---|
| `0x16` | TLS ClientHello, то есть HTTPS | `127.0.0.1:8443`, обычный `http`-блок |
| `0x03` … `0xe0` на пятом байте | RDP (заголовок TPKT) | стриппер `127.0.0.1:13389` → контейнер windows |
| `0xfe`/`0xff` + `SMB` | SMB2 или SMB1 | стриппер `127.0.0.1:13445` → samba-ad |
| `0x00` + `0x6a`/`0x6c` | Kerberos AS-REQ или TGS-REQ | стриппер `127.0.0.1:1088` → KDC |
| `0x00` + `04 d2` или `00 03` | PostgreSQL SSLRequest или StartupMessage | стриппер `127.0.0.1:15432` |
| `0x30` | BER SEQUENCE, то есть LDAP | стриппер `127.0.0.1:1389` |
| всё остальное | считаем HTTPS | `127.0.0.1:8443`, где запрос и отвергнется |

Такой разбор возможен потому, что во всех этих протоколах первым говорит
клиент и первое же сообщение узнаваемо. Скрипт не разбирает протокол
целиком: ему достаточно нескольких байтов, а если их пришло меньше, чем
нужно для решения, он просто возвращает управление и ждёт следующую порцию.

Отдельного упоминания заслуживает разбор RDP: скрипт достаёт из первого
пакета поле `mstshash`, то есть имя, которое клиент подставляет в строке
подключения. Это позволяет по одному внешнему порту раздавать несколько
разных RDP-машин, выбирая целевую по метке из клиента. Сейчас в таблице одна
запись, но механизм рассчитан на рост.

### Зачем нужны стрипперы и PROXY-протокол

Если просто перебросить соединение в контейнер, сервис увидит адрес nginx, а
не адрес клиента. Для веба это решается заголовками, но RDP, LDAP и SMB —
бинарные протоколы, в них заголовки не вставишь. Стандартный ответ на эту
задачу — PROXY-протокол: прокси дописывает в самое начало соединения
короткую строку с адресами источника и назначения, а принимающая сторона её
читает и отбрасывает.

Проблема в том, что PROXY-протокол понимают далеко не все. nginx понимает,
Windows с его RDP — нет, samba и postgres — тоже нет. Отсюда конструкция из
двух шагов: публичный вход на 443 всегда добавляет PROXY-заголовок
(`proxy_protocol on`), а перед каждым «непонимающим» сервисом стоит
внутренний слушатель, объявленный как `listen 127.0.0.1:<порт>
proxy_protocol`. Он этот заголовок читает, запоминает адрес клиента для
логов и передаёт дальше уже чистый протокол. В файлах эти слушатели названы
стрипперами, и каждый из них занимает десяток строк.

Полезный побочный эффект: адрес клиента доезжает до логов nginx даже для
бинарных протоколов, а для HTTPS — доезжает до `http`-блока, где становится
`$remote_addr` (см. следующий раздел).

### Ограничение доступа

HTTPS остаётся публичным: это веб, его должны открывать откуда угодно.
Остальные протоколы — RDP, Kerberos, LDAP, SMB, PostgreSQL — доступны только
с перечисленных в скрипте подсетей: локальная сеть, docker-сеть, офис и
несколько домашних адресов. Проверка идёт до выбора бэкенда, и при
несовпадении соединение закрывается методом `s.deny()`, то есть клиент
получает разрыв, а не отказ с подсказкой.

Смысл здесь именно в разделении: веб защищён аутентификацией и TLS, а
доменные и файловые протоколы такого же уровня защиты на публичном порту не
дают, поэтому их периметр сужен до известных адресов.

### Чего стоит опасаться

Разбор по первому байту — эвристика, а не гарантия. Он корректен для
перечисленных протоколов, но любой новый протокол придётся добавлять в
скрипт руками, и чем длиннее становится цепочка условий, тем выше шанс
ошибиться в порядке проверок. В самом файле уже есть комментарий про такую
ошибку: если проверять сигнатуру SMB и длину буфера одним условием, неполный
первый чанк провалится в ветку «всё остальное» и уедет в HTTPS. Это
показательный пример: сначала различаем по первому байту, а достаточность
данных проверяем внутри ветки.

Второе ограничение: список разрешённых адресов зашит в код скрипта. Каждое
изменение — это правка исходника и перезагрузка nginx.

## 3. Реальный адрес клиента

Поскольку весь HTTPS-трафик приходит в `http`-блок не напрямую, а через
внутренний переброс с `127.0.0.1`, без дополнительных мер каждый клиент
выглядел бы как локальный. Сломались бы сразу три вещи: логи, ограничения
`allow`/`deny` в отдельных хостах и заголовок `X-Real-IP`, который читают
приложения.

Поэтому в `http`-блоке стоит:

```nginx
set_real_ip_from 127.0.0.1;
real_ip_header   proxy_protocol;
```

Первая строка говорит «соединениям с этого адреса можно верить», вторая —
«настоящий адрес брать из PROXY-заголовка». После этого `$remote_addr`
снова означает адрес клиента, и всё, что на него опирается, работает как
обычно.

Важно, что доверие ограничено именно `127.0.0.1`. Если бы здесь стояла
широкая подсеть, любой контейнер внутри docker-сети мог бы представиться
чужим адресом.

## 4. TLS

Настройки собраны в `conf.d/options/ssl.conf` и подключаются в каждый
виртуальный хост. Сертификат один, wildcard на домен, поэтому файл общий.

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:...;
ssl_prefer_server_ciphers off;
```

Оставлены только два протокола. TLS 1.0 и 1.1 давно объявлены небезопасными
и выключены во всех современных браузерах, так что их поддержка не даёт
совместимости, зато расширяет поверхность атаки. Набор шифров сведён к
четырём вариантам, и все они дают forward secrecy: ключ сессии
согласовывается эфемерным Диффи-Хеллманом на эллиптических кривых, поэтому
компрометация ключа сертификата не позволяет расшифровать записанный ранее
трафик.

`ssl_prefer_server_ciphers off` выглядит контринтуитивно, но это правильное
современное значение. Когда-то сервер навязывал свой порядок, чтобы не дать
клиенту выбрать слабый шифр. Сейчас все оставшиеся шифры сильные, а клиент
лучше знает, что у него быстрее: на телефоне без аппаратного AES выгоднее
ChaCha20, на сервере с AES-NI — AES-GCM. Пусть выбирает клиент.

```nginx
ssl_session_timeout  10m;
ssl_session_cache    shared:SSL:10m;
ssl_session_tickets  off;
```

Полное рукопожатие TLS стоит дорого, поэтому результат согласования
кэшируется, и повторное подключение того же клиента проходит по короткой
схеме. Кэш общий для всех воркеров, десять мегабайт — это примерно сорок
тысяч сессий.

Билеты сессий (`ssl_session_tickets`) выключены сознательно. Билет — это
зашифрованное состояние сессии, которое хранится у клиента; сервер шифрует
его ключом, который по умолчанию живёт всё время работы процесса и не
ротируется. Пока ключ не меняется, forward secrecy фактически теряется: кто
добудет этот ключ, расшифрует все сессии, восстановленные по билетам.
Правильно делать либо регулярную ротацию ключей, либо не использовать
билеты вовсе. Здесь выбран второй путь, а роль ускорителя выполняет общий
кэш.

```nginx
ssl_stapling        off;
ssl_stapling_verify off;
```

OCSP stapling — это когда сервер сам получает у центра сертификации ответ о
том, что сертификат не отозван, и прикладывает его к рукопожатию, избавляя
клиента от отдельного запроса. Штука полезная, но требует, чтобы nginx мог
ходить наружу к OCSP-респондеру и чтобы был настроен резолвер. Если этого
нет, каждое рукопожатие получает лишние задержки на неудачных попытках,
поэтому механизм выключен. Это разумный выбор для закрытого контура; если
однажды понадобится ускорить первое подключение внешних клиентов, включать
надо вместе с `resolver` и проверкой, что запросы к OCSP действительно
проходят.

Отдельная деталь: HTTP/2 включён только для одного хоста (`ccr`), директивой
`http2 on` внутри его `server`-блока. Комментарий в файле объясняет почему
это вообще работает: njs-мультиплексор смотрит только первый байт и не
вмешивается в согласование ALPN, поэтому протокол согласуется уже на уровне
`http`-блока. Для остальных хостов HTTP/2 не включён, и это скорее
историческое, чем осознанное решение (см. раздел с рекомендациями).

## 5. Заголовки безопасности

`conf.d/options/common.conf` подключается в каждый виртуальный хост и
добавляет четыре заголовка.

`Strict-Transport-Security` говорит браузеру: этот домен и все его
поддомены следующий год открывать только по HTTPS. Это закрывает окно, в
котором пользователь набирает адрес без схемы, получает редирект с 80 порта
и на этом коротком незашифрованном участке может быть перехвачен.

`X-Frame-Options: SAMEORIGIN` запрещает встраивать страницы сайта в фрейм на
чужом домене. Защита от кликджекинга: злоумышленник размещает прозрачный
фрейм с настоящим интерфейсом поверх своей страницы, и пользователь нажимает
кнопки, думая, что кликает совсем в другом месте.

`X-Content-Type-Options: nosniff` запрещает браузеру угадывать тип
содержимого вопреки заголовку `Content-Type`. Без него загруженный
пользователем файл, отданный как текст, может быть распознан браузером как
скрипт и выполнен.

`X-XSS-Protection` — реликт. Он управлял встроенным фильтром межсайтового
скриптинга в старых браузерах; в Chrome фильтр удалён, в Firefox его не было
никогда, а в некоторых версиях он сам служил источником уязвимостей. Вреда
от заголовка нет, пользы тоже.

**Грабли, о которых стоит знать заранее.** Директива `add_header` в nginx не
складывается по уровням: если в `location` появится хотя бы один свой
`add_header`, все заголовки, объявленные выше на уровне `server`, для этого
`location` исчезнут. Сейчас конфигурация это не задевает — единственный
дополнительный `add_header` (challenge для ClickHouse) объявлен на уровне
`server`, рядом с `include common.conf`, поэтому они складываются. Но стоит
кому-то добавить заголовок внутрь `location`, и с этого пути тихо пропадут
HSTS и остальные три. Признак беды: заголовки есть на одних путях сайта и
отсутствуют на других.

## 6. Проксирование HTTP: общий набор и его границы

`conf.d/options/proxy.conf` — самый часто подключаемый файл. Он собирает всё,
что нужно, чтобы за прокси стояло веб-приложение с веб-сокетами.

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection "upgrade";
```

По умолчанию nginx ходит к бэкенду по HTTP/1.0, где нет постоянных
соединений и нет механизма Upgrade. Веб-сокет начинается с обычного
HTTP-запроса, в котором клиент просит сменить протокол, и без этих трёх
строк такой запрос до бэкенда не доедет в понятном ему виде: соединение
останется обычным HTTP, а приложение ответит ошибкой рукопожатия.

```nginx
proxy_buffering         off;
proxy_request_buffering off;
```

Обычно буферизация полезна: nginx целиком вычитывает ответ бэкенда, тем
самым освобождая приложение раньше, и уже сам отдаёт данные медленному
клиенту. Но здесь за прокси стоят интерактивные приложения: чат с потоковой
выдачей, консоли, терминалы, логи. Для них важна не пропускная способность,
а то, чтобы каждая порция долетала сразу. С включённой буферизацией ответ
копится в буфере и приходит рывками, а иногда и вовсе застревает до конца
запроса. Симметрично выключена буферизация запроса: без неё загрузка файла
начинает уходить в приложение сразу, а не после того как nginx примет её
целиком.

Плата за это — nginx перестаёт защищать бэкенд от медленных клиентов:
соединение с приложением держится ровно столько, сколько клиент читает
ответ.

```nginx
proxy_set_header Host              $http_host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host  $http_host;
proxy_set_header X-Forwarded-Port  $server_port;
```

Приложение за прокси не знает, по какому адресу к нему пришли. Если ему это
не сообщить, оно построит ссылки и редиректы по внутреннему имени вида
`http://chainlit:8501`, и пользователь получит нерабочий адрес. Этот набор
восстанавливает картину: `Host` и `X-Forwarded-Host` дают исходное имя,
`X-Forwarded-Proto` — что снаружи был HTTPS (иначе приложение начнёт слать
редиректы на `http://` и получится цикл), `X-Forwarded-Port` — порт,
`X-Real-IP` и `X-Forwarded-For` — адрес клиента для логов и ограничений.

Обратите внимание: `$http_host` вместо `$host`. Разница в том, что `$host`
приводит имя к нижнему регистру и отбрасывает порт, а `$http_host` передаёт
заголовок как есть. Для приложений, которые строят абсолютные ссылки, второе
точнее.

### Когда этот набор не подходит

Показательный случай — поток Server-Sent Events в `chsimcity.conf` и
`pgsimcity.conf`. Там `proxy.conf` осознанно не подключён, а заголовки
выписаны вручную, и в комментарии объяснено почему.

Причина в устройстве `proxy_set_header`: повторное объявление того же
заголовка в том же блоке **не заменяет** предыдущее значение, а добавляет
второе. Значит, подключив `proxy.conf`, вы не сможете «переопределить»
`Connection: upgrade` — вы получите два заголовка `Connection`. А для SSE
нужен обычный keep-alive: это не веб-сокет, а долгий обычный ответ, который
сервер дописывает по мере событий. Отсюда правило: если набор из общего
файла не подходит по существу, его не переопределяют, а не подключают.

Там же выключены сжатие, кэширование и chunked-кодирование и поднят таймаут:
всё, что может накапливать данные в буфере, для потока событий вредно.
И отключён журнал доступа — от записи об одном соединении, живущем часами,
в логе пользы нет.

## 7. Приложение с тяжёлыми заголовками

`conf.d/options/boba-headers.conf` повторяет `proxy.conf` и добавляет к нему
буферы и таймаут. Причина конкретная: вход в приложение отдаёт JWT, внутри
которого лежит билет доменной аутентификации, и всё это едет тремя cookie
общим объёмом около десяти килобайт.

Дефолтные буферы nginx рассчитаны на заголовки в пределах восьми килобайт.
Когда запрос в них не помещается, клиент получает 400 или 431, причём
внезапно: страница работала, пользователь вошёл через SSO — и перестала.
Поэтому в файле подняты буферы ответа:

```nginx
proxy_buffer_size       32k;
proxy_buffers           8 32k;
proxy_busy_buffers_size 64k;
```

а в самих виртуальных хостах, где ожидаются такие cookie, поднят буфер
запроса:

```nginx
large_client_header_buffers 4 32k;
```

Первая директива относится к ответу от бэкенда, вторая — к запросу от
браузера, и нужны обе. Это частая ошибка: увеличивают что-то одно и
получают ту же ошибку с другой стороны.

`proxy_read_timeout 86400s` в этом же файле держит открытыми долгие
соединения: веб-сокет чата и длинные ходы модели не должны обрываться по
таймауту простоя.

## 8. Имена контейнеров и резолвер

Почти в каждом `location` встречается такая пара строк:

```nginx
resolver 127.0.0.11 [::1]:5353 valid=5s;
set $target http://grafana:3000;
proxy_pass $target;
```

Выглядит избыточно — почему не написать `proxy_pass http://grafana:3000;`?
Причина в том, что nginx резолвит имя из `proxy_pass` **один раз при старте**
и дальше держит адрес в памяти. В docker это ломается на первом же
пересоздании контейнера: сервис получил новый адрес, а nginx продолжает
ходить на старый и отдаёт 502 до перезагрузки конфигурации.

Если же адрес указан через переменную, nginx обязан резолвить имя на каждый
запрос, а `resolver` говорит ему, у кого спрашивать: `127.0.0.11` — это
встроенный DNS docker, а `valid=5s` ограничивает время жизни кэша ответа
пятью секундами. Итог: контейнер пересоздан — nginx подхватывает новый адрес
через несколько секунд, без вмешательства.

Есть нюанс, о котором стоит помнить при правках. Когда в `proxy_pass` стоит
переменная, nginx не выполняет замену префикса пути. То есть при
`location /boba/` с обычным `proxy_pass http://chainlit:8501/` бэкенд
получил бы путь без `/boba/`, а с переменной — получает полный путь как
есть. Здесь это ровно то, что нужно: приложение развёрнуто на своём префиксе
и само его ожидает. Но если однажды понадобится срезать префикс, простого
слэша в конце будет недостаточно.

## 9. Аутентификация: Kerberos, Basic, доверенные заголовки

### Единый вход по доменной учётной записи

Часть сервисов закрыта доменной аутентификацией по SPNEGO: браузер, у
которого есть билет Kerberos, входит без пароля. За это отвечает модуль
`ngx_http_auth_spnego_module`, подключаемый в самом начале `nginx.conf`.

Настройка выглядит так (пример из `grafana.conf`):

```nginx
auth_gss on;
auth_gss_keytab /etc/nginx/nginx.keytab;
auth_gss_realm LOSHARA.COM;
auth_gss_service_name HTTP/grafana.loshara.com;
```

Механика: браузер запрашивает у контроллера домена билет на службу
`HTTP/grafana.loshara.com`, присылает его в заголовке `Authorization:
Negotiate`, а nginx проверяет билет ключом из keytab. Имя службы должно в
точности совпадать с тем, на что браузер просит билет, то есть с внешним
именем хоста, а ключ для этого имени должен лежать в keytab. Отсюда типичная
ошибка настройки: сервис переехал на другое имя, а SPN остался прежним — и
аутентификация молча деградирует до окна с паролем.

Роли берутся из групп домена. Модуль отдаёт список групп пользователя в
переменной, а `map` превращает его в роль приложения:

```nginx
map $spnego_groups $grafana_role {
  default                "";
  "~(^|,)boba-ADM(,|$)"  Admin;
  "~(^|,)boba-DEV(,|$)"  Editor;
  "~(^|,)boba-READ(,|$)" Viewer;
}
```

Здесь важен пустой вариант по умолчанию, и комментарий в файле объясняет
почему: если групп нет, nginx не отправляет заголовок роли вовсе, и Grafana
оставляет пользователю ту роль, что у него уже есть. Иначе вход через
запасной путь без данных о группах понижал бы администратора до зрителя.

### Почему затираются заголовки

Две строки, которые встречаются рядом с каждой SPNEGO-настройкой, заслуживают
отдельного объяснения:

```nginx
proxy_set_header X-WEBAUTH-USER $remote_user;
proxy_set_header Authorization "";
```

Первая передаёт приложению имя аутентифицированного пользователя. Приложение
настроено доверять этому заголовку — иначе смысла в аутентификации на прокси
нет. Но доверие означает, что любой, кто сможет прислать такой заголовок
напрямую, войдёт под чужим именем. Защита здесь ровно одна: nginx **всегда**
устанавливает эти заголовки сам, тем самым затирая то, что прислал клиент.
Именно поэтому в `dbeaver.conf` целый список заголовков принудительно
очищается пустым значением на общем пути и заполняется только на пути, где
аутентификация действительно произошла.

Вторая строка удаляет заголовок `Authorization` перед отправкой в
приложение. Причина в файле объяснена: при запасном входе по паролю модуль
подставляет фиктивный `Basic`-заголовок, и приложение, увидев его, отвергает
запрос своей собственной проверкой пароля, не дойдя до проверки доверенного
заголовка. Есть и обратный пример — путь `/v1/` у `claude-code-router`, где
`Authorization` наоборот пробрасывается как есть, потому что там клиент не
браузер, Kerberos не умеет вовсе, и авторизуется ключом API.

### Хитрый случай: challenge за чужой сервис

В `clickhouse.conf` решается редкая задача. ClickHouse умеет принимать
Kerberos-билет, но сам о такой возможности не объявляет: на анонимный запрос
он отвечает `401` и предлагает только Basic. Браузер и `curl` присылают
билет лишь тогда, когда сервер явно попросил `Negotiate`, — и получается
тупик.

Решение: nginx дописывает недостающее предложение к ответу бэкенда.

```nginx
map $upstream_status $ch_negotiate_challenge {
    401     "Negotiate";
    default "";
}
add_header WWW-Authenticate $ch_negotiate_challenge always;
```

Заголовок добавляется только к ответам с кодом 401, а пустое значение
переменной означает, что заголовок не добавляется вовсе. Basic при этом
остаётся: клиент без билета откатывается на логин и пароль.

### Basic-аутентификация и ограничение по адресам

Для сервисов, которым доменный вход не нужен или не поддерживается,
используется связка проще:

```nginx
allow 192.168.88.0/24;
allow 172.16.0.0/12;
deny all;

auth_basic "ohmy";
auth_basic_user_file /etc/nginx/conf.d/passwords/all;
```

Ограничение по адресам стоит на уровне `server`, пароль — на уровне
`location`. Порядок здесь именно такой, потому что отсечь чужую сеть дешевле,
чем проверять пароль, и потому что список паролей не должен быть
единственной защитой.

Слабое место этой схемы — отсутствие ограничения частоты запросов. Basic не
имеет защиты от перебора: клиент может слать сотни попыток в секунду, и ни
nginx, ни приложение этому не мешают (см. рекомендации).

## 10. Сжатие

```nginx
gzip on;
gzip_comp_level 5;
gzip_min_length 1024;
gzip_vary on;
gzip_types text/plain text/css text/xml application/javascript
           application/json application/xml application/rss+xml
           image/svg+xml font/woff2;
```

Комментарии в файле содержат измерение, ради которого стоит поднять уровень
сжатия с дефолтной единицы: крупный бандл одностраничного приложения даёт
466 килобайт против 420 на пятом уровне, а дальше выигрыш уходит в шум, тогда
как расход процессора продолжает расти. Пятый уровень — это точка, после
которой платить перестаёт быть выгодно.

`gzip_min_length` избавляет от бессмысленного сжатия мелочи: у совсем
коротких ответов накладные расходы на заголовок gzip съедают выигрыш.

`gzip_vary` добавляет заголовок `Vary: Accept-Encoding`. Без него
промежуточный кэш, единожды получив сжатый ответ, может отдать его клиенту,
который сжатие не запрашивал.

`gzip_types` пришлось перечислить, потому что по умолчанию nginx сжимает
только HTML. Список закрывает всё, что действительно даёт выигрыш: текст,
стили, скрипты, JSON, SVG и шрифты. Картинки и видео в список не входят
намеренно: они уже сжаты своим форматом, и повторное сжатие только тратит
процессор.

Отдельно отмечено, что `text/event-stream` в список не добавлен. Поток
событий сжимать незачем, а фильтр сжатия неизбежно вносит буферизацию, то
есть именно ту задержку, которой поток и старается избежать.

## 11. Таймауты, лимиты и буферы

В `nginx.conf` заданы очень большие значения:

```nginx
proxy_read_timeout  86400s;
proxy_send_timeout  86400s;
send_timeout        86400s;
proxy_connect_timeout 360s;
client_max_body_size 0;
```

Логика понятна: через прокси идут веб-сокеты, длинные ходы модели, консоли и
выгрузки, а нулевой лимит на тело запроса позволяет загружать файлы любого
размера. Сутки простоя — это способ гарантировать, что ничто живое не будет
оборвано.

Обратная сторона тоже понятна. Таймаут чтения — это защита от зависшего
бэкенда: если приложение перестало отвечать, nginx будет держать соединение
сутки, и такие соединения накапливаются, занимая воркеры. Нулевой лимит на
тело запроса означает, что любой клиент может начать заливать в прокси
терабайт, и остановит его только место на диске бэкенда.

Разумнее задать умеренные значения глобально и поднимать их точечно там, где
это действительно нужно. Так уже сделано для отдельных путей: у выгрузки в
`dbeaver.conf` стоят свои сутки, у потока событий — час, у API модели — час.
Не хватает только уменьшить глобальные значения (см. рекомендации).

Ещё две строки в `nginx.conf` относятся к внутренним таблицам:

```nginx
proxy_headers_hash_max_size 1024;
proxy_headers_hash_bucket_size 128;
```

Они подняты потому, что заголовков, устанавливаемых прокси, много, и при
дефолтных размерах nginx отказывается стартовать с сообщением о нехватке
места в хеш-таблице. Это чисто техническая настройка, менять её не нужно.

## 12. Логи и наблюдаемость

Формат журнала переопределён так, чтобы одна строка отвечала на все обычные
вопросы:

```
[время] [адрес:порт] метод схема://хост/путь | путь | код (время_обработки, num, cnt, bytes)
```

Здесь есть время обработки запроса, номер соединения и счётчик запросов
внутри него — по последним двум видно, переиспользует ли клиент соединение,
и это заметно помогает при разборе странного поведения веб-сокетов и
keep-alive.

`log_subrequest on` добавляет в журнал внутренние подзапросы. Это полезно при
отладке аутентификации и любых схем с `auth_request`, где основная работа
происходит именно в подзапросе, но делает журнал заметно многословнее.

Состояние сервера отдаётся отдельным хостом на внутреннем порту:

```nginx
server {
  listen 8080;
  location /nginx_status {
    stub_status;
    allow 127.0.0.0/8;
    allow 172.18.0.0/16;
    deny all;
  }
}
```

Этот адрес читает `nginx-exporter`, который переводит счётчики в метрики
Prometheus. Ограничение по адресам обязательно: страница показывает число
активных соединений и запросов, наружу её отдавать незачем.

Что сейчас настроено плохо — ротация. На момент написания документа
`logs/access.log` занимает 134 мегабайта, `logs/error.log` — 100 мегабайт,
и ни один из них не ротируется. Вторая цифра особенно показательна: уровень
журнала ошибок выставлен в `info`, то есть туда пишется поток обычных
событий, а не только проблемы (см. рекомендации).

## 13. Контейнер: rootless и запрет записи

`docker-compose.yml` заслуживает внимания не меньше, чем сама конфигурация,
потому что там решается вопрос «что сможет сделать злоумышленник, если
однажды найдёт дыру в nginx».

```yaml
user: "101:101"
cap_drop: [ALL]
security_opt: [no-new-privileges:true]
sysctls: [net.ipv4.ip_unprivileged_port_start=0]
read_only: true
tmpfs:
  - /var/cache/nginx:mode=1777
  - /var/tmp:mode=1777
```

Обычно nginx запускается от root, чтобы занять порты ниже 1024, и лишь потом
переключает рабочие процессы на непривилегированного пользователя. Здесь
root не нужен вовсе: процесс сразу работает под своим uid, а право занять
порты 80 и 443 даёт параметр ядра, разрешающий непривилегированным процессам
низкие порты. Все capability сняты, повышение привилегий запрещено.

Корневая файловая система смонтирована только для чтения, поэтому
подменить бинарник или конфигурацию изнутри контейнера нельзя. Писать nginx
может ровно в два места в памяти: свой каталог кэша и временных файлов и
`/var/tmp`, куда библиотека GSSAPI кладёт кэш защиты от повторов Kerberos.
Журналы пишутся в примонтированный каталог хоста.

Конфигурация, ключи и сертификаты примонтированы только для чтения — включая
keytab, файл, из которого читаются ключи доменной службы.

Ограничения ресурсов (гигабайт памяти, половина ядра) не дают одному
сервису утянуть за собой хост.

Экспортёр метрик настроен так же строго и даже строже: статический бинарник
работает от `nobody`, без capability и без права записи.

## 14. Что стоит поменять: приоритетный список

Ниже — рекомендации по текущей конфигурации, от более важных к менее важным.
Каждая описывает проблему, а не просто «лучшую практику».

### 14.1. Ротация журналов

Сейчас журналы растут неограниченно, суммарно уже около 235 мегабайт. Рано
или поздно это закончится заполнением диска, причём в самый неудобный
момент. Нужна ротация: либо `logrotate` на хосте с последующей отправкой
сигнала `USR1` контейнеру, либо драйвер журналирования docker с ограничением
размера.

### 14.2. Уровень журнала ошибок

`error_log /var/log/nginx/error.log info;` — это подробный режим, который
имеет смысл включать на время расследования, а не держать постоянно. Он даёт
сто мегабайт шума и, что важнее, скрывает настоящие ошибки среди рутинных
записей. Рабочее значение — `warn` или `error`, а `info` включать точечно,
когда что-то расследуется.

### 14.3. Число соединений на воркер

`worker_connections 1024` — дефолт, рассчитанный на скромную нагрузку.
В нашем случае за прокси стоят приложения с долгоживущими веб-сокетами, а
каждое проксируемое соединение занимает две записи: к клиенту и к бэкенду.
При нескольких десятках виртуальных хостов упереться в лимит вполне реально,
и выглядеть это будет как случайные отказы под нагрузкой. Разумное значение
— 4096 или 8192, вместе с явным `worker_rlimit_nofile`, иначе лимит
дескрипторов станет новым потолком.

### 14.4. Скрыть версию

Ответы содержат `Server: nginx/1.28.0`. Это подсказка для того, кто ищет
известные уязвимости конкретной версии. Директива `server_tokens off;` в
`http`-блоке убирает номер версии. Защитой это не является, но снижает
привлекательность цели.

### 14.5. Явный хост по умолчанию

Сейчас запрос с незнакомым именем попадает в первый по порядку
`server`-блок. Порядок определяется алфавитом при подключении файлов, то
есть держится на том, что имя `_default.conf` начинается с подчёркивания.
Это хрупко: достаточно переименовать файл, и точка входа по умолчанию
сменится незаметно.

Последствие видно прямо сейчас. Запрос с неизвестным именем хоста доходит
до `_default.conf`, не совпадает ни с одним из его путей и получает
стандартную страницу «Welcome to nginx!» из каталога по умолчанию:

```
$ curl -sk -H "Host: nosuchhost.example" https://<хост>/ | head -3
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
```

Сканеру этого достаточно, чтобы понять, что за адресом живой веб-сервер.
Лучше объявить хост по умолчанию явным флагом `default_server` и отвечать на
неизвестные имена разрывом соединения (`return 444;`), чтобы не отдавать ни
страницы, ни редиректа.

### 14.6. Глобальные таймауты и лимит тела запроса

Значения `86400s` и `client_max_body_size 0` разумно оставить только там, где
они действительно нужны, а глобально снизить — скажем, до минуты на чтение и
разумного предела на размер тела. Тогда зависший бэкенд перестанет копить
соединения, а случайная многогигабайтная загрузка на произвольный хост
будет отвергнута сразу.

### 14.7. Ограничение частоты для входов с паролем

Пути с `auth_basic` и страницы входа приложений сейчас никак не защищены от
перебора. Пара зон `limit_req` (по адресу клиента) на этих путях делает
перебор бессмысленным и почти ничего не стоит:

```nginx
limit_req_zone $binary_remote_addr zone=login:10m rate=10r/m;
# в нужном location:
limit_req zone=login burst=5 nodelay;
```

### 14.8. HTTP/2 для всех хостов

HTTP/2 включён у одного хоста. Для остальных он тоже полезен: мультиплексирование
запросов в одном соединении заметно ускоряет загрузку интерфейсов с большим
числом мелких файлов. Раз с мультиплексором на 443 это уже проверено на
одном хосте, стоит вынести `http2 on;` в общий подключаемый файл рядом с
настройками TLS. Образ собран и с поддержкой HTTP/3, так что при желании
можно посмотреть и в эту сторону, но это уже отдельная работа с UDP и
объявлением альтернативного сервиса.

### 14.9. Постоянные соединения к бэкендам

Сейчас каждое проксируемое соединение открывается заново. Для сервисов с
частыми короткими запросами (API, метрики) блок `upstream` с директивой
`keepalive` снимает накладные расходы на установление соединения. Важная
деталь: в таких блоках нужно отправлять `Connection ""`, а не `upgrade`,
поэтому общий `proxy.conf` для них не подойдёт — понадобится отдельный
набор, как это уже сделано для потока событий.

### 14.10. Заголовки безопасности

`X-XSS-Protection` можно удалить: он ничего не делает в современных
браузерах. Его настоящая замена — `Content-Security-Policy`, но эту политику
нельзя включить одной строкой для всех: она подбирается под конкретное
приложение и почти всегда требует правок фронтенда. Разумный путь — начать с
одного-двух сервисов в режиме отчёта (`Content-Security-Policy-Report-Only`)
и расширять постепенно.

Если домен точно никогда не будет отдаваться по HTTP, к HSTS можно добавить
`preload` и внести домен в список предзагрузки браузеров. Решение
необратимое, поэтому только осознанно.

### 14.11. Список разрешённых адресов вне кода

Подсети, с которых пускают RDP, LDAP, Kerberos и SMB, зашиты в
`njs/rdp.js`. Каждое изменение — правка кода. Список стоит вынести в
отдельный файл данных, который скрипт читает при загрузке; тогда изменение
периметра перестанет быть правкой логики.

### 14.12. Мелочи

`log_subrequest on` полезен при отладке аутентификации, но удваивает объём
журнала. Если сейчас ничего не расследуется, его можно выключить.

Дублирование `proxy.conf` и `boba-headers.conf` (второй файл повторяет
первый целиком и добавляет четыре строки) стоит убрать: пусть второй
подключает первый и дописывает только своё. Сейчас любое изменение в общем
наборе нужно вносить дважды, и рано или поздно про второе место забудут.

## 15. Диагностика: симптом, причина, куда смотреть

| Симптом | Вероятная причина | Что смотреть |
|---|---|---|
| 502 сразу после пересоздания контейнера | адрес закэширован; в `location` не хватает `resolver` и `set` | наличие пары `resolver`/`set` в этом `location` |
| Веб-сокет не поднимается, приложение жалуется на рукопожатие | не подключён `proxy.conf` либо в блоке два заголовка `Connection` | какие `proxy_set_header` действуют в этом `location` |
| Поток данных приходит рывками или с задержкой | включена буферизация или сжатие на пути потока | `proxy_buffering`, `gzip` для этого пути |
| 400 или 431 после входа через SSO | заголовки не помещаются в буферы | `large_client_header_buffers` в `server`, `proxy_buffer_size` в наборе прокси |
| SSO не срабатывает, браузер спрашивает пароль | имя службы не совпало с внешним именем хоста, либо в keytab нет ключа | `auth_gss_service_name`, содержимое `nginx.keytab` |
| Grafana понижает роль администратора | в ветку `map` попало пустое значение групп | значение `$spnego_groups` и `default` в `map` |
| HSTS и другие заголовки пропали на части путей | в `location` появился свой `add_header` | все `add_header` в этом `server` и его `location` |
| Не-HTTP протокол не проходит на 443 | адрес не в списке разрешённых, либо сигнатура не распознана | список в `njs/rdp.js`, журнал stream-блока |
| Приложение видит всех клиентов как `127.0.0.1` | не работает восстановление адреса из PROXY-заголовка | `set_real_ip_from`, `real_ip_header`, наличие `proxy_protocol` в `listen` |
| Кончилось место на диске | журналы не ротируются | размер `logs/access.log` и `logs/error.log` |

## Приложение: порядок правки

Конфигурация раскладывается по контейнеру только для чтения, поэтому цикл
изменения такой:

1. Правим файл на хосте в `/app/docker/compose/nginx`.
2. Проверяем синтаксис, не трогая работающий процесс:
   `docker exec nginx nginx -t`.
3. Применяем без разрыва соединений: `docker exec nginx nginx -s reload`.
   Старые воркеры дорабатывают текущие запросы и завершаются сами.
4. Смотрим журнал ошибок первые секунды после перезагрузки.

Перезапуск контейнера нужен только при смене образа, тома или параметров
запуска. Изменения в `njs/rdp.js` подхватываются перезагрузкой, как и
обычная конфигурация.
