# Соединения пользователя: декларативный параметр вместо базовых классов

План переработки. Цель: инструмент объявляет соединение аннотацией параметра,
а весь поиск, проверку прав и подготовку кредов делает хост. Ядро перестаёт
знать про конкретные семейства соединений.

## 1. Что не так сейчас

Инструмент, которому нужно соединение пользователя, обязан объявить
injected-конфиг наследником одного из двух классов: `SqlProfiles` из
`boba.toolkit.sql` либо `WebConnection` из `boba.transport.http.web`. Хост
выбирает, вешать ли обвязку, проверкой `isinstance(base, SqlProfiles |
WebConnection)`.

Отсюда три проблемы.

**Ядро знает про семейства.** `SqlProfiles` лежит в `packages/core`. Новый вид
соединения, который не является ни SQL, ни web (очередь, объектное хранилище,
брокер сообщений), не имеет своего места: либо правится ядро, либо тип
наследуется от SQL-класса, к которому отношения не имеет.

**Сервис знает про транспорт.** `boba-connection-broker` держит
`boba-transport-http` в обычных зависимостях только ради `WebConnection`,
`HttpConnection` и `HostPattern`: в обвязке есть web-специфичный шаг `_at_host`,
который читает аргумент `url` и привязывает профиль к хосту.

**Инструмент делает работу хоста.** Тело получает whitelist и само достаёт из
него профиль вызовом `cfg.resolve(connection_name)`. Ключ адресации при этом
зашит перечислением `ConnectionKeying` с единственным значением, поэтому два
соединения в одном вызове выразить нечем. Инструмент `*_connection_list`
продублирован в каждом плагине.

## 2. Целевая модель

Соединение объявляется на параметре: тип параметра — модель профиля, маркер
рядом с ним говорит, что значение приходит из соединений пользователя.

```python
@tool
async def redis_query(
    connection: Annotated[RedisConfig, UserConnection],
    command: Annotated[str, Field(min_length=1, description="Команда redis")],
    cfg: Annotated[RedisToolConfig, Injected],
) -> tuple[str, ToolResult]:
    """Выполнить команду redis на выбранном соединении."""
    client = await open_redis(connection)
```

У параметра две ипостаси:

- для LLM это строка — имя соединения, которое модель выбирает;
- для тела это готовый профиль с кредами внутри.

Между ними работает хост. Он читает имя из аргументов вызова, определяет вид
соединения по типу параметра, спрашивает у хранилища строки субъекта этого
вида, снимает неоднозначности, готовит креды и подставляет профиль в аргумент.

Вид соединения хост берёт из аннотации: у профиля поле `kind` объявлено как
`Literal`, реестр `ConnectionTypes` уже сопоставляет `kind` и модель, обратное
сопоставление добавляется в реестр одним методом. Списка семейств в ядре не
появляется.

Несколько соединений в одном вызове получаются сами собой: два параметра с
маркером, у каждого своё имя и свой тип.

```python
@tool
async def pg_copy_between(
    source: Annotated[PostgresConfig, UserConnection],
    target: Annotated[PostgresConfig, UserConnection],
    sql: Annotated[str, Field(...)],
) -> tuple[str, ToolResult]: ...
```

## 3. Решения, принятые до начала работ

**Список соединений для модели.** Один общий инструмент `connection_list`
вместо трёх плагинных. Возвращает имя, вид и описание каждой доступной строки.
Описание берётся из нового поля `description` в базовой модели профиля, то есть
хранится в jsonb вместе с остальным профилем и правится на странице соединений.
Модель по описанию понимает, какое имя передать в инструмент.

**Kerberos и хосты.** Знание о том, где в профиле лежит хост и как получить
билет, остаётся у реализации типа: базовый класс профиля объявляет
`kerberos_section()`, `service_name()` и `with_call_ticket()`, а общий
kerberos-компонент выпускает билет по этим данным. Хост не разбирает типы.
Web-специфичный шаг привязки к хосту URL с хоста снимается: проверить, что
запрошенный URL покрывается соединением, обязан сам инструмент в теле.

**Совместимость.** Старый путь удаляется целиком, без промежуточных слоёв
совместимости. Плагины pg, ch и web переезжают в рамках этой же работы.

## 4. Этапы

Все этапы выполнены; ниже — что сделано на каждом.

Каждый этап заканчивается зелёными тестами и отдельным коммитом.

### Этап 1. Маркер параметра и контракт команды (toolkit)

Сделано.

- `UserConnection` — маркер рядом с `Injected` в `boba/toolkit/facade.py`.
  Распознаётся по имени класса, как остальные маркеры.
- `ToolArgv`: метод `connection_fields(schema)`; значения таких параметров
  уезжают инъекционным каналом (в них креды), а не через argv; обратный разбор
  валидирует их в модель профиля.
- Тесты: команда собирается и разбирается, секрет не попадает в argv.

### Этап 2. Реестр и модель профиля (connections)

Сделано.

- `description` в `ConnectionProfileBase`.
- `ConnectionTypes.kind_of(model)` — вид по типу профиля; неизвестный тип даёт
  внятную ошибку.
- Упрощение whitelist: ключ всегда имя, `ConnectionKeying` удаляется.
- `ConnectedToolManifest` и `UserConnectionsSpec` удаляются: вид приходит из
  аннотации, манифесту объявлять нечего.

### Этап 3. Хост: обвязка по аннотации

Сделано.

- `UserConnections` переписывается: находит connection-параметры по схеме,
  определяет вид по типу, резолвит строку субъекта, готовит креды, подставляет
  профиль.
- Схема, которую видит LLM, получает на месте параметра строку с описанием.
- `_at_host` и `_hosts` удаляются, зависимость брокера от `boba-transport-http`
  снимается.
- `ToolLoader` вешает обвязку по наличию connection-параметров, а не по
  манифесту.

### Этап 4. Общий connection_list

Сделано.

- Встроенный инструмент рядом с workflow и pipeline: отдаёт имя, вид и описание
  доступных строк субъекта.
- Плагинные `pg_connection_list`, `ch_connection_list`, `web_connection_list`
  удаляются.

### Этап 5. Переезд плагинов

Сделано.

- pg, ch, web переходят на параметр с маркером; `cfg.resolve` уходит из тел.
- Проверка хоста URL переезжает в тело web-инструмента.
- `SqlProfiles` удаляется из ядра, `WebConnection` — из transport-http.
- Лимиты выдачи (`max_rows`, `max_bytes`) остаются обычными полями
  injected-конфига секции.

### Этап 6. Studio, workflow, тесты

Сделано.

- Вид аргумента для страниц: хост кладёт `ConnectionArg(family=<kind>)` в
  метадату строки, которую видит модель, поэтому страницы workflow рисуют
  выбор соединения нужного вида. Инструменту объявлять вид больше не нужно.
- Гайд docs/adding-connections-and-tools.md переписан под новую модель.
- Тесты: test_connection_binding.py в брокере (обвязка без песочницы и
  домена), test_connection_param.py в toolkit (контракт команды).

## 5. Что останется без изменений

Хранилище и схема таблиц: `connections`, `roles`, `grants`, шифрование
профилей, значения `kind` в jsonb. Миграция данных не нужна.

Выпуск билета вызова: `ServiceTicketIssuer`, `TicketAuth`, подстановка билета
вместо keytab и разбор его в теле остаются как есть.

Страница соединений в studio: формы строятся из json-schema реестра, новое поле
описания появится на ней само.

## 6. Что изменилось по ходу работ

Сверх плана по замечанию пользователя:

**ClientLabel убран из ядра.** Он рендерил строку подписи и резал её до 63
байт — предела `application_name` postgres, то есть нёс специфику одного
сервера в общем слое. Теперь ядро передаёт данные (`ClientIdentity`:
приложение, логин, инструмент), а рендер и предел длины живут в профиле:
`ApplicationName` в postgres, `ClientName` в clickhouse.

**HttpProfile переименован в HttpConnection** — симметрично остальным типам.
