# Реестр LLM и пользовательские агенты: план реализации

Дата: 2026-11-05. Статус: план работ, реализация ещё не выполнена.

Документ предназначен для агента-исполнителя и не требует истории переписки.
Пути ниже указаны относительно корня репозитория. Перед работой сверить их с
текущим кодом: в рабочем дереве уже есть изменения других задач.

## 1. Цель и первый результат

Пользователь или администратор создаёт LLM-провайдеров и записи моделей в
собственной БД Boba. Эти записи становятся доступны без перезапуска приложения.
В дальнейшем пользователь сохраняет собственные определения агентов: модель,
инструкции, параметры генерации, skills, инструменты и политику памяти.

**Первый законченный этап:** Boba запускается с пустым реестром; уполномоченный
пользователь через ACP создаёт провайдера и модель; открывает сессию с этой
моделью и получает ответ. Повторное подключение клиента и второй процесс Boba
видят сохранённые изменения. Перезапуск и редактирование конфигурационного
файла не нужны.

Первый этап использует существующие адаптеры инференса. Редактор полного
определения агента, долговременная память и развитие контракта инференса —
следующие самостоятельные этапы. Не считать весь план выполненным после
появления таблиц или только первого сквозного сценария.

Сохранить собственные HTTP-адаптеры OpenAI-compatible и Ollama, привести их
к целевому контракту и динамическому реестру. Контракт описан в разделе 10,
конкретные изменения адаптеров и сборки ресурсов — в разделе 11.

## 2. Обязательные ограничения

- Хранение провайдеров и определений агентов принадлежит Boba.
- Провайдеры — программные библиотеки, работающие внутри процесса:
  OpenAI-compatible, нативный Ollama, ONNX GenAI, FastEmbed.
- AID взаимодействует с Boba исключительно через ACP и согласованные расширения
  ACP. Не добавлять прямые запросы AID к таблицам Boba или обходной REST API.
- Не переносить пользовательские данные из прежней схемы и конфигурационных
  файлов автоматически. Обратная совместимость старых пользовательских
  контрактов не является требованием. Изменения документировать явно.
- `migrate` приводит схему к указанной версии в указанном месте. Не добавлять
  backfill, импорт TOML, переименование бизнес-идентификаторов, анализ старых
  пользователей и зависимость от конкретной предыдущей схемы.
- Не запускать миграции на реальной БД в рамках реализации. Не применять
  разрушительный обход несовместимых данных: сохранить транзакционную ошибку
  и понятное объяснение администратору.
- **Агент реализации меняет программный код и необходимую документацию.
  Тесты не изменяет и не запускает; их обновление, проверку поведения, отладку
  и деплой пользователь передаёт отдельной модели.** Разрешены необходимые
  статические проверки изменённого кода. Сценарии проверки передать в отчёте.
- Не добавлять произвольные поля `metadata`, `meta`, `extras` для обхода
  проектирования. У данных должен быть тип и владелец; связи хранить явно.
- Не создавать отдельный пакет или сервис для каждой сущности. Использовать
  существующие слои; новый пакет обосновывать самостоятельной ответственностью.
- Не скрывать новые циклы импортов через `TYPE_CHECKING` или локальные импорты.
  Контракты должны находиться ниже своих реализаций в графе зависимостей.
- Сохранять чужие изменения рабочего дерева.

## 3. Границы ответственности

```text
AID: редактор и интерфейс чата
  ↕ ACP, включая согласованные расширения управления
Boba: реестр, права, определения агентов, разрешение авторизации провайдера,
      сборка контекста, исполнение, сессии и история
  ├── собственная схема PostgreSQL
  └── boba.llm: ChatModel / EmbeddingModel
        └── адаптеры → HTTP API либо локальные библиотеки инференса
```

Под Boba здесь понимается приложение из `packages/apps/boba-cli`, в том числе
его сервисный режим. Общие библиотеки ядра не должны импортировать это приложение.

- Реестр, определения агентов и их авторизация принадлежат Boba. Один кластер
  PostgreSQL допустим, но не означает общего владения таблицами AID и Boba.
- AID показывает разрешённый каталог и отправляет команды. Проверки прав
  выполняет Boba при чтении, изменении и использовании ресурсов.
- Адаптер инференса получает разрешённую конфигурацию обращения. Он не знает
  о PostgreSQL, AID, ACP, владельцах записей или пользовательских ролях.
- MCP продолжает владеть своими ресурсами. Сохранённый агент содержит
  устойчивые ссылки на инструменты/ресурсы, а не копию каталога MCP.
- Реестр установленных адаптеров отделён от реестра провайдеров. Новый
  провайдер установленного типа не требует перезапуска. Новый тип адаптера
  требует установки кода; новые локальные веса требуют подготовки исполнителя.

## 4. Целевые сущности

Названия ниже описывают смысл; это не требование создать по отдельному классу,
пакету и таблице для каждой строки. Физическую схему определить на этапе 0.

| Сущность | Содержание |
| --- | --- |
| Адаптер (`adapter`) | Установленный `kind`, схема допустимой конфигурации, поддерживаемые операции и способы авторизации |
| Провайдер (`provider`) | Настроенный источник инференса: стабильный ID, название, владелец, состояние, ревизия, тип адаптера, адрес API либо ссылка на управляемый локальный ресурс, политика авторизации |
| Авторизация провайдера (`provider auth`) | Способ авторизации и привязка защищённых данных к провайдеру и субъекту использования; владелец, состояние и ревизия привязки |
| Модель (`model`) | Стабильный ID, ссылка на провайдера, имя модели у провайдера, назначение chat/embedding, возможности и ограничения |
| Определение агента | ID, владелец, права, ревизия, выбранная модель, инструкции, параметры генерации/контекста, ссылки на skills, инструменты и политику памяти |
| Сессия | Владелец, выбранные ревизии конфигурации, история и состояние исполнения |

Например, `ollama` — адаптер, «Домашняя Ollama» — провайдер, `qwen3:8b` —
модель. В предметных типах и API реестра использовать `provider`, а не
`connection`, чтобы отличать эту сущность от connections в MCP. Технические
HTTP-подключения и общие типы транспортной инфраструктуры переименовывать не нужно.

Управление авторизацией в публичном API привязано к провайдеру. Отдельный
верхнеуровневый каталог `credentials` не вводить. Защищённые данные могут
храниться отдельно и использовать общую инфраструктуру шифрования: границы
API не обязаны повторять разделение таблиц. Термин credentials ниже обозначает
сам материал авторизации, а не самостоятельную публичную сущность реестра.

Уточнения для контрактов:

- Возможности модели и бюджета агента различаются. Например, физическое окно
  модели и выбранный агентом бюджет контекста — разные поля. Проверять бюджет
  вместе с резервом ответа; не разрешать превышение поддерживаемого окна.
- Для embeddings фиксировать размерность и идентичность модели. Смена модели
  не означает совместимости уже построенного векторного индекса.
- Возможности адаптера не гарантируют возможностей любой модели. Проверка
  совместимости учитывает обе стороны. Автоматическое обнаружение моделей
  необязательно для первого этапа; ручное добавление должно работать.
- Типизированные настройки протокола допустимы. Они не должны позволять через
  `sampling` подменять сообщения, модель, credentials или адрес запроса.
- Нормализовать владельцев, ссылки, grants, ревизии и ключевые ограничения.
  Если узкий типизированный документ хранится в JSONB, обосновать это отдельно;
  не превращать весь реестр или определение агента в универсальный JSON-мешок.
- Локальный путь к весам и лимиты исполнителя относятся к управлению ресурсами
  Boba. Обычный пользователь выбирает разрешённый ресурс, а не произвольный
  путь на файловой системе сервиса.

## 5. Доступ и авторизация провайдера

Различать три независимые авторизации: вход пользователя в Boba, доступ к LLM,
доступ к MCP/другим инструментам. Входной токен не становится автоматически
ключом провайдера и не сохраняется внутри определения агента.

Предлагаемая начальная политика, которую необходимо явно закрепить в контракте:

1. Новые пользовательские ресурсы приватны. Действия управления и использования
   различаются; общие ресурсы доступны через явно выданные права.
2. Провайдер задаёт явный режим: без авторизации, выделенные credentials
   провайдера либо credentials текущего пользователя. Нет неявного перехода
   с отсутствующего пользовательского ключа на ключ владельца или администратора.
3. Для общих credentials право использовать провайдера разрешает исполнение
   через этот секрет, но не чтение секрета. Для пользовательского режима
   получатель общего агента должен иметь собственную подходящую привязку.
4. Право на определение агента не выдаёт автоматически права на все его
   зависимости. Проверять доступность модели, провайдера, credentials и
   инструментов в контексте вызывающего пользователя.
5. Секреты шифруются существующим инфраструктурным механизмом. Ответы чтения
   каталога не возвращают секрет; правила обновления различают «не менять»,
   «заменить» и «удалить». Секреты не входят в историю, снимок промпта и логи.
6. Первичное управление пустым реестром доступно через существующую явно
   настроенную административную авторизацию. Не выдавать администратора
   первому вошедшему и не требовать наличия модели для входа в управление.

Перед реализацией проверить возможности существующих `boba-access`, auth и
`SecretCipher`. Не создавать параллельную систему идентичности или grants.
Каталог динамических моделей не должен зависеть от списка имён профилей,
зафиксированного в токене при входе. Отзыв права должен учитываться перед
следующим обращением; изменение состава ролей также не должно незаметно
оставаться разрешённым до бесконечного завершения старого ACP-подключения.

## 6. ACP-контракт управления

В проекте используется ACP v2 через `acp.experimental.v2`; версию и доступные
типы сверить с зависимостями. Уже существуют расширения `_boba/...`.

Стандартные session config options использовать для выбора доступного значения
в сессии. CRUD реестра оформить собственными типизированными расширениями.
Ниже предлагаемые имена, а не существующие методы стандартного ACP:

| Группа | Операции |
| --- | --- |
| `_boba/llm/adapters/...` | Список установленных типов и поддерживаемых возможностей |
| `_boba/llm/providers/...` | list/get/create/update/delete/check, управление доступом к провайдеру |
| `_boba/llm/providers/auth/...` | get/set/delete авторизации в контексте провайдера и разрешённого субъекта использования |
| `_boba/llm/models/...` | list/get/create/update/delete, управление доступом |
| `_boba/agents/...` | Следующий этап: определения агентов и их ревизии |

Методы `providers/auth/...` принимают ID провайдера и однозначно определяют,
какая привязка используется: общая привязка провайдера или привязка текущего
пользователя. Право изменять каждую из них проверяется отдельно. `auth/get`
возвращает только способ авторизации и безопасное описание состояния привязки,
без секрета; `auth/set` задаёт или заменяет данные, `auth/delete` удаляет
привязку. Запись чужой пользовательской привязки не разрешается простым
указанием чужого ID в запросе.

Требования к протоколу:

- Согласовывать поддержку и версию расширения через capabilities. Для
  неподдерживаемой обязательной операции возвращать явную ошибку.
- Каждый метод имеет типы запроса, ответа и ошибок. Запретить неизвестные
  поля; определить пагинацию и стабильный порядок для списков.
- Update/delete принимают ожидаемую ревизию; изменение условное и атомарное.
  Конфликт не перезаписывает чужую правку.
- Повтор create после потери ответа не должен незаметно создавать дубликаты:
  определить клиентский ID либо ключ идемпотентности и правила его повторения.
- Сохранение конфигурации не требует доступности провайдера. Проверка
  подключения — отдельная ограниченная операция, учитывающая текущие права
  и credentials; она не доказывает поддержку всех возможностей модели.
- Управление реестром не требует активной чат-сессии или загруженной модели.
- Выбор модели передаётся устойчивым ID. Не использовать отображаемое имя как
  идентификатор; не передавать секреты в `session/new` или config options.
- При появлении выбора агента связать его с конкретной ревизией. Изменение
  модели внутри агента допустимо только если это разрешено его политикой.
- Использовать существующий механизм ошибок ACP. Числовые коды прикладных
  ошибок определить централизованно, не выдавать придуманные коды за стандарт.

Минимальные категории ошибок: некорректные параметры, неподдерживаемый тип или
возможность, отсутствие ресурса/доступа, конфликт ревизии, ресурс используется,
credentials отсутствуют/отозваны, провайдер недоступен, локальная модель не
подготовлена. Не раскрывать существование чужих приватных ресурсов через
различие сообщений об отсутствии и запрете.

## 7. Ревизии, сессии и несколько процессов

- Новая сессия использует актуальную разрешённую конфигурацию. Открытая сессия
  сохраняет выбранную ревизию; сохранить необходимые неизменяемые данные для
  возобновления, а не только номер изменяемой строки.
- Изменения применяются к открытой сессии явно между ходами. Не менять модель,
  системный промпт или параметры посередине генерации.
- Отзыв права, отключение ресурса и отзыв credentials действуют независимо от
  закрепления конфигурации. Перед следующим обращением проверить их заново.
  Политику уже выполняющегося обращения определить явно; не обещать удалённую
  отмену инференса, если провайдер её не поддерживает.
- Предлагаемый вариант удаления: запретить физическое удаление используемых
  ресурсов, предложить отключение. История остаётся читаемой; последующее
  исполнение отключённой зависимости завершается понятной ошибкой.
- Для первого этапа читать актуальное состояние БД при выборе/использовании
  ресурса. Не строить сразу распределённую шину инвалидирования. Кеш не должен
  делать изменения видимыми только тому процессу, который их записал.
- Ключ повторного использования HTTP-клиента учитывает ID провайдера, его
  ревизию, субъект и ревизию привязки авторизации. Не разделять пользовательский
  авторизованный клиент между разными субъектами по одному URL.
- Устаревший клиент закрывается после освобождения активных пользователей;
  запрос не должен внезапно потерять транспорт из-за обновления реестра.
- HTTP-клиенты принадлежат своему event loop. Локальные веса можно разделять
  на уровне процесса с явными ограничениями конкурентного исполнения.
- Параметры генерации задаются на обращение. Не мутировать общий экземпляр
  модели ради параметров одного пользователя. Отмена ожидания локального
  потока не равнозначна остановке уже запущенной работы в thread.

| `packages/apps/boba-cli/src/boba/cli/migrations/` | DDL владельца нового реестра; подключение к существующему runner и выбору schema/version |

Найти остальных потребителей `LlmProviders`, `ChatModelConfig`,
`EmbeddingModelConfig`: индексаторы `packages/apps/ix` и пакеты инструментов
также используют инференс. Не превращать каждый автономный индексатор в
обязательного клиента сервиса Boba. Исправить затронутые программные контракты,
не расширяя перенос пользовательского реестра на все приложения автоматически.

## 10. Целевой контракт инференса

Этот раздел задаёт контракт для этапа 6. Различия протоколов OpenAI/Ollama
нормализуются на границе адаптера; доменные потребители работают с типами Boba.

### 10.1. Ответ и причина завершения

Сохранить `ChatModel.chat(ChatRequest)` и поток `ChatDelta | ChatReply`.
Для обычного запроса без стриминга выдаётся один `ChatReply`. Достоверно
завершённое обращение заканчивается ровно одним `ChatReply`, после которого
событий нет. Обрыв, ошибка и отмена не создают фиктивного финального ответа.

Добавить обязательный типизированный `ChatReply.finish_reason`:

| Значение | Смысл для Boba | Действие слоя агента |
| --- | --- | --- |
| `stop` | Генерация завершена без вызова инструментов | Использовать ответ; отдельно применить политику пустого ответа |
| `tool_calls` | Полностью получены корректные вызовы инструментов | Проверить права/аргументы и исполнять вызовы |
| `output_limit` | Провайдер явно сообщил достижение потолка генерации | Сохранить текст/reasoning/usage и обработать ограничение |
| `blocked` | Провайдер явно завершил ответ фильтрацией | Показать предусмотренное сообщение, не исполнять инструменты |

Это нормализованные исходы. Например, нормальный
Ollama `done_reason=stop` с корректными вызовами преобразуется в `tool_calls`.
Явный лимит или фильтрация имеют приоритет над наличием вызовов. Не выводить
blocked из содержания обычного текстового отказа модели.

Отсутствующий/неизвестный terminal status не превращать автоматически в stop.
Допустимые случаи восстановления статуса определяет адаптер для конкретного
протокола и подтверждает отдельной проверкой, а не общей эвристикой по EOF.
Исключениями остаются ошибки обращения: недоступность, HTTP-отказ, превышение
входного контекста, повреждённый ответ и обрыв без достоверного финала.
Отмена сохраняет принятую семантику cancellation.

`LlmOutputLimitError` перестаёт описывать **подтверждённый** лимит генерации
в порте. В `ModelAsk.attempt` преобразовывать новый итог в существующий
`OutputLimited`; не изобретать заново все исходы агента. Для blocked добавить
явный путь обработки с сохранением уведомлений интерфейса. Пустой корректно
завершённый ответ — stop; необходимость повтора решает агент, как уже делает
`TurnLoop._is_empty`. Не оставлять два способа выдачи одного и того же финала.

При `output_limit`/`blocked` содержимое может быть частичным. Tool calls
исполняются только при `finish_reason=tool_calls`. Незавершённые JSON-аргументы
не превращать в `ToolCall`, не достраивать и не подставлять `{}`. Для первого
изменения достаточно не включать черновики в исполняемый список; новый
публичный поток черновиков инструментов сейчас не нужен.

Проверка недописанных аргументов не должна скрывать подтверждённый output_limit.
Сохранять partial и usage из финального ответа также при `stream=False`,
когда дельт не было. Не добавлять финальный текст повторно к показанным дельтам.

### 10.2. Вызовы и результаты инструментов

Сохранить внутренний `ToolCall.id`: он нужен истории, исполнителю и UI. Это
ID Boba, а не требование к наличию одноимённого поля в каждом протоколе.
Пригодный ID поставщика можно сохранить; иначе адаптер назначает его локально.
Не объединять вызовы по имени или аргументам.

Результат ссылается на этот ID. Перед отправкой адаптер проверяет связь с
вызовом: OpenAI получает `tool_call_id`, Ollama — `tool_name`. Не добавлять
второе независимое поле имени в каждый результат только ради Ollama: имя
есть в связанном вызове. Если результат остался без вызова после compaction,
исправлять сборку истории или явно отказывать, а не угадывать имя.

`ToolSpec.parameters` остаётся JSON Schema. Её открытая структура — стандартный
язык описания входа инструмента, а не универсальный metadata-мешок. Проверять
представимость конкретной схемы до инференса. Разрешены преобразования только
с сохранением смысла. Разворачивание `$ref` требует учёта области ссылок и
рекурсии. Для неподдерживаемой схемы вернуть предметную ошибку до запроса.
Не удалять ограничения для получения формально допустимого запроса.

### 10.3. Reasoning и параметры генерации

Сохранить `reasoning: str | None` у истории, чтобы различать отсутствие и
явно сохранённое пустое значение. Не требовать одинаковой побайтовой
сериализации во всех протоколах:

- Решение возвращать reasoning в историю принимает агент по политике модели;
  адаптер не добавляет скрыто новые рассуждения в запрос.
- OpenAI-compatible адаптер сохраняет требуемый моделью `reasoning_content`,
  включая пустую строку, когда она обязательна.
- Для Ollama разрешить опускать пустой thinking, если это допустимо выбранным
  протоколом/моделью. Допустимость подтвердить проверкой на сервере.
- Непустой reasoning не должен теряться. Невозможность вернуть его в историю
  описывается ограничением возможностей, а не скрытым удалением данных.

Заменить `sampling: dict[str, Any]` явной конфигурацией генерации:

1. Небольшая общая часть: лимит выхода, temperature, top_p, stop, где смысл
   сопоставим. Поля опциональны. Для отсутствующего значения определить,
   используется ли настройка модели или default сервера. Неподдерживаемые
   параметры/значения дают явную ошибку.
2. Типизированные настройки адаптера для специфичных возможностей: thinking,
   keep_alive, options Ollama и расширения OpenAI-compatible серверов. Схему
   объявляет адаптер; ядро не импортирует инфраструктуру. Не вводить `extras`.
3. Модель, сообщения, инструменты, формат ответа, адрес, auth и stream задаются
   отдельно. Их нельзя подменять настройками генерации.
4. Преобразование лимита в `max_tokens`, `max_completion_tokens`, `num_predict`
   зависит от модели. Учёт reasoning в лимите документировать явно, не
   предполагать одинаковую семантику любого числового поля.

Настройки агента в БД, снимок истории и runtime-запрос используют одинаковый
типизированный смысл. Настройки загрузки локальной модели отделены от
параметров обращения: новая temperature не создаёт вторую копию весов.

### 10.4. Возможности и структурированный ответ

Объявлять возможности адаптера и модели: tools, images, streaming,
структурированный ответ, выдача/возврат reasoning и ограничения контекста.
Не подменять отсутствие сведений безусловным `supports_tools=True`.
Различать «неизвестно» и «не поддерживается»: неизвестное требует явной
настройки либо проверки перед использованием возможности, без тихого fallback.

Проверять сочетания, а не только флаги: tools + format, images + tools,
streaming + structured output. Диагностика называет конкретную несовместимость.

Разделить описание инструмента и запрос структурированного ответа: заменить
`ToolSpec` в `reply_schema` отдельным типом схемы результата. Для первого
изменения сохранить текущую потребность — JSON-объект; не расширять все
потребители на произвольные корневые JSON-значения.

Адаптер выбирает поддерживаемый механизм: native schema/format либо
принудительную функцию. Служебный вызов ответа не попадает в исполнитель
инструментов. Определить явно допустимость сочетания с обычными tools.
`SchemaReply.ask` принимает только допустимый завершённый результат этого
механизма. Не брать первый произвольный tool call или обрывок JSON при
output_limit/blocked как успешный объект. Проверка по прикладной модели
остаётся явной обязанностью потребителя. Prompt-only имитация structured
output — только отдельно выбранный режим, если он нужен, а не тихое
понижение гарантий.

`EmbeddingModel` оставить отдельным портом. Сохранить document/query, батчи,
проверку порядка/количества/размерности. Не создавать универсальный `invoke`,
скрывающий различия операций, и не требовать от адаптера поддержки chat и
embedding одновременно.

### 10.5. Порядок изменения потребителей и передачи проверки

1. Зафиксировать типы запроса/результата, статусы, reasoning, capabilities и
   преобразования настроек. Названия здесь — рекомендация; отдельный пакет
   для каждого типа не нужен.
2. Одним согласованным изменением обновить порты и текущие HTTP/ONNX реализации
   в затронутой части, проверить влияние на FastEmbed. ONNX также выдаёт
   нормализованный лимит, не сохраняя прежнюю альтернативную семантику.
3. Обновить `boba/agent/asking.py`: классификация финала, partial и usage;
   `turn.py`: повторы, запрет исполнения неполных вызовов, учёт результата;
   `template.py` и `compaction.py`: лимит/фильтр при ответе и пересказе.
   Сохранить cancellation и не допустить повторного исполнения инструментов.
4. Обновить `builder.py`, `profile.py`, `settings.py`, `records.py`: возврат
   reasoning, типизированные параметры, снимки и запись причин завершения.
   Проверить CLI settings/app, AID/ACP отображение и остальных потребителей
   `SchemaReply`/`ChatModel` в инструментах и индексаторах.
5. Не переносить старые данные истории и не вводить совместимые поля-двойники.
   Изменения записываемого формата и последствия чтения старой истории явно
   документировать, без автоматического backfill.
6. Передать отдельной модели сценарии проверки HTTP-адаптеров относительно
   целевого контракта и ожидаемые результаты.

Матрица проверки разделяет обязательные инварианты и протокольные различия.
Обязательны: сохранение непустого содержимого и смысла схем, правильные связи
инструментов, один достоверный финал либо ошибка, partial/usage при лимите,
отмена/освобождение ресурсов и изоляция авторизации. Допустимы при подтверждении:
разный wire-ID, отсутствие пустого thinking и разные поля параметров протокола.
Добавить случаи: лимит без стриминга, лимит посреди аргументов, blocked с
частичным текстом, неизвестный terminal status, structured output при лимите,
результаты инструментов после compaction.

Обновление/запуск тестов проекта и полный прогон реальных серверов остаются
за отдельной моделью.

## 11. Изменения адаптеров и сборки ресурсов

В текущем коде уже отделены `HttpTransport`, `LlmEndpoint`,
преобразование сообщений, декодеры и сборка ответа. Эти границы сохранить.
Поддерживать явно выбранные операции: OpenAI-compatible Chat Completions
и embeddings, нативный Ollama chat; новые операции добавлять по потребности.
Не обещать поддержку всего OpenAI API или всех совместимых серверов.

Конкретные изменения программного кода:

1. В обоих `_payload` убрать произвольный `payload.update(sampling)`.
   Типизированные настройки не должны перезаписывать `model`, `messages`,
   `tools`, `stream` и другие структурные поля. Общие параметры явно
   преобразовывать в формат адаптера; специфичные параметры валидировать
   объявленной им схемой. Сохранять различие отсутствия, `false` и нуля.
2. В Ollama связывать результат инструмента с исходным вызовом через ID Boba
   и передавать `tool_name`, как в официальном протоколе. Не считать
   `tool_call_id` заменой имени. Сохранять порядок и отдельность одинаковых
   вызовов; отсутствие исходного вызова обрабатывать явно.
3. В обоих адаптерах проверять финальное состояние и у обычного ответа:
   сейчас `_check_complete` разрешает отсутствие причины при `streamed=False`.
   По разделу 10 возвращать нормализованный исход, partial и usage;
   неполные аргументы инструмента не исполнять. Обрыв и неизвестный статус
   не превращать в успешный финал. Проверить закрытие вложенных потоков
   при отмене и досрочном прекращении чтения.
4. В OpenAI embeddings дополнить сортировку индексов проверкой точного набора
   `0..N-1`: количество и размерность уже проверяются, но дубли/пропуски
   индексов этим не исключаются.
5. Вынести structured output из `ToolSpec`, выбирать поддерживаемый способ
   явно. Нынешняя принудительная функция OpenAI не должна быть единственным
   способом для всех endpoint. Сохранять схемы tools и формат ответа без
   удаления ограничений; проверять поддержку конкретным сервером/моделью.
6. Сохранить один владеющий слой транспорта/auth/повторов. Не вводить ещё
   один HTTP-клиент и отдельные retries внутри адаптера. Приватный импорт
   `httpx_sse._decoders.SSEDecoder` учесть как зависимость от внутреннего API:
   выбрать поддерживаемую границу декодирования с сохранением обработки
   keepalive и контроля пауз; не заменять полноценный SSE разбором `data:`.

Для динамического реестра отдельно изменить сборку ресурсов:

- Разделить установленный тип адаптера, сохранённого провайдера и исполняемый
  backend. `LlmProviderTypes` может оставаться реестром установленного кода;
  записи пользователей не добавляются в entry points.
- Репозиторий хранит провайдеров/модели, прикладной сервис Boba проверяет
  права и разрешает авторизацию, фабрика создаёт backend из готового
  типизированного описания. HTTP-адаптер не импортирует БД, ACP или AID.
- Заменить кеш `LlmProviders`, основанный на равенстве полных конфигов,
  управлением ресурсами по идентификатору, ревизии провайдера и контексту/
  ревизии авторизации. Права проверять независимо от кеша. Не хранить секрет
  как ключ кеша. Старый ресурс освобождать после окончания текущих обращений;
  ротацию применять к следующим, без накопления клиентов до остановки процесса.
- Общую конфигурацию HTTP-процесса отделить от пользовательского endpoint
  и привязки авторизации. Секреты не включать в каталог и снимки агента.
- AID управляет этими записями только через ACP. Промпт, skills, memory и
  контекст остаются ответственностью агента Boba, а не HTTP-адаптера.

Новые записи провайдеров установленного типа не требуют рестарта. Совершенно
новый протокол требует поставки кода; локальная модель — доступных весов
и ресурсов исполнителя. Хранение в БД не устраняет этих требований.

Первичные ориентиры: [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create),
[Ollama chat](https://docs.ollama.com/api/chat),
[Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling).

## 12. Критерии готовности и передача проверки

Для выполненного этапа передать следующей модели сценарии, ожидаемые исходы
и оставшиеся ограничения. Следующие проверки не считать выполненными без
реального прогона:

- Пустая БД после штатного создания схемы: сервис запускается, уполномоченный
  пользователь управляет реестром без модели; обычный вход не даёт admin.
- Создание и изменение через ACP видны другому клиенту и другому процессу;
  выбранная модель отвечает без рестарта. Потерянный ответ create не плодит записи.
- Чужой пользователь не читает и не изменяет приватные ресурсы; общий агент
  не выдаёт чужие credentials. Ротация/отзыв учитываются при следующем обращении.
- Конфликт ревизии, отключение и удаление используемых ресурсов обрабатываются
  явно. Открытая сессия не переключается молча на другую модель или промпт.
- Возобновление сохраняет выбранную конфигурацию, но перепроверяет действующие
  права. История остаётся доступной после отключения модели.
- Нет утечек секретов в каталог, ошибки, журналы, историю и снимки промптов.
- Неподдерживаемое расширение/адаптер/возможность дают понятный отказ;
  недоступный провайдер не блокирует редактирование реестра.
- Для доработанных адаптеров: reasoning туда и обратно; несколько и
  перемежающиеся tool calls; строгое завершение/лимит/фильтр; 400/401/403/429/5xx;
  отмена и освобождение ресурсов; порядок, число и размерность embeddings.
- Локальные модели: отсутствующие веса, конкурентные обращения, освобождение
  ресурсов, отсутствие блокировки event loop и корректные границы отмены.
- DDL применяется к отдельно указанной схеме без переноса бизнес-данных;
  другие приложения и их схемы не изменяются побочно.

Отчёт агента реализации: выполненные этапы, изменённые контракты и настройки,
статические проверки, сценарии для отдельного прогона, известные ограничения.
Не включать утверждение «тесты прошли», если их не запускали. Не выполнять
деплой и не расширять задачу до переписывания всего auth, MCP или индексаторов.
