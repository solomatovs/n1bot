# Каталог данных: источники, процесс, диаграммы

Что такое каталог, как в нём живут источники метаданных и процесс над ними,
черновики и версии, кто что может, как устроены страница, JSON API, события
и инструменты LLM, где лежит конфиг и как собирается страница. План и
решения — в `catalog-sources-plan.md`, схема хранения по таблицам и полям —
в `catalog-storage.md`.

## 1. Модель

Каталог из двух слоёв. Нижний — **источники метаданных**: снимки структуры
баз в родной форме (Postgres: база → схема → таблицы, представления,
секции, функции, процедуры, последовательности, типы; ClickHouse: база →
таблицы, представления, словари), по версии на каждое обновление. Верхний —
**процесс**: слои хранилища, узлы и потоки между ними. Узел не хранит
структуру объекта, он ссылается на объект источника адресом, а колонки, типы
и определения читаются из той версии источника, к которой процесс привязан.

### Источник и адрес объекта

`Source{id, kind, name, description, manual}` — самостоятельная сущность;
подключения к нему привязываются отдельно. `kind` — вид типа соединения из
реестра `boba.connections` («postgres», «clickhouse»): своего перечня видов
у каталога нет. Снимок каждого вида живёт в пакете-владельце драйвера
(`boba.db.postgres.snapshot`, `boba.db.clickhouse.snapshot`) и
регистрируется entry point'ом группы `boba.catalog` с именем, равным kind
соединения; реестр `SourceKinds.discover()` собирает их на старте, а
`GET /source-kinds` отдаёт странице те виды, у которых снимок установлен.
Новый вид источника — это новый пакет драйвера со снимком и инструментом
снятия, домен каталога при этом не меняется.
Ручной источник (`manual = true`) заполняется операциями над объектами
(`add_object`, `set_object`, `remove_object` с коротким набором полей: имя,
вид, комментарий, колонки с типом и nullable) и нужен для планируемых
объектов, которых в базе ещё нет.

### Синхронизация

Синхронизируемый источник получает версии инструментом снятия своего вида:
класс снимка объявляет его в `SYNC_TOOL` (`PgSnapshot` —
`pg_schema_snapshot`), у вида без инструмента синхронизация отвечает отказом.
Запуск идёт от имени пользователя с `edit_roles` через одно из подключений,
привязанных к источнику и видимых этому пользователю: инструмент выполняется
как любой другой — в песочнице, под секретами пользователя (`SyncCaller`:
субъект, инициатор, `credential` входа), но вне чата, в области
`job/<sync_id>`.

Инструмент читает системные каталоги порциями (`batch_size`, `pause_ms`
между заходами) и шлёт в выходной порт кадры: `SyncPlan` (что нашёл, сколько
объектов, версия сервера), `SyncBatch` с телом-списком записей одной части
снимка, `SyncDone` со счётчиками. Хост (`SyncRunner` в `boba-catalog-service`)
принимает кадры через `FrameTap`, кладёт каждую порцию в staging-таблицу
`sync_<id>` и двигает `objects_done`; по завершении инструмента собирает
снимок из порций (`SnapshotAssembler` сверяет счётчики с планом и
инварианты), пишет версию, закрывает запись `Sync` итогом и убирает staging
одной транзакцией. Снимок либо целиком становится версией, либо не
появляется вовсе: отказ инструмента, битый кадр, расхождение счётчиков или
отмена закрывают синхронизацию как `failed` / `cancelled` с причиной в
`error`, staging сносится, версии нет.

У источника не бывает двух синхронизаций сразу: вторая отвечает `409`.
Отмена (`DELETE /syncs/{id}`) снимает инструмент через `RunCancellation` и
ждёт закрытия записи; запись синхронизации другого инстанса закрывается
`cancelled` без остановки инструмента — задача живёт в том процессе, который
её запустил.

`ObjectRef{source_id, kind, path}` — адрес объекта внутри версии источника.
`kind` — родной вид: `relation`, `routine`, `sequence`, `type` у Postgres,
`table`, `dictionary` у ClickHouse; `path` — ступени адреса, у рутины с
сигнатурой последней ступенью:

```json
{"source_id": "…", "kind": "relation", "path": ["prod", "public", "orders"]}
{"source_id": "…", "kind": "routine",  "path": ["prod", "etl", "load_orders", "date"]}
```

В подписях адрес печатается через `/`: `prod/public/orders`.

### Процесс

| Сущность | Поля | Смысл |
|---|---|---|
| `Layer` | `name`, `position`, `description` | слой хранилища: raw, stg, dm; дорожки идут по `position` |
| `Node` | `layer_id`, `ref: ObjectRef`, `alias`, `note` | объект источника, поставленный в слой; один объект стоит не больше чем в одном слое; подпись — `alias` либо последняя ступень адреса |
| `LoadKind` | `name`, `description`, `fields[]` | вид загрузки: full, hashkey, period; `fields` описывают, что заполняется у потока |
| `Flow` | `from_node_id`, `to_node_id`, `load{kind_id, values}`, `description` | поток из узла в узел с правилом загрузки |

Поле вида: `LoadField{name, type, side, required, description}`. Тип задаёт
форму значения у потока, сторона — с какого конца потока берутся колонки:

| Тип поля | `side` | Значение у потока | Пример |
|---|---|---|---|
| `text` | — | строка | `note = "nightly"` |
| `int` | — | число | `batch = 7` |
| `bool` | — | флаг | `full_refresh = true` |
| `column` | `source`, `target`, `any` | имя колонки объекта той стороны | `key_column = "id"` |
| `columns` | `source`, `target`, `any` | список имён колонок | `hash_columns = ["id", "updated_at"]` |
| `routine` | — | адрес функции или процедуры — реализация загрузки | `implemented_by = {ref рутины}` |

Колонки хранятся по имени, а не по id: они принадлежат снимку источника, не
процессу. Существование объекта и колонки проверяется по привязанной версии
источника при применении операции.

Снимок процесса (`CatalogSnapshot`) проверяет инварианты целиком: имена
слоёв и видов уникальны, адрес узла уникален, поток ссылается на
существующие узлы и вид, значения полей соответствуют типам, обязательные
поля заполнены. Проверка по источникам (`check_against`) идёт по резолверу
из привязанных версий: объект узла есть, колонки из значений есть у объекта
нужной стороны, рутина найдена.

Правки — это операции, тринадцать: `add_layer`, `set_layer`,
`remove_layer`, `add_node`, `set_node` (слой, alias, заметка),
`retarget_node` (тот же узел на другой адрес, например с ручного источника
на реальный; потоки остаются), `remove_node`, `add_load_kind`,
`set_load_kind`, `remove_load_kind`, `add_flow`, `set_flow`, `remove_flow`.
`remove_node` отказывает, пока на узел ссылается поток; `remove_layer` —
пока в слое есть узлы; `remove_load_kind` — пока есть потоки этого вида.
Инварианты проверяются после каждой операции. Расхождения с источниками
проверяются по разнице: операция отвергается, только если добавляет новое
расхождение, поэтому уже устаревший процесс можно чинить по одной операции
(снять поток, перенацелить узел).

Список операций в JSON:

```json
[
  {"op": "add_layer", "layer": {"id": "…", "name": "raw", "position": 0, "description": ""}},
  {"op": "add_node", "node": {"id": "…", "layer_id": "…", "alias": null, "note": "",
                              "ref": {"source_id": "…", "kind": "relation", "path": ["prod", "public", "orders"]}}},
  {"op": "add_load_kind", "load_kind": {"id": "…", "name": "hashkey", "description": "",
      "fields": [{"name": "hash_columns", "type": "columns", "side": "source", "required": true, "description": ""}]}},
  {"op": "add_flow", "flow": {"id": "…", "from_node_id": "…", "to_node_id": "…", "description": "",
                              "load": {"kind_id": "…", "values": {"hash_columns": ["id"]}}}},
  {"op": "retarget_node", "id": "…", "ref": {"source_id": "…", "kind": "relation", "path": ["prod", "public", "orders_v2"]}}
]
```

### Привязки версий и устаревание

Версия процесса и черновик помнят `pins: {source_id: version}` — над
какими версиями источников они проверены. Черновик при создании привязывается
к последним версиям всех источников. Когда у источника появляется новая
версия, сервис считает устаревание (`Staleness`) для опубликованного процесса
и для черновика: у узла — `object_removed`, `object_changed` (с деталями,
что изменилось), у потока — `column_removed`, `column_changed`,
`routine_removed`, `routine_changed` по колонкам и рутинам из значений полей.
Устаревание показывается, а не чинится: «raise pins» у черновика поднимает
привязки до последних версий и перечисляет, что после этого перестало
сходиться; дальше пользователь снимает поток или перенацеливает узел.

`ProcessContext{pins, columns: {node_id: [NodeColumn{name, type, nullable,
key}]}, stale}` — всё, что странице нужно от источников одним ответом.

## 2. Черновики, версии, публикация

Опубликованный процесс живёт версиями `v1, v2, …`. Версия — это применённый
к предыдущей список операций и привязки версий источников. Черновик — ветка
операций над базовой версией: он создаётся над текущей версией и накапливает
порции операций. Порция принимается только с ожидаемым номером
`expected_seq`: если кто-то успел положить порцию раньше, сервер отвечает
`409` с текущим `current_seq`, и клиент перечитывает черновик и повторяет.
Так человек на странице и LLM в чате правят один черновик, не затирая друг
друга: порции только добавляются.

Публикация в одной транзакции применяет операции черновика к таблицам,
пишет новую версию с привязками черновика и закрывает черновик. Если за
время работы над черновиком каталог ушёл вперёд (опубликована другая
версия), публикация отвечает `409` с `current_version`. Тогда черновик
перебазируется: его операции проигрываются поверх новой версии. Операция,
которая больше не применима (например, `set_node` узла, который уже
удалили), попадает в список `issues` с номером порции и индексом; по просьбе
пользователя такие операции вычёркиваются (`drop_conflicts`), и черновик
встаёт над новой версией.

Статусы черновика: `open` → `published` или `discarded`. Закрытый черновик
на странице показывается только для чтения.

Черновики ручного источника живут отдельно (`SourceDraft`) с теми же
правилами порций и публикации; публикация создаёт новую версию источника.

## 3. Диаграммы, раскладка, шаринг

Диаграмма (`View`) — сохранённый срез опубликованного процесса: имя и
фильтр. Фильтр — список слоёв (`layer_ids`, слои целиком) плюс список
отдельных узлов (`node_ids`). Пустой фильтр значит весь процесс. Срез по
фильтру считает домен: узлы из фильтра, их слои, потоки строго между ними и
только задействованные виды загрузки. Диаграммы — не вход на страницу, а
срез для показа и шаринга.

Раскладка (`Layout`) — сохранённые позиции узлов диаграммы. Узел без
позиции раскладывает ELK по замеренным размерам карточек. Владелец
перетаскивает узлы, раскладка пишется отложенно; «прибрать» перекладывает
ELK заново и тоже сохраняет.

Шаринг (`Share`) открывает диаграмму на просмотр роли по имени или
пользователю по id. Шаринг даёт только просмотр: вместе со срезом тому,
кому расшарили, доступны контекст среза (колонки, устаревание) и родные
карточки объектов узлов среза; правки и черновики требуют роли из
`edit_roles`.

## 4. Права

Секция `[catalog]` задаёт две группы ролей: `view_roles` читают весь
каталог, `edit_roles` правят его. Владелец диаграммы — тот, кто её создал.

| Действие | Роль из `edit_roles` | Роль из `view_roles` | Никакой роли, диаграмма расшарена |
|---|---|---|---|
| снимок, версии, контекст, устаревание, список черновиков | да | да | нет (`403`) |
| источники, версии, деревья, карточки, diff | да | да | нет |
| создать источник, привязать подключение, записать версию, черновики источника | да | нет | нет |
| создать черновик, порции, публикация, rebase, поднять привязки | да | нет | нет |
| создать диаграмму | да | нет | нет |
| открыть диаграмму (`state`, `context`, `nodes/{id}/object`) | да | да | да, только срез |
| править диаграмму, раскладку, шаринг, удалить | только владелец | нет | нет |
| события `GET /events` | да | да | нет |

`GET /access` отдаёт `user_id`, `login`, `can_view`, `can_edit`: страница по
этому решает, какие формы и кнопки показывать.

## 5. Страница

Сетка, виджеты `src/ui` и правила расширения фронта описаны в
`catalog-frontend-plan.md`.

Адреса под префиксом chainlit:

| Адрес | Что показывает |
|---|---|
| `{prefix}/catalog/` | сам процесс: опубликованная версия; без права читать каталог — список расшаренных диаграмм |
| `{prefix}/catalog/drafts/{draft_id}` | черновик процесса с правками |
| `{prefix}/catalog/views/{view_id}` | диаграмма: срез процесса с сохранённой раскладкой |
| `{prefix}/catalog/sources` | источники метаданных: список, новый источник |
| `{prefix}/catalog/sources/{source_id}` | дерево версии источника, карточки объектов, diff версий, подключения и синхронизация |
| `{prefix}/catalog/sources/{source_id}/drafts/{draft_id}` | редактор объектов ручного источника |

Вход — процесс без списков. Состояние страницы живёт в адресе:
`?active=<node_id>` — выбранный узел, `object=<адрес>` — выбранный объект
дерева источника, `pane=sources` — вкладка источников слева,
`mode=ALL_FIELDS|KEY_ONLY|TABLE_NAME` — режим карточек, `hidden=<id,id>` —
скрытые узлы, `diff=0` — выключенная подсветка изменений черновика. Ссылку
можно отправить коллеге, он увидит то же самое.

Три панели. Слева две вкладки: **process** — узлы по слоям (поиск, глаз
скрывает узел на холсте; на черновике — карандаш и корзина у слоя, «layer»
внизу) и **sources** — источники с версией привязки, каждый раскрывается в
дерево той версии, к которой привязан процесс; объект выбирается в панель
справа, на черновике тащится на холст. Посередине холст: дорожки слоёв слева
направо (на черновике пустой слой получает пустую дорожку, чтобы в неё можно
было бросить объект), карточки узлов с родным видом объекта и колонками из
привязанной версии, рёбра потоков с ярлыком вида загрузки, тулбар (зум,
вписать, прибрать, режим карточек). Справа панель узла: слой и подпись,
адрес и привязанная версия, причины устаревания, колонки, входящие и
исходящие потоки со значениями полей, ниже — родная карточка объекта из
источника. Панель объекта дерева: карточка и действия процесса — «add to
layer» с выбором слоя, «open node», если объект уже в процессе, «retarget …
here» в режиме перенацеливания. Клик по узлу выбирает его и подсвечивает
соседей, наведение подсвечивает без выбора. Узлы и рёбра, разошедшиеся с
источниками, помечены пунктиром и значком; в шапке чип «N stale». На узком
экране левая панель закрыта по умолчанию.

Шапка: версия, «diff» на черновике, «edit» на опубликованной странице
(диалог: свои и чужие открытые черновики, форма нового), «raise pins ·
N stale», «publish», «discard», «update to vN» на черновике, карандаш,
«share», корзина у владельца диаграммы, «load kinds» (список видов с
полями; на черновике — создание, правка и удаление вида без потоков),
«diagrams» (список доступных диаграмм, «save slice» сохраняет текущий срез
новой диаграммой). Пустой процесс встречает кнопками «add a source»,
«manual source» и «add a layer» на черновике.

На черновике (`data-editable="true"`) правки:

| Где | Что | Операция |
|---|---|---|
| список, низ | «layer» | `add_layer` через подсказку имени |
| заголовок слоя | карандаш, корзина (только у пустого слоя) | `set_layer`, `remove_layer` |
| панель объекта дерева | слой + «add to layer»; перетаскивание объекта на дорожку слоя; мимо дорожек — диалог «which layer?» | `add_node` |
| панель узла, шапка | карандаш, прицел, корзина | форма узла → `set_node`; перенацеливание → `retarget_node`; `remove_flow…` + `remove_node` |
| панель узла, исходящие | «flow» | форма потока с выбором приёмника → `add_flow` |
| панель узла, поток | карандаш; ребро на холсте | форма потока → `set_flow` или `remove_flow` |
| холст | соединение handle'ов двух узлов | форма потока → `add_flow` |
| «load kinds» | «load kind», карандаш, корзина | `add_load_kind`, `set_load_kind`, `remove_load_kind` |
| шапка | «diff» | подсветка added/modified/removed относительно базовой версии |
| шапка | «raise pins», «publish», «discard», «update to vN» | поднятие привязок, публикация, отмена, перебазирование |

Форма потока строится по полям вида: число, флаг, текст, колонки по именам
с того конца, что задан стороной поля, рутина — из узлов-рутин процесса.
Каждое действие уходит порцией в `POST drafts/{id}/ops`. Страница держит
очередь порций строго по одной; на `409` перечитывает черновик и повторяет
до трёх раз; после каждой порции перечитывает контекст (колонки новых
узлов, устаревание). Отказ сервера (нарушен инвариант, объект или колонка
не найдены в источнике) показывается тостом с номером операции и причиной.

Публикация при устаревшем черновике открывает диалог «the catalog has moved
on»: «update the draft» перебазирует; если операции не применимы, диалог
перечисляет их (`portion N · operation #i: причина`) и предлагает «drop the
conflicts and update» или «keep the draft as is».

Атрибуты для тестов и отладки: `data-testid="catalog-page"` с
`data-source=published|view|draft`, `data-editable`, `data-owned`,
`data-seq` (номер последней принятой порции), `data-layout-saves`,
`data-stale` (число устаревших узлов и потоков); холст `data-testid="canvas"`
с `data-ready` и счётчиком `data-layouts`; узлы `data-testid="catalog-node"`
с `data-node` (адрес объекта), `data-label`, `data-kind`, `data-status`,
`data-stale`, `data-active`, `data-highlighted`; дорожки
`data-testid="layer-lane"` с `data-layer`; левая панель `data-tab`; ветка
источника `data-testid="source-branch"` с `data-source` и `data-open`; узлы
дерева `data-testid="tree-node"` с `data-path`; панель узла
`data-testid="detail-panel"` с `data-node`; панель объекта
`data-testid="object-panel"` с `data-object` и `data-in-process`; диалоги
`data-dialog=<mark>`; чипы шапки `data-testid="stale-chip"`.

## 7. Живые события

После каждой правки сервис публикует `CatalogChanged{draft_id | version |
view_id | source_id | sync_id, action}` в шину сообщений в область пользователя.
`GET /events` отдаёт их server-sent events: кадр `data: {json}` на событие
и `: ping` раз в 15 секунд. Страница подписана через `EventSource`:

- событие по своему черновику — дотянуть новые порции (чужие правки, в том
  числе от LLM, появляются без перезагрузки);
- новая версия процесса или источника — перечитать страницу: контекст,
  устаревание, кнопка «update to vN» на черновике;
- правка диаграммы — перечитать диаграмму;
- синхронизация (`sync_id`: `created` на старте, `updated` на план, каждую
  порцию и итог) — страница источника перечитывает запись `Sync` и ведёт
  полосу прогресса; итог приходит ещё и событием по `source_id`;
- на опубликованной странице — новый или закрытый черновик обновляет
  счётчик у «edit».

Ответ загрузки, совпадающий с уже показанным (эхо своего же события), граф не
перекладывает.

## 8. Инструменты LLM

Плагин `catalog` chainlit (секция `[tool.catalog]`, файл
`conf/plugins/catalog.toml`) даёт модели шесть инструментов. Субъект вызова —
пользователь чата, права те же, что на странице.

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `catalog_read` | `nodes` — подписи или адреса узлов через запятую, пусто — весь процесс | снимок или срез: узлы с колонками из привязанной версии, соседи по потокам, виды загрузки, `pins`, `unknown_nodes` |
| `catalog_draft` | `name` | новый черновик над текущей версией; в ответе id |
| `catalog_propose` | `draft_id`, `operations` — JSON-список операций | порция в черновик; `expected_seq` инструмент перечитывает сам, до трёх попыток; отказ называет индекс операции и причину |
| `catalog_diff` | `draft_id` | изменения черновика относительно базовой версии словами: `added node 'prod/public/orders'` |
| `catalog_open` | `kind` = `draft` или `view`, `entity_id` | элемент-ссылка `CatalogLink` в чат на страницу |
| `catalog_sync` | `source` — имя или id, `connection` — id привязанного подключения (пусто — единственное привязанное), `schemas` через запятую | запускает синхронизацию под пользователем чата и ждёт итога; ответ — запись `Sync` с номером версии либо отказ с причиной |

Сценарий «LLM правит, страница показывает»: пользователь открыл черновик на
странице, в чате попросил модель поставить таблицу в слой; `catalog_propose`
положил порцию с `add_node`, событие дошло до страницы, узел появился с
пометкой `added`.

Конфиг плагина:

```toml
enable = true
tools  = ["catalog_read", "catalog_draft", "catalog_propose", "catalog_diff", "catalog_open", "catalog_sync"]
```

Инструмент снятия `pg_schema_snapshot` включается в `conf/plugins/pg.toml`
списком `tools` плагина postgres: без него синхронизация отвечает, что
инструмент недоступен пользователю.

Элемент `CatalogLink.jsx` лежит в `assets/public/elements/` пакета и в
`app_root/public/elements/` развёртывания.

## 9. Конфиг и развёртывание

Секция `[catalog]` в `config.toml` chainlit:

```toml
[catalog]
    enable     = true
    connection = "${postgres}"
    db_schema  = "catalog"
    view_roles = ["read"]
    edit_roles = ["wrt"]
    dist       = "${env.app_root}/public/catalog"
```

| Ключ | Смысл |
|---|---|
| `enable` | создавать таблицы схемы при старте; `false` — API отвечает `503` |
| `connection` | Postgres-профиль ссылкой |
| `db_schema` | схема таблиц каталога: процесс (`versions`, `drafts`, `draft_ops`, `layers`, `nodes`, `load_kinds`, `flows`, `views`, `view_layout`, `view_shares`) и источники (`sources`, `source_connections`, `source_versions`, `syncs`, `source_drafts`, `source_draft_ops`, таблицы снимков `pg_*`, `ch_*`); полный перечень в `catalog-storage.md` |
| `view_roles`, `edit_roles` | роли чтения и правок |
| `dist` | каталог сборки страницы (`index.html`, `assets/`); страница всегда раздаётся из сборки |

Страница `web/catalog` (vite, React 18, @xyflow/react, elkjs, react-router,
zod, типы из OpenAPI) собирается node'ом образа:

```sh
make -C build/chainlit web-catalog        # npm ci, generate, check, build → assets/catalog
make -C build/chainlit catalog-openapi    # обновить web/catalog/openapi.json из приложения
cp -a packages/agents/boba-chainlit/assets/catalog compose/chainlit/app_root/public/catalog
```

В образ страницу собирает стадия `catalog-build` Dockerfile. Отдельного
dev-сервера у страницы нет: node живёт только в образе, правки фронта
проверяются пересборкой и копией dist; пока dist не скопирован заново,
dev-стенд показывает старую сборку.

## 10. Пакеты и слои

| Пакет | Слой | Что внутри |
|---|---|---|
| `boba-catalog` | core | база снимка источника (части, семейства, реестр видов), процесс над ссылками, инварианты, операции, diff, устаревание, кадры синхронизации; без I/O и без знания конкретных видов |
| `boba-db-postgres`, `boba-db-clickhouse` | infra | тип соединения и снимок источника своего вида (`snapshot.py`, образец `snapshot_sample.py`), entry points `boba.connections` и `boba.catalog` |
| `boba-tool-postgres` | tools | `pg_schema_snapshot` — снятие структуры базы кадрами синхронизации |
| `boba-catalog-service` | services | `CatalogStore` на Postgres, `CatalogService` с правами и событиями, записи API |
| `boba-messaging` | core | `CatalogChanged` |
| `boba-chainlit` | agents | `catalog/api.py` (маршруты, SSE), `catalog/tools.py` (инструменты), `catalog/schema.py` (OpenAPI), страница `web/catalog` |
| `boba-stand` | testing | учётки `admin/ADM`, `dev/DEV`, `guest/GST`, сброс схемы каталога |

Домен не знает про транспорт и базу, сервис не знает про chainlit, chainlit
зовёт сервис через провайдеры хоста.
