# pg-indexer-vector: векторный индекс объектов PostgreSQL

Независимый индексатор поверх схемы `ix`. Читает только `ix.node`, `ix.tree` и surface-таблицы
`ix.pg_*`, пишет только в `ix.pg_emb_e5_1024`. Со скрапером не связан ни вызовами, ни внешними
ключами: строки node, которых больше нет, убирает сам. Модель считает Python между очередью и
записью; SQL знает только текст и вектор.

## Установка

`schema/00_pg_emb_e5_1024.sql`: таблица и частичные HNSW-индексы по парам surface и aspect.
Предусловие: ядро `ix` из `docs/knowledge-schema.sql`, `docs/pg-scraper/schema/00_surface.sql`
(значения `surface_e` в предикатах индексов), словарь аспектов из схемы любого индексатора.

## Воркер: worker.py

Готовый цикл на Python поверх провайдера проекта `boba.llm.embedding` (fastembed, ONNX на
CPU, модель `intfloat/multilingual-e5-large` из каталога `models/fastembed`, префикс
`passage:` подставляет fastembed). Запуск из venv проекта:

```
.venv/bin/python docs/pg-indexer-vector/worker.py \
    --dsn "host=... dbname=... user=... password=..." \
    --cache-dir compose/chainlit/models/fastembed \
    --batch 64
```

Ключи: `--model` (по умолчанию `intfloat/multilingual-e5-large`), `--dim` (1024), `--batch`
(размер пачки очереди), `--rounds` (0 значит до пустой очереди), `--no-prune`. Воркер читает
SQL-файлы пакета как есть, `$N` переводит в параметры psycopg, держит одну сессию с
`lock_timeout` и `statement_timeout`, после каждой пачки и при любой ошибке снимает захваты
очереди, в конце делает prune. На стенде 435 текстов e5-large на CPU заняли 25 секунд.

## Цикл воркера

Одна сессия к `ix`, `set lock_timeout`, `set statement_timeout`, autocommit:

1. `10_queue.sql` с параметром `$1` (размер пачки): строки `(node_id, surface, aspect, content)`,
   у которых эмбеддинга нет или `content` в таблице отличается от вычисленного. Каждая
   выданная строка захвачена сессионным advisory-замком по `node_id`, строки, занятые другим
   воркером, пропущены. Пустой результат значит, что очередь пуста.
2. `embed_documents` провайдера кодирует `content` пачкой, на каждую строку выполняется
   `20_write.sql` с параметрами `node_id`, `surface`, `aspect`, `content`, `emb` (вектор
   строкой вида `[0.1, ...]`). Если за время расчёта текст изменился, upsert всё равно
   запишет старый content, и следующая очередь выдаст строку снова.
3. `90_unlock.sql` после записи пачки и при любой ошибке (finally). Обрыв сессии снимает
   захваты сам.
4. `30_prune.sql` в конце цикла: удалить строки, для которых аспекта больше нет, пропуская
   занятые. Порядок «сначала добавить, удалять последним» тот же, что у fts и trgm;
   поисковые запросы join'ят `ix.node`, сироты до ближайшего prune безвредны.

Несколько воркеров работают одновременно: захваты делят очередь без пересечений, запись
идёт `on conflict do update ... where content is distinct from`, prune никого не ждёт.
Запрос при поиске кодируется `embed_query` того же провайдера (префикс `query:`).

## Аспекты

| aspect | кто пишет |
|---|---|
| description | все surface |
| comment | у кого comment не пуст |
| columns | pg_table, pg_view |

Текст тот же, что у `pg-indexer-fts` (заголовок объекта, комментарий, для таблиц колонки с
типами), поэтому сниппет полнотекста и вектор описывают одно и то же. Аспект summary появится
с describer'ом.

## Важно: дублирование определения аспектов

CTE `obj` и `aspect` в `10_queue.sql` и `30_prune.sql` этого пакета и в соседних пакетах
индексаторов это одна и та же логика, скопированная намеренно. Общих объектов в базе
(представлений, функций) по решению нет. При переносе на Python эти CTE должны стать одной
общей функцией, которая генерирует текст аспектов для всех индексаторов; до тех пор при
правке определения аспекта править все копии.

## Требования к схеме

Ядро `ix` (`ix.node`, `ix.tree`) и surface-таблицы `ix.pg_*` скрапера. Свою таблицу пакет
создаёт сам в `schema/`: без внешнего ключа на `ix.node`, со ссылками на словари `ix.surface`
и `ix.pg_aspect`. Расширение `vector` (halfvec, hnsw) должно быть установлено.
