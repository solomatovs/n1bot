# Границы общих компонентов и расширяемость

Состояние: 2026-11-04. Задача — убрать из общего механизма знание его
конкретных потребителей и подключаемых реализаций. Добавление приложения,
бэкенда или ресурса не должно требовать изменения общего компонента.

Проведён статический проход по 588 Python-файлам в `packages/**/src`, включая
поддержку стендов, без изменения и запуска тестов. Проверены импорты,
перечисления, конфигурационные unions, фабрики, реестры и места использования
найденных списков. Дополнительно просмотрены совпадения имён приложений в
JS/TS/shell и составление целей Make: найденные связи UI находятся в самом
AID, а выбор поставки — в сборке, не в общих механизмах.
Поиск импортов верхних слоёв сам по себе проблемы не
показывает: многие связи зашиты в строках, enum и wire-моделях.
Это карта подтверждённых мест для изменений, а не утверждение, что после
первых исправлений вся архитектура уже стала расширяемой.

## Правило проектирования

Общий компонент получает данные и реализации через конструктор или явную
сборку приложения. Он держит механизм и контракт ошибок. Владелец реализации
держит её идентификатор, конфиг, ресурсы и поведение. Приложение выбирает,
какие реализации подключить. Реестр, наполненный переданными фабриками или
entry points, допустим; закрытый список потребителей внутри механизма — нет.

Не заменять enum на `str`, оставляя рядом `if name == "aid"`: это сохраняет
ту же зависимость. При переносе проверок сохранять их смысл и отказ при
неизвестном/недопустимом входе. Статусы протокола, SQL-колонки конкретного
репозитория, сигналы ОС и допустимые значения одного формата не являются
каталогом потребителей; их не надо механически превращать в плагины.

## Уже изменено в целевом коде

### 1. Имя приложения в runtime

Места:

- `packages/services/boba-runtime/src/boba/runtime/config.py`: `AppName`,
  `ClusterConfig.instance_of`;
- `packages/services/boba-runtime/src/boba/runtime/providers.py`:
  `app_name`, `message_bus`, `live_locks`;
- `packages/services/boba-runtime/src/boba/runtime/bus.py`: `PgMessageBus`;
- `packages/apps/boba-aid/src/boba/aid/infra/bootstrap.py`: сборка контейнера.

`AppName` больше не enum со значениями AID/MCP. Это неизменяемое значение,
проверяющее только формат имени. AID передаёт `AppName("aid")` из своего
корня сборки. Другой сервис передаёт своё имя без изменения runtime.
Поля БД и существующее имя инстанса AID сохраняют прежние значения.

Из `PgMessageBus` удалён аргумент `app`: он только сохранялся в поле и нигде
не использовался. Регистрация имени приложения остаётся в `PgLiveLocks`,
где оно действительно записывается в `live_instances`.

### 2. Путь к ресурсам AID в общем поиске программы

Места:

- `packages/services/boba-runtime/src/boba/runtime/config.py`:
  `SourceTree`, `SourceProgram`, `ProgramRoots`;
- `packages/apps/boba-aid/src/boba/aid/infra/entry.py`: `AppEntry`.

Удалён `SourceTree.AID_ASSETS`. `ProgramRoots` получает `source_paths` от
потребителя и передаёт их `SourceProgram`; AID сам задаёт свой путь `share`.
Общий механизм знает раскладку программы, но не пакет `boba-aid`.
Для собранной программы ресурсы по-прежнему берутся из её каталога.

## Подтверждённые места для следующего изменения

### 3. Два закрытых списка СУБД в общем toolkit — высокий приоритет

Места:

- `packages/core/boba-toolkit/src/boba/toolkit/transfer.py`: `Engine`,
  `SchemaHead.source_engine`;
- `packages/core/boba-toolkit/src/boba/toolkit/contract.py`: второй `Engine`;
- `packages/infra/db/boba-db-postgres/src/boba/db/postgres/transfer.py` и
  `packages/infra/db/boba-db-clickhouse/src/boba/db/clickhouse/transfer.py`:
  загрузка entry points с последующим `Engine(entry.name)`;
- `arrow_stream.py` в пакетах PostgreSQL, ClickHouse, Oracle;
- пакеты `packages/infra/stream/boba-stream-*/` с проверками `is Engine.*`.

Новая реализация источника может объявить entry point, но закрытый enum всё
равно её отвергнет. Кроме того, два enum уже различаются: `greenplum` есть
только в одном.

Решение: один открытый тип идентификатора источника в общем контракте;
идентификатор и обработчик объявляет пакет драйвера/адаптера. Реестр пар
источник–приёмник строится из переданных или обнаруженных реализаций.
Решение о совместимости формата принимает адаптер, а не общий toolkit.
Существующие строковые значения wire сохранить. Замены `is` обязательны:
сравнение идентичности enum неприменимо к открытому идентификатору.

Ошибки: неподдержанная пара или формат — `TransferError` до начала записи;
неизвестное имя не должно выбирать запасной драйвер. Отдельно проверить
точные типы одного движка и перенос через нейтральный Arrow-контракт.

### 4. Identity знает имена бэкендов входа — высокий приоритет

Места:

- `packages/core/boba-identity/src/boba/identity/session.py`: `SignInProvider`;
- `packages/core/boba-identity/src/boba/identity/signin.py`:
  `SignInMetadata.is_kerberos`, `ticket`, `credential`;
- `packages/services/boba-auth/src/boba/auth/signin.py`: `SignInDetails`,
  `SignedInFactory` и провайдеры;
- `packages/services/boba-auth/src/boba/auth/service.py`:
  ветвления по `is_kerberos` при выдаче/обновлении сессии;
- `packages/services/boba-runtime/src/boba/runtime/signin.py`:
  `SignInAssembly`; `boba.auth.config.AuthConfig` и
  `ProcessConfig.kerberos_entries/proxy_entries`.

Домен содержит закрытый список Local/LDAP/Kerberos/Proxy и определяет наличие
делегированных credentials по имени провайдера. Добавление иного бэкенда,
способного выдать те же credentials, требует изменения identity. Фабрика
runtime повторяет список конкретных конфигов в `isinstance`.

Решение: идентификатор провайдера — диагностические данные; подтверждённые
credentials и возможности обновления — отдельный результат/порт провайдера.
Сборщик принимает набор фабрик с моделями конфигурации. Реализации проверяют
свои входы, общий сервис получает подтверждённую личность и вызывает порты,
не выбирая алгоритм по имени бэкенда.

Это изменение нельзя свести к удалению `is_kerberos`: оно влияет на выдачу,
обновление и отсутствие SSO-билета. Сохранить шифрование билета в JWT,
отказ delegated connection при отсутствии билета, локальную проверку
токена без DB-чтений и строгое ограничение способами из конфига. Внешний
JWT/OIDC не добавлять. Ошибки сохраняют контракт AuthenticationError /
AuthorizationError / ExternalServiceError / InternalServiceError.

### 5. Модель grants знает ресурс AID — высокий приоритет

Места:

- `packages/core/boba-connections/src/boba/connections/stored.py`:
  `GrantKind`, `GrantTarget._target_only`;
- `packages/services/boba-connection-broker/src/boba/connection_broker/grants.py`:
  `GrantedIds.params`;
- `packages/services/boba-connection-broker/src/boba/connection_broker/store.py`;
- `packages/apps/boba-aid/src/boba/aid/mcp_servers/store.py`.

`GrantKind` смешивает виды субъектов (`users`, `roles`) с видами ресурсов
(`connections`, `mcp_servers`). Валидатор субъектов отбрасывает перечисленные
ресурсы. Каждый новый ресурс требует правки общего enum и этой проверки.
Знание о таблице AID оказывается в ядре connections.

Решение: отделить субъект гранта от открытого идентификатора ресурса.
Репозиторий ресурса передаёт свой идентификатор общему запросу grants;
субъекты проверяются собственным контрактом, без перечня всех ресурсов.
SQL-имена и проекции таблиц connections держит его репозиторий, mcp_servers —
репозиторий AID. Проверки ссылочной целостности в SQL MCP остаются у MCP:
это владелец своей схемы, а не общий реестр ресурсов всех приложений.
Не создавать новый маленький пакет на каждую разновидность гранта.

Ошибки хранилищ сохраняются у их публичных границ; неизвестный ресурс не
даёт доступ. Значение `src_kind` передавать параметром SQL, не интерполяцией.

### 6. Общая шина содержит каталог прикладных событий — высокий приоритет

Места:

- `packages/core/boba-messaging/src/boba/messaging/messages.py`:
  `MessageKind`, `_HOLDER_ONLY`, `AnyMessage`, `AnyCommand`;
- `packages/core/boba-messaging/src/boba/messaging/bus.py`: модели конвертов
  и порты publish/command;
- `packages/services/boba-runtime/src/boba/runtime/bus.py`: TypeAdapter
  закрытого union, обход MessageKind, проверка requires_lock;
- `packages/core/boba-messaging/src/boba/messaging/memory.py`: реализация
  шины в памяти — проверить вместе с PostgreSQL-реализацией.

Новый домен должен дописывать в общий механизм свои события. Шина знает
изменение MCP-серверов, feedback, черновики workflow и состояние чата.

Решение: механизм доставки и конверт отделить от каталога событий домена.
Кодек/реестр событий и правила публикации передаёт корень приложения.
Связанные события держать в пакете доменных контрактов, не по пакету на
каждое событие. Право публиковать событие под блокировкой задаёт доверенная
регистрация типа; отправитель не может отключить проверку флагом в JSON.

Ошибки разбора/доставки остаются `MessageBusError` на границе реализации;
ошибки блокировок сохраняют текущий контракт. Обязательно проверить replay,
очередность, payload references, межпроцессную доставку и неизвестные виды
событий. Простое расширение union до `Any` неприемлемо.

### 7. Runtime одновременно механизм и каталог инфраструктуры

Места:

- `packages/services/boba-runtime/src/boba/runtime/config.py`:
  `MessagingConfig`, `ProcessConfig`;
- `packages/services/boba-runtime/src/boba/runtime/providers.py`:
  повторяющийся выбор LocalMessagingConfig/Postgres;
- `packages/services/boba-runtime/src/boba/runtime/storage.py`:
  `StorageConfig`, `StorageFactory`;
- `packages/services/boba-runtime/src/boba/runtime/launchers.py`:
  `ToolLaunchers` и встроенная сборка sandbox;
- `packages/services/boba-runtime/src/boba/runtime/signin.py`:
  фабрика конкретных способов входа.

Выбор реализаций в корне сборки нормален. Здесь часть выбора помещена в
пакет, который одновременно заявлен как общий runtime: новый транспорт,
хранилище или способ входа требует менять его конфиги и фабрики.

Решение: отделить общие порты/сборку от готовых инфраструктурных комплектов.
Комплект регистрирует фабрику, модель конфига и жизненный цикл. Приложение
передаёт набор комплектов; повторяющиеся выборы bus/payloads/locks должны
выдавать согласованный набор из одной фабрики. Не заводить три независимых
реестра с возможностью несовместимого выбора. Не разносить всё по десяткам
микропакетов: сначала выделить устойчивые границы auth, messaging, storage.

Ошибки неверной регистрации/конфига — до запуска ресурсов. Ошибки реализации
переводятся в контракт соответствующего порта, а не попадают вызывающему
коду как ошибки чужой библиотеки.

### 8. Общий CLI ограничивает набор команд

Места: `boba.runtime.config.ProgramCommand`, `ConfigArguments`;
собственные парсеры `boba.cli.app.ArgumentParser` и `boba.mcp_server.app.McpEntry`.

Общий helper зашивает serve/health/migrate, поэтому приложения с дополнительной
командой обходят его. Это менее срочно, чем авторизация и wire-контракты,
но ведёт к повторению разбора аргументов.

Решение: приложение передаёт описания команд и их установщики аргументов;
общий код занимается разбором. MigrationArguments остаётся подключаемым
набором аргументов, а не причиной перечислять приложения. SystemExit и код
возврата принадлежат CLI, ошибки выполнения — вызываемому сервису.

### 9. Форматы документов: закрытая фабрика адаптеров

Места: `packages/infra/format/boba-doc/src/boba/doc/document.py`:
`DocumentKind`, `Formats`; `router.py`: `DocumentRouter`; `ocr.py`: `OcrEngines`.

Здесь нет зависимости от AID/MCP, но новый reader требует правки общего
роутера и таблиц форматов. Выделить регистрацию reader с распознаванием
формата и factory, которые передаются роутеру. Поддерживаемые media types
строить из зарегистрированных reader. Конкретные DOCX/PDF/etc. реализации
вправе знать свой формат. OCR сейчас не разрабатывать: это только найденная
граница в уже имеющемся коде, пользователь отложил OCR-работы.

## Сопутствующее смешение ответственности

`ConnectionTable`/`ConnectionsColumn`/`GrantsColumn` в core connections,
`UsersColumn` в core identity, `Live*Column` в core messaging и
`LiveLocksColumn` в core identity относятся к хранению. Они не образуют
список приложений, но их размещение заставляет домен описывать проекции БД.
При изменении соответствующих репозиториев перенести SQL-детали туда;
чистым портам оставить модели предметной области. Не связывать эту уборку
с изменением формата таблиц без необходимости.

## Уже используемые подходящие механизмы

- `boba.connections.manifest.ConnectionTypes` и `boba.connections.address`
  загружают манифесты реализаций через entry points.
- `boba.llm.providers.LlmProviderTypes` получает модели и фабрики из пакетов,
  а не перечисляет HTTP/ONNX/etc. в ядре.
- Программа tool-плагина получает объявления через `boba.tools`;
  `PluginMigrations` запрашивает план, а не импортирует реализацию хранилища.

Эти механизмы можно использовать как образец границы. Не копировать их
классы и не заводить новый общий пакет только ради одинакового цикла обхода.
Глобальные кеши/саморегистрацию проверять отдельно: возможность расширения
не означает, что жизненный цикл каждого реестра уже удачно инкапсулирован.

## Порядок дальнейших изменений

1. Выполнено в коде: имя приложения, ненужная зависимость bus от него,
   передача путей ресурсов из AID.
2. Разделить субъекты/ресурсы grants и убрать два списка движков toolkit;
   сохранить wire-значения и проверки совместимости в адаптерах.
3. Разделить факт входа/credentials и бэкенды auth; затем фабрики auth.
4. Отделить механизм messaging от прикладного каталога и проверки публикации.
5. Выделить инфраструктурные комплекты runtime; после этого общий CLI и
   расширение reader документов.

Для каждого пункта сначала менять весь целевой путь: контракт → реализация
→ корень сборки → обработка ошибок → удаление старого пути. Затем отдельный
этап адаптации и выполнения тестов другой моделью. Не заявлять готовность
по одной замене enum. Любая новая реализация в проверке расширяемости должна
подключаться без редактирования общего слоя.

## Передача этапа тестирования

Тесты и testing support в этом этапе не менялись и не запускались. Для уже
изменённого кода потребуется заменить AppName.AID/MCP на значения,
адаптировать вызовы PgMessageBus и проверку SourceProgram.share. Добавить
проверку произвольного третьего приложения, некорректного имени и разных
путей ресурсов двух приложений. Установленная сборка должна сохранить путь
share внутри своего дерева.

Отдельная задача по SQL-миграциям продолжается по §15
[mcp-database-endpoints-implementation.md](mcp-database-endpoints-implementation.md).
Миграции не удаляют таблицы, отсутствующие в их собственном определении;
каталогов приложений и таблиц в общем Python-исполнителе нет.

Статические проверки текущих правок: Pyright без ошибок, `sec/sec.sh sast`
завершился с кодом 0 (Ruff/Bandit/Semgrep; Semgrep без находок),
`git diff --check` без замечаний. Это не функциональная проверка.
