# Руководство администратора boba

Документ для того, кто впервые видит boba и машину, на которой его предстоит
собрать, запустить и сопровождать. Он отвечает на четыре вопроса: что нужно
сделать на новой машине, чтобы проект собрался; как запустить его в docker
compose; как запустить без Docker, юнитами systemd; как запустить на хосте под
отладчиком. Попутно объясняется, почему каждая вещь устроена именно так: без
причин раскладка каталогов и ограничения контейнеров выглядят произвольными, а
первое же отклонение от инструкции ставит в тупик.

Значения в примерах — имена, адреса, домены — выдуманные. Что стоит на
конкретной машине, записано в её собственной памятке рядом с деревом compose
(например `compose/README-<пользователь>.md`).

## 1. Что такое boba для администратора

Boba — три приложения, каждое в своём процессе и со своим образом.

**chainlit** (чат, порт 8501) — веб-интерфейс, в котором пользователь
разговаривает с языковой моделью. Сам он инструментов почти не исполняет: когда
модель просит выполнить команду, запрос к базе или поиск по базе знаний, чат
обращается к сервису boba-mcp.

**boba-mcp** (сервис инструментов, порт 8650) — сервер протокола MCP. Он
исполняет инструменты (bash, запросы к PostgreSQL, ClickHouse и Oracle, чтение
документов, поиск по Confluence и базе знаний) и хранит файлы пользователей.
Каждый вызов идёт в песочнице — отдельном процессе без прав, со своим корнем
файловой системы и лимитами памяти и процессора.

**studio** (API и страницы, порт 8502) — REST API над теми же инструментами,
каталог данных и страница workflow. Инструменты исполняет сам, тем же
механизмом песочницы, что и boba-mcp.

Чат и сервис связаны по сети: чат — клиент, сервис — сервер. Чат входит на
сервис от имени пользователя, предъявляя подписанное утверждение «это такой-то
пользователь с такими-то ролями»; подпись проверяется общим секретом. Поэтому у
чата и сервиса в конфигурации есть пара значений, которые обязаны совпадать, —
о них в разделе 5.

Чтобы всё это работало, снаружи нужны:

- **PostgreSQL** — история чатов, пользователи, соединения, каталог, база
  знаний. Приложения сами создают схемы и расширения при старте, поэтому роль
  приложения должна иметь право `create extension` либо расширения ставит
  администратор базы заранее: `vector` (pgvector), `pg_trgm`, `btree_gin`,
  `btree_gist`, `unaccent`.
- **Kerberos и каталог (Active Directory либо совместимый)** — вход
  пользователей по SSO, вход приложений в PostgreSQL по keytab, роли
  пользователей из групп каталога. Без каталога приложение работает с
  локальными учётками из конфигурации.
- **Языковая модель** — любой сервер с OpenAI-совместимым API либо ollama.
- **Источники данных инструментов** — ClickHouse, Oracle, Confluence, почтовый
  сервер. Нужны только тем инструментам, которые к ним ходят; без них
  приложение стартует.
- **Обратный прокси** (nginx) перед приложениями, если они публикуются под
  одним именем с префиксами `/boba`, `/boba-mcp`, `/boba-studio`. Настройка
  nginx описана в разделе 13.

## 2. Требования к машине и однократная подготовка

Приложения запускаются от обычного пользователя, не от root. Это относится ко
всем трём способам запуска: контейнеры поднимает rootless-демон Docker этого
пользователя, юниты systemd — его пользовательский менеджер, отладка идёт от
него же. Root нужен один раз — подготовить машину так, чтобы пользователь дальше
справлялся сам.

Почему не root и не обычный демон Docker. Инструменты исполняют произвольные
команды, которые пишет языковая модель. Песочница — основная защита, но если она
окажется пробита, злоумышленник получит права процесса приложения. При
rootless-демоне это права непривилегированного пользователя машины, а
пользователь внутри контейнера отображается в его subuid — на машине у такого
номера нет вообще ничего. При обычном демоне ошибка в конфигурации контейнера
означала бы root на машине.

Что делает root, по пунктам и с причиной.

**Пользователь и linger.** Заводится пользователь (в примерах — `boba`), и ему
включается linger:

```
useradd -m boba
loginctl enable-linger boba
```

Без linger systemd останавливает пользовательский менеджер, когда пользователь
выходит из системы, а вместе с ним — демон Docker и все юниты. С linger они
стартуют при загрузке машины и живут без входа.

**Диапазоны subuid и subgid.** Нужны rootless-демону: в них отображаются
пользователи контейнеров. Во многих системах диапазон выдаёт уже `useradd`
(настройки `SUB_UID_COUNT` и `SUB_GID_COUNT` в `/etc/login.defs`), поэтому
сначала смотрят, что есть:

```
grep '^boba:' /etc/subuid /etc/subgid
```

Строка вида `boba:100000:65536` в обоих файлах означает, что делать больше
нечего. Если строк нет, диапазон добавляют:

```
usermod --add-subuids 100000-165535 --add-subgids 100000-165535 boba
```

Числа в примере — первый свободный диапазон на машине, где других записей в
`/etc/subuid` нет. Диапазоны разных пользователей не должны пересекаться:
иначе файлы контейнеров одного пользователя окажутся доступны контейнерам
другого. `usermod` пересечение не проверяет, поэтому на машине с уже занятыми
диапазонами берут следующие 65536 номеров после последнего занятого.

**Rootless Docker.** Демон ставится самим пользователем
(`dockerd-rootless-setuptool.sh install`), cgroup-драйвер — systemd, иерархия
cgroup — v2. Установщику нужны `newuidmap` и `newgidmap` (пакет `uidmap` либо
`shadow`) и работающий пользовательский systemd: чего не хватает, покажет
`dockerd-rootless-setuptool.sh check`. Запускать установщик нужно в сеансе, где
отвечает `systemctl --user`, — после входа по ssh либо `machinectl shell
boba@`. После `sudo -u boba` или `su` сеанса systemd может не быть, и
`systemctl --user` отвечает `Failed to connect to user scope bus ...
$DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined`; при включённом
linger достаточно задать переменную: `export XDG_RUNTIME_DIR=/run/user/$(id -u)`.
Проверка установки: `docker info` показывает `rootless` среди
`Security Options`, `Cgroup Driver: systemd` и `Cgroup Version: 2`.

**Контроллеры cgroup для пользователя.** Песочница ограничивает каждый вызов по
памяти, процессору и числу процессов. Для этого пользовательскому менеджеру
systemd должны быть делегированы контроллеры `cpu`, `memory`, `pids`; по
умолчанию `cpu` часто не делегируется.

```
mkdir -p /etc/systemd/system/user@.service.d
printf '[Service]\nDelegate=cpu cpuset io memory pids\n' > /etc/systemd/system/user@.service.d/delegate.conf
systemctl daemon-reload
```

Делегирование применяется при запуске пользовательского менеджера. Если он уже
работает — а при включённом linger он работает с загрузки, — его перезапускают:
`systemctl restart user@$(id -u boba).service` (команда останавливает все
процессы пользователя, включая его контейнеры) либо перезагружают машину.
Проверка — перечень контроллеров, доставшихся менеджеру:

```
cat /sys/fs/cgroup/user.slice/user-$(id -u boba).slice/user@$(id -u boba).service/cgroup.controllers
```

В выводе должны быть `cpu`, `memory` и `pids`.

**/dev/fuse.** Рабочий каталог пользователя в песочнице — файл-образ ext4,
который монтируется драйвером `fuse2fs` без root. Устройство должно быть
доступно пользователю на чтение и запись (`crw-rw-rw-`), модуль `fuse` —
загружен. В большинстве систем так и есть сразу. Если устройства нет,
модуль загружают (`modprobe fuse`, постоянно — строка `fuse` в файле каталога
`/etc/modules-load.d`); если права уже — их задаёт правило udev, например
файл `/etc/udev/rules.d/99-fuse.rules` со строкой `KERNEL=="fuse", MODE="0666"`.

**User namespace без привилегий.** Песочница строится на `bwrap` в собственном
user namespace: `sysctl kernel.unprivileged_userns_clone` (где он есть) равен 1,
`user.max_user_namespaces` больше нуля. Постоянно значения записывают в файл
каталога `/etc/sysctl.d`.

**cgroup2 без nsdelegate** — только если приложение с песочницей работает в
контейнере. Контейнер живёт в своём cgroup namespace, и ядро с опцией
монтирования `nsdelegate` запрещает процессу выйти за его границу. Песочнице же
нужно перенести дочерний процесс в соседнее поддерево (раздел 9). Root
перемонтирует иерархию без этой опции:

```
mount -t cgroup2 -o remount,rw,nosuid,nodev,noexec,relatime cgroup2 /sys/fs/cgroup
```

Опции перечислены явно, вместе с типом и именем устройства: короткая запись
`mount -o remount /sys/fs/cgroup` берёт текущие опции из таблицы монтирования
и `nsdelegate` оставляет. Проверка: в выводе `findmnt -no OPTIONS
/sys/fs/cgroup` слова `nsdelegate` нет.

Перемонтирование не переживает перезагрузку, поэтому команду выполняют при
каждом старте машины — например, системным юнитом
`/etc/systemd/system/boba-cgroup.service`, включённым командой `systemctl
enable --now boba-cgroup.service`:

```
[Unit]
Description=cgroup2 without nsdelegate for the boba sandbox

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/mount -t cgroup2 -o remount,rw,nosuid,nodev,noexec,relatime cgroup2 /sys/fs/cgroup

[Install]
WantedBy=multi-user.target
```

Юниту нельзя задавать `ProtectSystem`, `PrivateTmp`, `PrivateDevices` и другие
ограничения, которые дают службе отдельное пространство монтирования:
перемонтирование должно произойти в пространстве самой машины.

Для запуска юнитами systemd и для отладки на хосте это не требуется.

**Инструменты сборки.** `make`, `gcc`, `git`, `curl`, `tar`, `xz`, `envsubst`
(пакет gettext), заголовки Kerberos (`krb5-config`), Python 3.11. Остальное —
`uv`, компиляторы, node — сборка берёт из образов.

**Базовые образы.** Сборка идёт в контейнерах и ожидает в демоне пользователя
пять образов: `dmp/glibc:2.28`, `dmp/gcc:8.5.0`, `dmp/python:3.11-dist`,
`dmp/nodejs:20`, `dmp/nodejs:22`. Их загружают один раз (`docker load` из
архива либо `docker pull` из своего реестра); другие имена задаются
переменными `GLIBC_IMAGE`, `GCC_IMAGE`, `PYTHON_IMAGE`, `NODE_IMAGE`,
`STUDIO_NODE_IMAGE`.

Проверять вручную всё перечисленное не нужно: цели `make dev`, `make debug` и
`make install` запускают проверку машины и называют, чего не хватает и что
попросить у root. На подготовленной машине вывод такой:

```
  ✓ пользовательский systemd работает (/run/user/1001)
  ✓ linger включён: юниты boba живут без входа в систему
  ✓ контроллеры cgroup cpu, memory, pids делегированы user@1001.service
  ✓ /dev/fuse доступен: образы workspace монтируются без root
  ✓ непривилегированные user namespace разрешены: bwrap запускается без root
  ✓ docker работает в режиме rootless
  ✓ у boba есть диапазоны subuid и subgid
  ✓ cgroup2 смонтирована без nsdelegate
```

Каждая строка с `✗` сопровождается командой для root.

## 3. Раскладка каталогов

В репозитории пять каталогов верхнего уровня, и разделены они по одному
признаку: кто туда пишет.

| Каталог | Что лежит | Кто пишет | В git |
|---|---|---|---|
| `packages/` | код приложений, их общие конфиги (`apps/boba-<приложение>/conf`) и статика | разработчик | да |
| `build/` | `Makefile`, `Dockerfile`, сценарии и образцы (`conf/`); `build/src` — скачанные артефакты сборки | разработчик; `build/src` — `make fetch` | да, кроме `build/src` |
| `runtime/` | то, что подкладывается приложению для работы: модели, бинарники и библиотеки песочницы, её образы | сборка (`make fetch`, `sandbox`, `plugin-rootfs-all`) | нет |
| `compose/<приложение>/` | случай запуска в Docker: `docker-compose.yml`, `.env`, `conf/` (специфика машины), `data/` | администратор — `conf` и `.env`; контейнер — `data` | только `docker-compose.yml` |
| `debug/<приложение>/` | случай запуска на хосте под отладчиком и для тестов: `conf/`, `data/` | администратор — `conf`; процесс на хосте — `data` | нет |

`runtime/` устроен плоско и один на репозиторий:

```
runtime/
  models/    fastembed/  rapidocr/  onnx-genai/
  third/     bin/bwrap  bin/fuse2fs  lib/libstdc++.so.6  lib/libgcc_s.so.1
  sandbox/   workspace.ext4  plugins/<пакет>/rootfs.ext4  tools/
```

Почему отдельно от `compose/` и `debug/`. Модели и образы песочницы — это
гигабайты, одинаковые для контейнера и для отладки. Пока они лежали копиями в
каждом дереве, их приходилось перекладывать после каждой пересборки, и копии
расходились. Один каталог читают все: compose монтирует его томами, отладка
называет его путём в своей конфигурации, сборка образа boba-mcp берёт образы
песочницы прямо из него.

Почему `compose/` и `debug/` раздельны. Контейнер пишет данные от
пользователя 1000 внутри себя — на машине это номер из subuid: начало
диапазона плюс 999, при диапазоне с 100000 — 100999. Процесс под отладчиком пишет от самого пользователя. Пока оба писали в
один каталог `data`, каждый натыкался на файлы другого: кэш билетов Kerberos с
чужим владельцем (`Credentials cache permissions incorrect`), журнал вызова с
режимом `0600`, который второй не может прочесть. Раздельные деревья снимают
вопрос целиком: в `compose/<приложение>/data` пишет только контейнер, в
`debug/<приложение>/data` — только процесс на хосте.

Почему нет символических и жёстких ссылок. Ссылка прячет, откуда на самом деле
читается файл: каталог выглядит самостоятельным, а живёт за счёт другого, и
перенос или удаление «лишнего» ломают его молча. Жёсткая ссылка вдобавок
переживает удаление оригинала и продолжает держать старую версию. В проекте
каждый путь либо настоящий каталог, либо явно назван в конфигурации. Исключения
не наши: `systemctl --user enable` сам ставит ссылку в `default.target.wants`, а
в образе и дереве релиза у интерпретатора Python есть свои `python -> python3`.
Кэш моделей Hugging Face по умолчанию тоже состоит из ссылок; сценарий загрузки
после скачивания заменяет их настоящими файлами.

Владельцы и права. `runtime/` принадлежит пользователю сборки и закрыт на запись
остальным; чтение открыто всем — так файлы видит пользователь контейнера. Для
`runtime/third/bin` это не пожелание: песочница отказывается запускать `bwrap` и
`fuse2fs` из каталога, куда может писать кто-то кроме владельца (раздел 12,
`UntrustedBinaryError`).

## 4. Сборка

Сборкой управляет `build/Makefile`; `make -C build help` перечисляет цели.
Все тяжёлые шаги идут в контейнерах базовых образов, поэтому на машине нужны
только Docker и `make`. Стадии выполняются по порядку — каждая кладёт то, что
нужно следующей:

| Цель | Что делает | Куда кладёт | Время и объём (ориентир) |
|---|---|---|---|
| `base` | образ сборки `boba-base` с компилятором и uv | демон Docker | минуты в первый раз, секунды повторно |
| `fetch` | скачивает исходники bwrap, libfuse, e2fsprogs, uv, фронт chainlit, шрифты; модели | `build/src`, `runtime/models` | модели — около 6 ГБ, время зависит от сети |
| `sandbox` | собирает `bwrap` и `fuse2fs`, делает шаблон `workspace.ext4` | `runtime/third`, `runtime/sandbox` | около минуты, 1 ГБ |
| `plugin-rootfs-all` | образ корня файловой системы на каждый плагин инструментов | `runtime/sandbox/plugins/<пакет>/rootfs.ext4` | 10–15 минут, 7–8 ГБ |
| `web` | фронт: страница чата и страница workflow | каталоги `assets` пакетов (в git не входят) | минуты в первый раз |
| `build APP=<приложение>` | образ `boba-<приложение>:<версия>` | демон Docker | chainlit и studio — около минуты, mcp — 3–4 минуты |
| `test APP=<приложение>` | проверка образа: импорт модулей, запуск бинарников песочницы | — | секунды; печатает `RESULT: ALL OK` |
| `dev APP=<приложение>` | готовит дерево `compose/<приложение>` | `compose/<приложение>` | секунды |
| `debug APP=<приложение>` | готовит дерево `debug/<приложение>` и цели VS Code | `debug/<приложение>`, `.vscode` | секунды |
| `release APP=<приложение>` | дерево установки без Docker из готового образа | `release/<версия>/<экземпляр>` | до минуты; chainlit 4 ГБ, studio 9 ГБ, mcp 11 ГБ |

Цели `build`, `test`, `dev`, `debug`, `release` без `APP` идут по всем трём
приложениям; `make all` выполняет `fetch sandbox plugin-rootfs-all web build dev`
подряд.

Первая сборка на новой машине:

```
source dev.sh                      # окружение разработчика: .venv и uv
make -C build base
make -C build fetch
make -C build sandbox
make -C build plugin-rootfs-all
make -C build web
make -C build build JOBS=8
make -C build test
```

`source dev.sh` создаёт `.venv` в корне репозитория (`uv sync` по `uv.lock`):
оттуда сборка берёт Python для своих сценариев, а отладка и тесты — сами
приложения. В `.venv` ставится собственное колесо `python-oracledb`, которое
`dev.sh` собирает целью `make oracledb-wheel`.

`JOBS` ограничивает число заданий компилятора на шаг сборки (по умолчанию 4).
Запускать сборки одновременно нельзя: цели делят каталоги `runtime/` и
`build/src`, а неограниченная параллельная сборка способна занять всю память
машины.

Образ boba-mcp большой, потому что несёт в себе образы корней всех плагинов и
шаблон workspace — около 9 ГБ. Сделано это намеренно: пересборка плагинов на
машине не меняет файлы под работающим сервисом. У studio те же образы
приходят томом из `runtime/sandbox`.

Размер образа в выводе `docker images` зависит от того, как он попал в демон.
У образа, собранного на месте, слои хранятся сжатыми; у загруженного через
`docker load` — несжатыми, и число получается почти вдвое больше при том же
содержимом. Сравнивать образы стоит по `docker history`.

Частичная пересборка. Изменился код приложения — `make build APP=<приложение>`.
Изменился плагин инструментов — `make plugin-rootfs PLUGIN=<пакет>`, затем
`make build APP=mcp` (образы плагинов внутри образа) и пересоздание контейнера
studio (у него образы приходят томом). Изменился фронт — `make web`, затем
`build`. Изменился только общий конфиг приложения — тоже `build`: конфиг лежит
в образе.

В закрытом контуре рядом с `Makefile` кладут `build/conf/pip.conf`,
`build/conf/uv.toml` (индексы пакетов) и `build/conf/ca-chain.crt` (корневые
сертификаты); образцы — `*.example`. Адреса зеркал артефактов задаются
переменными, перечисленными в `make help`. Значения переменных сборки,
постоянные для машины, записывают в `build/conf/local.mk` — файл подключается
автоматически и в git не входит.

Версия у всех пакетов одна; `make version` показывает её, `make version-set
VER=X.Y.Z` проставляет во все `pyproject.toml`. Тег образа в строке `image:`
файлов `docker-compose.yml` при смене версии правят вручную.

## 5. Конфигурация

### Два файла вместо одного

У каждого приложения конфигурация состоит из двух файлов, и приложению их
называют двумя обязательными аргументами:

```
python -m boba.mcp_server --config <общий конфиг> --site <специфика случая>
```

**Общий конфиг** — `packages/apps/boba-<приложение>/conf/config.toml` и
`plugins/<инструмент>.toml` рядом с ним. Он описывает устройство приложения:
какие есть профили чата, какие инструменты включены, какие пулы соединений,
какие способы входа. В нём нет ни одного адреса, пароля или пути этой машины —
только ссылки вида `${site.pg_host}` и `${env.data}`. Он лежит в git, попадает в
образ и в дерево релиза и одинаков везде.

**site.toml** — всё, что зависит от машины и случая запуска: порты, пути,
адреса серверов, имена моделей, логины, секреты. Он свой у каждого случая:
`compose/<приложение>/conf/site.toml`, `debug/<приложение>/conf/site.toml`,
`<каталог установки>/conf/site.toml`. В git он не попадает никогда — имя файла
внесено в `.gitignore` целиком.

Почему так. Пока конфигурация была одним файлом вне git, у каждого случая
запуска была своя копия на четыреста строк, и правка устройства приложения
(новый профиль, новый параметр пула) требовала пройти по всем копиям — их
забывали. Теперь устройство описано в одном месте и версионируется вместе с
кодом, а вне git остаётся только то, что там и должно быть: секреты и
особенности машины. Подключение явное: какой файл читается, видно из командной
строки, и приложение не ищет конфигурацию «где-нибудь рядом».

Загрузчик следит за разделением. В site.toml допустимы только две секции,
`[env]` и `[site]`; любая другая — ошибка старта, иначе устройство приложения
снова описывалось бы в двух местах. В общем конфиге эти две секции,
наоборот, запрещены.

| В общем конфиге (git) | В site.toml (вне git) |
|---|---|
| профили чата, их системные промпты и параметры выборки | имена моделей (`[site.models]`) |
| секции входа: какие способы, какие заголовки, пути | секреты, адреса каталога, таблицы ролей и локальные учётки |
| пулы и схемы PostgreSQL | хост, адрес, база, способ входа и пароль |
| список MCP-серверов чата, таймауты | схема, хост, порт и префикс сервиса |
| включённые инструменты, лимиты песочницы плагинов | адреса Confluence и почты, их учётки |
| ссылки `${env.*}` на каталоги | сами каталоги: `data`, `models`, `third`, `sandbox`, `app_root`, `krb` |

### Как собирается конфигурация

Слои накладываются по порядку, поздний перекрывает ранний:

1. вычисленный `env.base` — каталог над `conf/`, в котором лежит site.toml.
   Рядом со спецификой случая лежат и его данные, поэтому пути в site.toml
   пишут от `${env.base}`;
2. общий `config.toml`;
3. файлы `plugins/<имя>.toml` рядом с общим конфигом — каждый становится
   секцией `tool.<имя>`;
4. site.toml;
5. переменные окружения `BOBA_<КЛЮЧ>` — они переопределяют отдельные ключи
   секции `[env]`: `BOBA_BASE`, `BOBA_DATA`, `BOBA_PORT`, `BOBA_HOST`,
   `BOBA_URL_PREFIX`, `BOBA_INSTANCE_ID`, `BOBA_APP_ROOT`, `BOBA_CGROUP_BASE`,
   `BOBA_TOOL_LAUNCHER`, `BOBA_MESSAGING`, `BOBA_WORKFLOW_PAGE`,
   `BOBA_PUBLIC_URL`, `BOBA_MCP_SCHEME`, `BOBA_MCP_HOST`, `BOBA_MCP_PORT`,
   `BOBA_MCP_PREFIX`. Других переменных загрузчик не читает.

Ссылки `${секция.ключ}` разрешаются по собранному целому, поэтому значение из
site.toml может ссылаться на `${env.base}`, а общий конфиг — на любое значение
site.toml.

### Первый site.toml

Образца site.toml в репозитории нет намеренно: образец пришлось бы помнить
править при каждом изменении общего конфига. Вместо него перечень ключей
строится из самого общего конфига:

```
$ make -C build site-keys APP=mcp
[env]
    data  — krb.ccache_dir; переопределяется переменной BOBA_DATA
    listen_host  — mcp.host
    port  — mcp.port; переопределяется переменной BOBA_PORT
    third  — storage.binaries.dirs
    ...
[site]
    auth_secret  — session.auth_secret
    confluence.host  — tool.confluence.confluence.host
    pg_host  — postgres.host
    proxy_secret  — auth.proxy.secret
    ...
```

Каждая строка — ключ и поле общего конфига, которое на него ссылается. Ключ с
точкой (`confluence.host`) — поле `host` таблицы `[site.confluence]`.

Пропущенный ключ обнаруживается при старте: приложение завершается и называет и
ключ, и поле, которому он понадобился.

```
boba-mcp failed: InterpolationKeyError: Interpolation key 'site.proxy_secret' not found
    full_key: auth.proxy.secret
```

Пример site.toml сервиса boba-mcp в контейнере (значения выдуманы):

```toml
[env]
    port          = 8650
    url_prefix    = ""
    public_url    = "https://boba.example.com/boba-mcp"
    listen_host   = "0.0.0.0"
    cgroup_base   = "/cgroup/boba-sandbox-mcp"
    tool_launcher = "sandbox"

    data    = "${env.base}/data"
    sandbox = "${env.base}/sandbox"
    third   = "${env.base}/third"
    models  = "${env.base}/models"
    krb     = "${env.base}/conf/krb"

[site]
    ldap_netbios       = "EXAMPLE"
    ldap_base_dn       = "DC=example,DC=com"
    ldap_url           = "ldaps://dc1.example.com:3269"
    ldap_bind_user     = 'EXAMPLE\boba-reader'
    ldap_bind_password = "..."

    krb_domain      = "example.com"
    krb_realm       = "EXAMPLE.COM"
    krb_config      = "${env.krb}/krb5.conf"
    krb_http_keytab = "${env.krb}/boba-svc.keytab"
    krb_ccache_http = "${env.data}/krb/krb5cc_http"

    pg_host        = "postgres.example.com"
    pg_addr        = "10.0.0.14"
    pg_port        = 5432
    pg_database    = "boba"
    pg_sslmode     = "disable"
    pg_auth_method = "kerberos"

    auth_secret  = "..."
    proxy_secret = "..."

    [site.pg_auth.kerberos]
        method    = "kerberos_keytab"
        principal = "boba-svc@${site.krb_realm}"
        keytab    = "${env.krb}/boba-svc.keytab"
        service   = "postgres"

    [site.local_auth.users]
        "admin" = "..."

    [site.local_auth.roles]
        "admin" = ["wrt", "read"]

    [site.mcp_client]
        secret = "..."

    [site.proxy]
        allowed_clients = ["10.0.0.0/16"]

        [site.proxy.local_roles]
            "admin" = ["wrt", "read"]

    [site.confluence]
        host = "wiki.example.com"
        port = 443
        path = "/confluence"

    [site.models]
        embedding = "intfloat/multilingual-e5-large"
```

В контейнере `env.base` равен `/app/boba`: site.toml смонтирован в
`/app/boba/conf/site.toml`. Поэтому пути здесь те, что видит процесс внутри
контейнера, а не пути машины.

### Секреты и keytab

Секреты лежат в `[site]`; какие из них обязаны совпадать у разных приложений:

- `auth_secret` — одинаков у chainlit и studio: чат выдаёт cookie входа,
  studio её проверяет;
- `database_encryption_key` — одинаков у всех, кто читает таблицу соединений
  (chainlit и studio);
- `proxy_secret` и секрет клиента (`[site.mcp_client].secret`) — одинаковы у
  chainlit и boba-mcp: первым чат подписывает утверждение о пользователе,
  вторым представляется сервису как клиент.

Как их сгенерировать и что каждый из них защищает, подробно описано в
разделе 14.

Keytab сервисной учётки и `krb5.conf` лежат в `conf/krb` случая запуска.
Keytab — тоже секрет: владелец — пользователь, от которого работает приложение,
режим `0400`. В дереве compose файл читают двое — администратор и процесс
контейнера, поэтому режим там `0640`: владелец — администратор, группа —
группа контейнера; её расставляет `make dev` (раздел 6). Отладка на хосте свой keytab не заводит:
ключ `krb` в её site.toml указывает на `compose/<приложение>/conf/krb`. Копия
ключа сервиса ничего бы не дала, а при смене пароля учётки пришлось бы менять
обе.

### Чем различаются site.toml трёх случаев

| Ключ `[env]` | compose | отладка | установка без Docker |
|---|---|---|---|
| `base` (вычисляется) | `/app/boba` | `<репозиторий>/debug/<приложение>` | `<каталог установки>` |
| `port`, `url_prefix` | рабочие | свои, чтобы не мешать контейнерам | рабочие |
| `models`, `third`, `sandbox` | `${env.base}/...` — тома и содержимое образа | `${env.base}/../../runtime/...` | `${env.base}/...` — из дерева релиза |
| `app_root` | `${env.base}/app_root` | каталог `assets` пакета приложения | `${env.base}/app_root` |
| `krb` | `${env.base}/conf/krb` | `${env.base}/../../compose/<приложение>/conf/krb` | `${env.base}/conf/krb` |
| `cgroup_base` | `/cgroup/boba-sandbox-<приложение>` | каталог `sandbox` юнита `boba-sandbox@debug` | задаёт юнит приложения |
| `tool_launcher` | `sandbox` | `process` | `sandbox` |
| `messaging_provider` | `postgres` | `local` | `postgres` |

Секция `[site]` у всех случаев одного приложения, как правило, совпадает.

### Вложения чата

Chainlit держит вложения сессий в каталоге `.files` внутри своего корня статики
и создаёт его при импорте; настройки для этого в нём нет. Корень статики при
этом — часть образа, а в отладке — каталог исходников пакета, и писать туда
приложение не должно. Поэтому каталог вложений задаётся обязательным ключом
`[chainlit].files_dir` общего конфига (`"${env.data}/files"`): точка входа
подменяет путь внутри chainlit до того, как он успеет создать `.files`.
Вложения оказываются там же, где остальные данные приложения, — в `data`.

## 6. Запуск в docker compose

### Что лежит в дереве compose

После `make -C build dev` (без `APP` — для всех трёх приложений) дерево
приложения выглядит так:

```
compose/mcp/
  docker-compose.yml     в git
  .env                   значения этой машины для compose-файла
  conf/
    site.toml            пишет администратор (раздел 5)
    boba.env             окружение контейнера, порождает make dev
    krb/                 keytab и krb5.conf
  data/                  пишет только контейнер
    krb/  workspace/  tool-logs/  dump/
```

Цель `dev` делает то, что можно сделать без человека: создаёт каталоги,
порождает `conf/boba.env`, для приложений с песочницей ставит и запускает юнит
`boba-sandbox@<приложение>.service`, создаёт `.env`, если его нет, и проверяет
его. Чего она не делает: не пишет site.toml и не кладёт keytab — про
отсутствующий site.toml она сообщает строкой
`нет .../conf/site.toml — напиши его по перечню ключей: make site-keys APP=mcp`.

Общего конфига в дереве нет: он в образе, по пути `/app/boba/conf/config.toml`.
Томами в контейнер приходит только специфика машины.

Владельцы. Процесс в контейнере идёт от пользователя 1000, а на машине это
номер из диапазона subuid — не администратор. Конфигурацию он должен читать, в
данные — писать, и при этом секреты не должны быть открыты всем. `make dev`
расставляет это сам, последней строкой сообщая
`владельцы: .../conf читает группа 1000 контейнера, в .../data пишет его
пользователь 1000`:

```
drwxr-s---  boba     <subgid>  conf/           администратор правит, контейнер читает через группу
-rw-r-----  boba     <subgid>  conf/site.toml
drwxrwsr-x  <subuid> boba      data/           контейнер пишет, администратор читает через группу
```

Сменить владельца на номер из subuid обычный пользователь не может, поэтому
цель делает это в user namespace с тем же отображением, что у демона
(`unshare --map-auto`): там администратор — пользователь 0, а пользователь
контейнера — 1000. Файлы, которые администратор положит в `conf` позже,
наследуют группу от каталога; режим им ставят `0640`. Трогает цель только
файлы администратора: то, чем уже владеет контейнер, не меняется.

### Compose-файл и .env

Compose-файлы плоские: в них нет значений по умолчанию, условных подстановок и
якорей — только простые `${ИМЯ}`. Всё, что зависит от машины, лежит в `.env`
рядом, по строке на значение:

```
BOBA_USER=1000:1000
BOBA_SANDBOX_CGROUP=/sys/fs/cgroup/user.slice/user-1001.slice/user@1001.service/boba.slice/boba-mcp.slice/boba-sandbox@mcp.service/sandbox
BOBA_NETWORK=boba
BOBA_NETWORK_EXTERNAL=true
BOBA_ADDRESS=
BOBA_ADDRESS_2=
```

Образец с пояснением каждой переменной — `build/conf/compose.env.example`.
`make dev` порождает `.env` сам: пользователя и путь cgroup (в нём стоит номер
текущего пользователя, `id -u`) он вычисляет, сеть называет `boba`, адреса оставляет пустыми.
Готовый `.env` цель не перезаписывает, но проверяет: каждой переменной
compose-файла соответствует строка, обязательные значения не пусты, каталог
cgroup и сеть существуют.

Раз значений по умолчанию нет, запускать `docker compose` нужно после `make
dev`. Без `.env` compose не откажет, а выдаст предупреждение
`The "BOBA_USER" variable is not set. Defaulting to a blank string.` и попробует
создать контейнер с пустыми значениями — это не тот запуск, который нужен.

Сеть. Чат обращается к сервису инструментов, прокси — ко всем трём приложениям,
поэтому сеть у них общая. Compose-проект у каждого приложения свой, а сеть,
созданная проектом, принадлежит только ему; общую сеть заводят один раз
отдельно и подключаются к ней как к внешней:

```
docker network create boba
```

`make dev` записывает в `.env` именно это — `BOBA_NETWORK=boba`,
`BOBA_NETWORK_EXTERNAL=true` — и останавливается с подсказкой, если сети нет:
`сети boba нет, а BOBA_NETWORK_EXTERNAL=true — создай её: docker network create
boba`. Имя сети пустым быть не может: `docker compose` отвечает на это
`invalid network name or ID: value is empty`. Другое имя пишут, когда такая
сеть на машине уже есть — та, в которой стоят прокси и базы.

`BOBA_ADDRESS` обычно пуст: адрес выдаёт Docker. Адрес закрепляют
(`BOBA_ADDRESS=10.0.0.6`), только если на адресах контейнеров что-то построено
снаружи — записи DNS или правила межсетевого экрана: иначе после перезапуска
демона контейнер получает другой адрес, и эти записи указывают в пустоту.

### Запуск

```
cd compose/mcp
docker compose up -d mcp        # в chainlit — сервис chainlit, в studio — studio
docker compose ps               # через минуту-полторы: Up ... (healthy)
docker logs -f boba-mcp
```

Сервисы `mcp2` и `chainlit2` в тех же файлах — вторые узлы тех же приложений;
у каждого свой `conf2/site.toml` и `conf2/krb`, окружение `conf/boba.env` у
узлов общее. Каталог `conf2` заводят вручную, когда второй узел нужен.

Порядок запуска: boba-mcp раньше chainlit. Чат подключается к сервису, когда
пользователь открывает сессию; пока сервис недоступен, в логе чата стоит
`mcp server boba_general is unavailable: ... connecting and initializing
failed`, а инструментов сервиса в профиле нет.

Проверка здоровья встроена в образ: раз в 30 секунд контейнер сам запрашивает
свой адрес (`/` у chainlit, `/api/openapi.json` у studio, `/health` у
boba-mcp), порт и префикс берёт из `conf/boba.env`. Значения `BOBA_PORT` и
`BOBA_URL_PREFIX` в этом файле — те же переопределения `[env]`, что и в разделе
5, поэтому порт контейнера задаётся там, а не в site.toml.

Признаки удачного старта boba-mcp и studio в логе:

```
sandbox cgroup: profile 'bash' ok in /cgroup/boba-sandbox-mcp (memory=1073741824B cpu_max=100% ...)
zygote[bash] 373e91 ready: pid=41, warmup 0.0s, section is serving again after 0.3s
...
Uvicorn running on http://0.0.0.0:8650
```

Строк `profile ... ok` и `zygote ... ready` должно быть по одной на каждый
включённый плагин. Строка `clone3 into cgroup refused ... Function not
implemented, falling back to fork` при каждом вызове инструмента — не ошибка:
seccomp-профиль контейнера запрещает `clone3`, и песочница переходит на
запасной путь.

### Почему контейнер устроен так

**Пользователь 1000:1000, а не root.** Внутри контейнера процесс не должен быть
root по двум причинам. Первая — защита: root без capabilities всё ещё владелец
всех файлов образа, включая собственный код. Вторая — техническая: песочница
создаёт user namespace и отображает в нём себя в root этого пространства.
Ядро разрешает процессу без привилегий записать в `uid_map` только
собственный номер, а для номера 0 дополнительно требует capability
`CAP_SETFCAP`. Процесс от 1000 запускает песочницу без единой capability;
процесс от 0 без `SETFCAP` получает `bwrap: setting up uid map: Operation not
permitted`. Выдавать контейнеру `SETFCAP` ради удобства владения файлами —
обмен защиты на удобство, поэтому её не выдают.

**`cap_drop: ALL` и `no-new-privileges`.** У процесса нет ни одной capability, и
получить их через setuid-файл он не может. Песочнице они и не нужны: права
внутри своего user namespace `bwrap` получает от ядра.

**Профиль seccomp** (`build/conf/seccomp-sandbox.json`) у boba-mcp и studio.
Стандартный профиль Docker запрещает `mount` и создание пространств имён, без
которых песочница не строится; свой профиль разрешает ровно их.
`systempaths=unconfined` снимает маскировку `/proc` и `/sys`, иначе вложенный
`bwrap` не может смонтировать собственный `/proc`.

**`/dev/fuse`** — рабочие каталоги пользователей монтируются из файлов-образов
драйвером fuse2fs.

**`cgroup_parent: boba-<приложение>.slice` и том cgroup** — раздел 9.

**Лимиты** `mem_limit`, `cpus`, `pids_limit` ограничивают приложение вместе со
всеми вызовами инструментов; лимиты отдельного вызова задаёт профиль плагина.

### Обновление версии и откат

Новая версия — это новый образ. Общий конфиг приезжает в нём же, site.toml и
данные остаются на месте.

```
make -C build build APP=mcp                  # образ с новым тегом версии
make -C build test APP=mcp
cd compose/mcp
docker compose up -d --force-recreate mcp
```

Если общий конфиг новой версии ссылается на ключ, которого ещё нет в site.toml,
контейнер не стартует и назовёт ключ (раздел 5); перечень — `make site-keys`.

Перед обновлением полезно оставить метку на работающем образе:
`docker tag boba-mcp:<версия> boba-mcp:<версия>-prev`. Откат — вернуть тег и
пересоздать контейнер:

```
docker tag boba-mcp:<версия>-prev boba-mcp:<версия>
docker compose up -d --force-recreate mcp
```

Правка site.toml вступает в силу после пересоздания контейнера. Файл смонтирован
в контейнер поодиночке, и редактор, который сохраняет через замену файла,
оставляет в контейнере старое содержимое, — `restart` в таком случае
недостаточно, нужен `up -d --force-recreate`.

## 7. Запуск под systemd без Docker

Приложение можно запустить и без контейнера — процессом на машине под
управлением systemd. Для этого сборка раскладывает из готового образа дерево
установки, а цель `install` ставит его и юниты.

```
make -C build release APP=mcp
make -C build install APP=mcp
```

`release` кладёт в `release/<версия>/mcp` интерпретатор Python с библиотеками
(`third`), код приложения (`app`), общий конфиг и плагины (`conf`), статику,
модели, образы песочницы и два файла юнитов. Дерево рассчитано на каталог
`/app/boba-<экземпляр>`: этот путь прописан в шебангах `app/bin/*`, в
`conf/boba.env` и в юните. Другой каталог задают при сборке релиза:
`INSTALL_ROOT=/srv` даст `/srv/boba-mcp`.

`install` копирует дерево в каталог установки и ставит юниты в
`~/.config/systemd/user`. Каталог должен существовать и принадлежать
пользователю — цель скажет, что попросить у root, если это не так. При
повторной установке код, интерпретатор, статика, модели, образы песочницы и
общий конфиг заменяются целиком, а `conf/site.toml`, `conf/boba.env`,
`conf/krb` и `data` остаются.

После первой установки администратор пишет `conf/site.toml` (раздел 5), кладёт
keytab и `krb5.conf` в `conf/krb` и запускает:

```
systemctl --user start boba-mcp.service
systemctl --user status boba-mcp.service
journalctl --user -u boba-mcp.service -f
```

### Юниты

Юнитов два, оба пользовательские.

`boba-sandbox@<экземпляр>.service` держит поддерево cgroup для песочницы
(раздел 9). `boba-<экземпляр>.service` — само приложение:

```
[Unit]
After=network-online.target boba-sandbox@mcp.service
Requires=boba-sandbox@mcp.service

[Service]
Slice=boba-mcp.slice
WorkingDirectory=/app/boba-mcp
EnvironmentFile=/app/boba-mcp/conf/boba.env
Environment=BOBA_CGROUP_BASE=/sys/fs/cgroup/user.slice/user-%U.slice/user@%U.service/boba.slice/boba-mcp.slice/boba-sandbox@mcp.service/sandbox
ExecStart=/app/boba-mcp/third/bin/python3 -m boba.mcp_server --config /app/boba-mcp/conf/config.toml --site /app/boba-mcp/conf/site.toml
Restart=always
RestartSec=5
TimeoutStopSec=30
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/app/boba-mcp/data
ProtectHome=read-only
PrivateTmp=yes
MemoryMax=16G
CPUQuota=800%
TasksMax=2048
```

Почему юнит пользовательский, а не системный с `User=boba`. Системный юнит
стартует в `system.slice`. Песочнице нужно переносить процессы вызовов в
поддерево cgroup, принадлежащее пользователю, а ядро разрешает перенос только
под общим предком, в `cgroup.procs` которого у процесса есть запись. У
системного юнита и пользовательского поддерева общий предок — корень иерархии,
запись туда есть только у root. Пользовательский юнит живёт в срезе
`boba-<экземпляр>.slice` рядом с юнитом песочницы, общий предок принадлежит
пользователю, и перенос проходит. Чтобы пользовательские юниты работали без
входа в систему, пользователю включён linger (раздел 2).

`Restart=always` перезапускает приложение после любого завершения, кроме
`systemctl stop`. Сорванный старт — нет связи с базой, не хватает ключа в
site.toml, не прошла проверка cgroup — завершает процесс с ненулевым кодом,
systemd перезапускает его раз в пять секунд, причина видна в журнале. При
остановке приложение успевает погасить зиготы песочницы; через
`TimeoutStopSec` оставшиеся процессы завершает systemd.

Ужесточение (`ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
`NoNewPrivileges`) с песочницей совместимо: приложение пишет только в `data`.

Порт и префикс приложения задаёт `conf/boba.env` (`BOBA_PORT`,
`BOBA_URL_PREFIX`); туда же дописывают другие переопределения `[env]`.

Второй экземпляр того же приложения на одной машине получает своё имя:
`make release APP=mcp INSTANCE=mcp2` и `make install APP=mcp INSTANCE=mcp2`
дают каталог `/app/boba-mcp2` и юниты `boba-mcp2.service`,
`boba-sandbox@mcp2.service`. Дефис в имени экземпляра запрещён: у systemd он
означает вложенность срезов, и каталог cgroup оказался бы в другом месте.

### На какой системе работает дерево релиза

Интерпретатор и колёса в дереве собраны под систему базового образа и ждут её
библиотек: `libssl1.1`, `libffi6`, `libsqlite3-0`, `libbz2-1.0`, `liblzma5`,
`libreadline7`, `libncurses5`, `zlib1g`, `libkrb5-3`, `libgssapi-krb5-2`. На
системе того же семейства их ставят пакетами. На другой системе этих версий
нет, и старт обрывается на `ImportError: libssl.so.1.1: cannot open shared
object file`. Для такого случая релиз собирают с `BUNDLE_OS_LIBS=1`: нужные
библиотеки образа кладутся в `third/lib` дерева, и остаётся одно требование —
glibc машины не старее той, что в образе.

### Обновление

```
make -C build build APP=mcp && make -C build release APP=mcp
systemctl --user stop boba-mcp.service
make -C build install APP=mcp
systemctl --user start boba-mcp.service
```

`install` отказывается работать, пока юнит запущен: заменять код под
работающим процессом нельзя.

## 8. Отладка на хосте

Отладка — это те же приложения, запущенные процессами на машине из исходников
репозитория: код берётся из `packages/`, интерпретатор — из `.venv`,
зависимости — из `runtime/`. От контейнеров она отделена полностью: свои порты,
свой каталог данных, свой экземпляр юнита песочницы.

### Дерево отладки

```
make -C build debug          # все три приложения; APP=<приложение> — одно
```

Цель проверяет машину, ставит и запускает `boba-sandbox@debug.service`, создаёт
каталоги и раскладывает цели запуска VS Code:

```
debug/mcp/
  conf/
    site.toml        пишет администратор
    stand.toml       адреса тестового стенда; нужен только тестам
  data/              пишет только процесс на хосте
.vscode/
  launch.json  tasks.json  python-debug-slice.sh
```

Общий конфиг отладка читает прямо из пакета —
`packages/apps/boba-<приложение>/conf/config.toml`. Свой у неё только
site.toml. Его удобно получить из site.toml дерева compose того же приложения:
секция `[site]` остаётся как есть, в `[env]` меняются значения, перечисленные
в таблице раздела 5. Для boba-mcp, например:

```toml
[env]
    port          = 8651
    url_prefix    = ""
    public_url    = "http://localhost:8651"
    listen_host   = "0.0.0.0"
    cgroup_base   = "/sys/fs/cgroup/user.slice/user-1001.slice/user@1001.service/boba.slice/boba-debug.slice/boba-sandbox@debug.service/sandbox"
    tool_launcher = "process"

    data    = "${env.base}/data"
    sandbox = "${env.base}/../../runtime/sandbox"
    third   = "${env.base}/../../runtime/third"
    models  = "${env.base}/../../runtime/models"
    krb     = "${env.base}/../../compose/mcp/conf/krb"
```

Путь `cgroup_base` для своего пользователя печатает сама цель `make debug`.

Файлы `.vscode` в git не входят (кроме `settings.json`): в `launch.json` стоит
путь cgroup с номером пользователя. Цель создаёт их из образцов
`build/conf/vscode`, подставляя номер; готовые файлы не перезаписывает.

### Цели запуска

| Цель VS Code | Что запускает | Адрес по умолчанию |
|---|---|---|
| `Chainlit: agent` | чат | `http://127.0.0.1:8601/boba-debug/` |
| `MCP: tools service` | сервис инструментов | `http://localhost:8651/health` |
| `Studio: api + workflow & catalog page` | studio | `http://127.0.0.1:8602/boba-studio-debug/` |
| `tool` | один инструмент без сервиса (`boba.runtime.toolcli`) | — |
| `pytest: ...` | тесты | — |

Порты и префиксы — из site.toml отладки. В `launch.json` у каждой цели только
то, чего в конфигурации быть не может: рабочий каталог `debug/<приложение>`,
два аргумента с файлами конфигурации и `PATH` с `LD_LIBRARY_PATH` на
`runtime/third` — там лежат `bwrap`, `fuse2fs` и библиотеки, с которыми собраны
колёса.

То же в терминале:

```
cd debug/mcp
PATH=$PWD/../../runtime/third/bin:$PATH LD_LIBRARY_PATH=$PWD/../../runtime/third/lib \
    ../../.venv/bin/python -m boba.mcp_server \
    --config ../../packages/apps/boba-mcp/conf/config.toml --site $PWD/conf/site.toml
```

VS Code запускает отладку от того пользователя, под которым открыто
соединение, поэтому подключаться к машине нужно сразу тем пользователем, чьи
это деревья.

Отладочный чат ходит в отладочный сервис: в его site.toml стоят
`mcp_scheme = "http"`, `mcp_host = "localhost"`, `mcp_port = 8651`,
`mcp_prefix = ""` и `mcp_issuer_path = "/"`. Имя `localhost` здесь существенно:
сервис объявляет себя издателем токенов под адресом из `public_url`, и клиент
обязан называть его так же. Чтобы отлаживать чат против сервиса в контейнере,
в эти ключи записывают адрес контейнера.

### Режимы process и sandbox

Ключ `tool_launcher` выбирает, как исполняется инструмент.

`process` — обычным дочерним процессом от того же пользователя, без bwrap и
cgroup. В отладке это режим по умолчанию: в тело инструмента можно зайти
отладчиком, файлы пользователя лежат обычным каталогом
`debug/<приложение>/data/workspace/<id>`.

`sandbox` — как в контейнере: bwrap, образ workspace, cgroup на вызов. Включается
значением в site.toml либо переменной `BOBA_TOOL_LAUNCHER=sandbox`. Образы
пользователей при этом лежат в `debug/<приложение>/data/workspace/<id>.ext4`, а
cgroup создаётся в поддереве `boba-sandbox@debug.service` — боевых контейнеров
это не касается.

Для режима sandbox важно, в каком cgroup стартует сам процесс. Процесс,
запущенный из SSH-сессии, живёт в cgroup этой сессии, и перенести своего
потомка в поддерево песочницы ему нельзя (правило общего предка, раздел 9):
старт падает с `CgroupError`. Поэтому интерпретатором у целей с песочницей
служит обёртка `.vscode/python-debug-slice.sh`. Она запускает юнит
`boba-sandbox@debug.service`, если он не запущен, и стартует Python внутри
среза `boba-debug.slice`:

```
systemctl --user start boba-sandbox@debug.service
exec systemd-run --user --scope --quiet --collect --slice=boba-debug.slice -- .venv/bin/python "$@"
```

### Фронт

Страницу workflow в отладке отдаёт vite с горячей перезагрузкой. Его поднимает
задача `web: dev server` (`make -C build web-dev`) в контейнере, а studio
проксирует под своим префиксом; адрес vite стоит в ключе `workflow_page`
site.toml. По умолчанию порт контейнера публикуется на `127.0.0.1:5173`. Демон
без проброса портов так не умеет: там контейнер подключают к сети, доступной с
машины, и называют его имя — `WEB_DEV_NETWORK=<сеть> WEB_DEV_HOST=<имя>`
(постоянно — в `build/conf/local.mk`), а в `workflow_page` пишут
`http://<имя>:5173`.

Статику чата отладка читает прямо из `packages/apps/boba-chainlit/assets`:
правка ассета видна без пересборки, а писать туда приложение не может
(раздел 5, «Вложения чата»).

### Тесты

Тесты запускаются из `debug/chainlit` и берут файлы конфигурации из двух
переменных — пути общего конфига и site.toml:

```
cd debug/chainlit
BOBA_CONFIG_PATH=$PWD/../../packages/apps/boba-chainlit/conf/config.toml \
BOBA_SITE_PATH=$PWD/conf/site.toml \
    ../../.venv/bin/pytest ../../packages/apps/boba-mcp/tests
```

Адреса и учётки живых сервисов, которые нужны только тестам (базы стенда,
Confluence, шрифт для образцов), лежат в `stand.toml` рядом с site.toml.
Тесты, которые сами поднимают приложение, берут свободные порты и свои
каталоги данных, поэтому идут рядом с запущенной отладкой. По умолчанию
отбираются тесты без меток; `-m integration`, `-m ui`, `-m load` запускают
соответствующие наборы.

Пропускаемых тестов в проекте нет. Окружение набора обязательно: без стенда,
keytab, среза cgroup, образа песочницы или браузера тест падает и называет,
чего не хватает (метка `failif` с подписью `skipif`). Случай, неприменимый к
версии сервера, не порождается вовсе: тест получает явный список серверов
стенда. Наборы с общими серверами идут под `-n 8 --dist loadgroup`: группу
xdist набор задаёт в своём conftest, остальным тестам группой служит модуль.

## 9. Песочница инструментов

### Что происходит при вызове

Инструмент — функция в пакете-плагине (`packages/tools/boba-tool-*`). У каждого
плагина свой профиль песочницы: образ корня файловой системы, что из машины
видно внутри, есть ли сеть, лимиты.

При старте приложение поднимает на каждый плагин **зиготу** — заранее
прогретый процесс внутри песочницы, в котором уже импортирован код
инструментов. Вызов не запускает Python заново, а просит зиготу породить
потомка; поэтому вызов занимает десятки миллисекунд. Старт зиготы виден в логе
строкой `zygote[<плагин>] ... ready`.

Песочницу строит `bwrap`: новый user namespace (процесс в нём — root, вне его —
тот же непривилегированный пользователь), свои пространства PID, IPC, UTS и
монтирования, без сети, если профиль её не включает. Корень файловой системы —
образ `runtime/sandbox/plugins/<пакет>/rootfs.ext4`, подключённый только для
чтения. Рабочий каталог пользователя `/workspace` — его личный образ
`data/workspace/<id>.ext4`, который монтирует `fuse2fs`; первый образ
создаётся копией шаблона `workspace.ext4`. Перед запуском тела инструмента
процесс сбрасывает все capabilities, запрещает их возврат (`no_new_privs`) и
закрывает создание вложенных user namespace.

Проверить это можно вызовом `bash` с командой
`id; grep -E 'CapEff|NoNewPrivs' /proc/self/status`: ответ —
`uid=0(root)`, `CapEff: 0000000000000000`, `NoNewPrivs: 1`. Root здесь — только
внутри пространства песочницы.

Бинарники `bwrap` и `fuse2fs` приложение берёт из каталогов, перечисленных в
конфигурации, и проверяет перед запуском: файл и каталог не должны быть
доступны на запись группе и прочим. Иначе подменить их мог бы любой, кто пишет
в этот каталог, — и подмена исполнилась бы с правами приложения.

### Cgroup на вызов

Каждый вызов помещается в собственный cgroup v2 с лимитами профиля: память,
доля процессора, число процессов. Превысивший память вызов убивает ядро, и он
не задевает ни соседние вызовы, ни приложение.

Чтобы создавать cgroup без root, нужны два условия. Первое: у приложения есть
каталог в иерархии cgroup, куда оно может писать. Второе вытекает из правила
ядра: процесс можно перенести из одного cgroup в другой, только если у
переносящего есть запись в `cgroup.procs` их общего предка. Значит, само
приложение и каталог для вызовов должны лежать под одним предком, принадлежащим
тому же пользователю.

Оба условия выполняет пользовательский юнит `boba-sandbox@<экземпляр>.service`
(шаблон `build/conf/boba-sandbox@.service`):

```
[Service]
Slice=boba-%i.slice
Delegate=cpu memory pids
DelegateSubgroup=holder
ExecStart=/usr/bin/sleep infinity
ExecStartPost=... echo "+cpu +memory +pids" > cgroup.subtree_control; mkdir -p sandbox ...
```

`Delegate=` говорит systemd: поддерево этого юнита принадлежит ему самому,
systemd в него не вмешивается и передаёт перечисленные контроллеры. Процесс
`sleep` нужен только затем, чтобы юнит существовал; `DelegateSubgroup` убирает
его в подгруппу `holder`, потому что ядро не позволяет держать процессы в
cgroup, у которого включены контроллеры для потомков. `ExecStartPost` включает
контроллеры и создаёт каталог `sandbox` — в нём приложение и заводит cgroup
вызовов. Полный путь:

```
/sys/fs/cgroup/user.slice/user-<uid>.slice/user@<uid>.service/boba.slice/boba-<экземпляр>.slice/boba-sandbox@<экземпляр>.service/sandbox
```

Приложение запускается в том же срезе `boba-<экземпляр>.slice`:

- контейнер — строкой `cgroup_parent: boba-<приложение>.slice` в compose-файле;
  каталог `sandbox` приходит в него томом (`BOBA_SANDBOX_CGROUP` в `.env`), а
  `cgroup_base` в site.toml называет точку монтирования;
- юнит приложения — строкой `Slice=`; путь он получает переменной
  `BOBA_CGROUP_BASE`;
- отладка — обёрткой `python-debug-slice.sh` и ключом `cgroup_base` site.toml.

Для контейнера есть ещё одна тонкость. Процесс в нём идёт от пользователя
1000, который на машине отображён в номер из subuid, а каталог `sandbox`
принадлежит пользователю машины. Поэтому юнит отдаёт каталог и нужные файлы
`cgroup.procs` группе с номером 1000 внутри пространства демона
(`Environment=SANDBOX_GID=1000`): смена группы выполняется через
`unshare --map-auto`, для чего и нужен диапазон subgid. На машине без subgid —
там, где Docker нет и приложение работает юнитом, — этот шаг пропускается.

При старте приложение проверяет каждый профиль пробным переносом процесса и
пишет `sandbox cgroup: profile '<имя>' ok in <каталог>`. Отказ прерывает старт
ошибкой `CgroupError` с причиной.

**Юнит песочницы нельзя перезапускать и останавливать, пока работает его
приложение.** Перезапуск удаляет каталог `sandbox` и создаёт новый с тем же
именем; у работающего приложения (а в контейнере — в точке монтирования)
остаётся старый, уже удалённый, и каждый вызов инструмента падает с
`CgroupError`. Порядок всегда один: остановить приложение, перезапустить юнит,
запустить приложение (контейнер — пересоздать). По той же причине цели сборки
не трогают запущенный экземпляр: обновлённый шаблон юнита применяется при его
следующем старте.

### Диагностика

- В логе нет `zygote[...] ready` для плагина — в строке `zygote[...] failed`
  стоит хвост stderr `bwrap`; типовые причины — в разделе 12.
- Сколько вызовов идёт сейчас: каталоги `run-<pid>-<id>` в каталоге `sandbox`
  юнита; у каждого — `memory.current`, `pids.current`, `memory.events`.
- Вывод вызовов сервис пишет в `data/tool-logs/<пользователь>/<запуск>/`: по
  файлу на канал (`tool_stdout`, `tool_stderr`, `tool_result`) и `meta.json`.
- Образ пользователя можно осмотреть, смонтировав копию:
  `runtime/third/bin/fuse2fs -o ro,fakeroot <копия>.ext4 <каталог>`, затем
  `fusermount3 -u <каталог>`. Файлы внутри образа принадлежат пользователю 0,
  часть каталогов закрыта режимом `0700`; опция `fakeroot` даёт их прочесть.

## 10. Эксплуатация

**Журналы.** Контейнеры пишут в stdout: `docker logs -f <контейнер>`. Юниты —
в журнал пользователя: `journalctl --user -u boba-<экземпляр>.service`.
Запросы к языковой модели приложение складывает в `data/dump`, если это
включено в `[http].dump` общего конфига; каталог растёт, его чистят по
возрасту.

**Что и в каком порядке перезапускать.**

| Что изменилось | Что сделать |
|---|---|
| site.toml, `.env`, compose-файл | пересоздать контейнер (`up -d --force-recreate`) либо `systemctl --user restart` юнита приложения |
| образ приложения | пересоздать контейнер |
| образы плагинов в `runtime/sandbox` | пересобрать образ boba-mcp и пересоздать его контейнер; контейнер studio пересоздать |
| шаблон юнита песочницы | остановить приложение, `systemctl --user restart boba-sandbox@<экземпляр>`, запустить приложение |
| перезагрузка машины | ничего: юниты песочницы стартуют раньше демона Docker, контейнеры поднимает политика `restart: unless-stopped` |

После перезапуска boba-mcp чат переподключается к нему сам, при следующем
обращении пользователя.

**Резервное копирование.** Состояние приложений лежит в трёх местах:

- база PostgreSQL — история чатов, пользователи, соединения (секреты в них
  зашифрованы ключом `database_encryption_key`), каталог, база знаний;
- `data/workspace/*.ext4` сервиса boba-mcp и studio — файлы пользователей.
  Копировать образ лучше при остановленном приложении либо когда у
  пользователя нет идущих вызовов: образ смонтирован только на время вызова;
- `conf/site.toml` и `conf/krb` — без них приложение не поднять, а
  `database_encryption_key` и `auth_secret` нельзя восстановить иначе, чем из
  копии.

`data/tool-logs`, `data/krb`, `data/dump`, `data/files` восстанавливать не
нужно: это журналы и кэши.

Образ workspace — разреженный файл: его объявленный размер (по умолчанию
гигабайт) намного больше занятого места. Копировать его нужно с сохранением
разреженности, иначе копия каждого образа займёт полный гигабайт. У `tar` это
ключ `-S`.

Вторая особенность — владельцы. Файлы в `compose/<приложение>/data` принадлежат
пользователю контейнера, на машине это номер из subuid. Администратор читает
их через группу, но восстановленные им файлы получили бы владельцем его
самого, и контейнер не смог бы в них писать. Поэтому при rootless-демоне и
копию, и восстановление делают в user namespace с тем же отображением, что у
демона (`unshare --user --map-root-user --map-auto`, как при расстановке
владельцев в разделе 6): там `tar` видит пользователя контейнера под его
номером 1000 и возвращает его файлам.

```
cd compose/mcp
unshare --user --map-root-user --map-auto \
    tar -cSf /backup/boba-mcp-data.tar --exclude=data/tool-logs --exclude=data/krb --exclude=data/dump data
tar -cf /backup/boba-mcp-conf.tar conf
```

Архив с `conf` содержит секреты и keytab: хранить его так же закрыто, как сам
каталог. Восстановление — при остановленном приложении, в каталог без прежнего
`data`, с ключом `-p`, чтобы вернулись режимы каталогов:

```
unshare --user --map-root-user --map-auto \
    tar -xpSf /backup/boba-mcp-data.tar -C compose/mcp
```

При обычном, не rootless-демоне пользователь контейнера — тот же номер на
машине, и обе команды выполняет root без `unshare`.

Проверить копию можно, не трогая рабочие данные: распаковать во временный
каталог, сравнить контрольные суммы (`sha256sum`) образов с исходными и
смонтировать распакованный образ на чтение, как описано в разделе 9. Базу
копируют средствами PostgreSQL (`pg_dump` либо копия уровня кластера); копия
базы и копия `database_encryption_key` должны быть от одной установки, иначе
секреты соединений не расшифруются.

**Чистка.** `make -C build prune` делает четыре вещи: удаляет промежуточные
образы сборки (`boba-plugin*`, `boba-sandbox*`, `boba-bwrap*`, `boba-fuse2fs*`);
удаляет все теги образов приложений, кроме текущей версии и `latest`; удаляет
образы без тега; урезает кэш сборки до `PRUNE_KEEP` (по умолчанию 20 ГБ).
Образ, под которым работает контейнер, Docker удалить не даст, он останется.
Вместе с прочими тегами уйдёт и метка `<версия>-prev`, оставленная для отката
(раздел 6): пока откат может понадобиться, `prune` не запускают либо сначала
переносят метку на имя вне шаблона, например `docker tag boba-mcp:<версия>-prev
keep/boba-mcp:<версия>-prev`. Образы workspace пользователей и журналы вызовов
сами не удаляются.

**Нездоровый контейнер.** Docker помечает контейнер `unhealthy`, но не
перезапускает его: политика `restart` срабатывает только на завершение
процесса. Если нужен автоматический перезапуск зависшего приложения, его
делает внешний сторож — таймер, который раз в несколько минут перезапускает
контейнеры в состоянии `unhealthy`.

## 11. Безопасность: от чего защищает каждое ограничение

Главная угроза — тело инструмента. Команду для `bash` или запрос к базе
составляет языковая модель по тексту пользователя и по содержимому документов,
которые она прочла; считать эти команды доверенными нельзя. Вторая угроза —
сам пользователь чата, который может пытаться добраться до чужих файлов и
соединений. Третья — уязвимость в приложении.

| Ограничение | От чего защищает |
|---|---|
| песочница bwrap: свой корень только для чтения, свои пространства имён | тело инструмента не видит файлов приложения, конфигурации, keytab и чужих процессов |
| сброс capabilities и `no_new_privs` в теле, запрет вложенных user namespace | внутри песочницы нельзя вернуть себе права и построить новую песочницу для обхода |
| сеть только у плагинов, которым она нужна | `bash` и чтение документов не могут ходить в сеть |
| личный образ workspace на пользователя | вызовы одного пользователя не видят файлов другого |
| cgroup на вызов | вызов не может занять всю память и процессор и уронить приложение |
| проверка владельца и прав `bwrap` и `fuse2fs` | подмена бинарника не исполнится с правами приложения |
| контейнер от 1000:1000, `cap_drop: ALL`, `no-new-privileges`, seccomp | пробитая песочница даёт процесс без прав и без владения кодом приложения |
| rootless-демон Docker либо пользовательские юниты | пробитый контейнер или приложение — это непривилегированный пользователь машины, не root |
| `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp` у юнита | приложение пишет только в свой каталог данных |
| секреты и адреса только в site.toml вне git | утечка репозитория не раскрывает ни паролей, ни устройства сети |
| соединение приходит в сервис запечатанным под конкретного пользователя и срок | сервис инструментов не хранит чужих паролей, перехваченное значение бесполезно другому |
| секрет клиента и подписанное утверждение между чатом и сервисом | к сервису инструментов нельзя обратиться от имени пользователя, не зная обоих секретов |

Чего эти меры не дают. Инструмент с сетью и выданным ему соединением делает в
базе всё, что разрешено учётке этого соединения: права самих учёток —
ответственность администратора баз. Ядро общее у песочницы, контейнера и
машины: уязвимость ядра, достижимая без привилегий, обходит все слои сразу,
поэтому ядро обновляют.

## 12. Если что-то пошло не так

**`InterpolationKeyError: Interpolation key 'site.x' not found`, ниже строки
`full_key: ...` и `object_type=dict`.** В site.toml нет ключа, на который
ссылается общий конфиг; `full_key` называет место в общем конфиге, где стоит
ссылка. Сервис boba-mcp печатает ошибку одной строкой с префиксом `boba-mcp
failed:`, чат и studio — последней строкой трассировки Python. Перечень
ключей — `make -C build site-keys APP=<приложение>`.

**`ConfigLayoutError: site file ...: expected only sections ['env', 'site'],
got also [...]; the structure of the application is described in the common
config alone`.** В site.toml попала секция устройства приложения. Её место — в
общем конфиге пакета; в site.toml остаются только значения, на которые он
ссылается.

**`ConfigLayoutError: config files: site expects an existing toml file, got
...`.** Неверный путь в `--site` либо site.toml ещё не написан. То же сообщение
со словом `config` вместо `site` — неверный путь в `--config`.

**`The "BOBA_USER" variable is not set. Defaulting to a blank string.`** от
`docker compose`. Нет `.env` либо в нём не хватает строки; `make -C build dev
APP=<приложение>` создаст файл или назовёт недостающую переменную.

**`bwrap: setting up uid map: Operation not permitted`** в хвосте строки
`zygote[<плагин>] <номер> failed: attempt failed: ...; stderr tail: ...`.
Процесс приложения идёт от пользователя 0 без `CAP_SETFCAP` — так
бывает, если в `.env` записать `BOBA_USER=0:0`. Вернуть `1000:1000`
(раздел 6).

**`UntrustedBinaryError: trusted binaries: .../third/bin is group-writable
(mode ...)`.** Каталог с `bwrap` и `fuse2fs` открыт на запись группе. Исправить:
`chmod -R go-w runtime/third`. Если каталог открыт всем, в тексте стоит
`world-writable`. Вариант той же ошибки — `trusted binaries: fuse2fs not found
in ...`: ключ `third` в site.toml указывает не туда либо `make sandbox` не
выполнялся.

**`CgroupError: sandbox profile 'bash': cgroup: cannot create base ...:
[Errno 13] Permission denied: '...'; the directory must live under a cgroup v2
subtree delegated to this user`.** Каталог из `cgroup_base` недоступен: не запущен юнит
`boba-sandbox@<экземпляр>`, в `.env` неверный `BOBA_SANDBOX_CGROUP`, либо
отладочный процесс запущен не через обёртку и живёт в cgroup SSH-сессии.
`CgroupError` на каждом вызове у давно работающего приложения — юнит песочницы
перезапускали под ним (раздел 9).

**`CgroupError: sandbox profile '...': cgroup: cannot move a child into ...:
... No such file or directory ...; the application itself must run inside the
delegated subtree ...`** при старте приложения в контейнере. Ядро отвергло
перенос процесса в поддерево песочницы: иерархия cgroup смонтирована с
`nsdelegate` (раздел 2). Тот же текст с `Permission denied` — приложение
запущено вне среза `boba-<экземпляр>.slice`: в `.env` неверный
`BOBA_SANDBOX_CGROUP` либо контейнер поднят без `cgroup_parent` (раздел 6).

**`clone3 into cgroup refused (... Function not implemented), falling back to
fork`** в логе на каждом вызове. Не ошибка: seccomp-профиль контейнера не
пропускает `clone3`, песочница переходит на запасной путь через `fork`, вызов
выполняется.

**`PostgresError: ... couldn't get a connection after 5.00 sec`, затем
`ServerStartError: ... the application startup failed`**, перед ними строки
`error connecting in 'pool-1'`. Число секунд — `pool_timeout` из общего
конфига. База недоступна: неверный адрес, сеть
контейнера не доходит до неё, либо вход по Kerberos не удался — тогда выше в
логе нет строки `kerberos: TGT ... from ...keytab`. Процесс завершается с кодом
1, и его перезапускает политика контейнера или юнита.

**`Credentials cache permissions incorrect (filename: .../data/krb/krb5cc_http)`.**
В каталог данных пишут два процесса от разных пользователей — контейнер и
процесс на хосте. У каждого случая запуска должен быть свой `data` (раздел 3).

**`ImportError: libssl.so.1.1: cannot open shared object file: No such file or
directory`** у юнита.
Дерево релиза поставлено на систему без библиотек базового образа
(раздел 7).

**`External data path escapes model directory`** от onnxruntime при загрузке
модели. Файл весов рядом с моделью — ссылка, ведущая за пределы её каталога:
так выглядит неизменённый кэш Hugging Face. Сценарий загрузки моделей заменяет
ссылки файлами; для кэша, положенного вручную, то же делает
`.venv/bin/python build/scripts/fetch_models.py links runtime/models/fastembed`.

**`EACCES: permission denied ... node_modules`** от npm при сборке фронта.
Контейнер node пишет в каталог исходников от пользователя, которому тот
недоступен. Сборка сама выбирает пользователя и группу: при rootless-демоне —
`0:0` (он отображается в пользователя машины), при обычном — номера
пользователя и группы машины. Ошибка означает,
что каталоги `node_modules` или `assets` остались от сборки под другим
пользователем: их удаляют и собирают заново.

**`== boba-web-dev: vite did not answer at http://127.0.0.1:5173/... in 180s
==`** от `make`. Демон не публикует порты на машину; см. раздел 8, «Фронт».

**Чат отвечает, но инструментов сервиса нет; в логе `mcp server boba_general is
unavailable: ...`.** Сервис не запущен либо адрес в ключах `mcp_*` site.toml чата не
совпадает с `public_url` сервиса. Сообщение `Authorization server metadata
issuer mismatch` говорит о втором: имя, схема, порт и путь издателя должны
совпадать буква в букву.

## 13. Nginx перед boba

Приложения развёрнуты на своих префиксах (например, `/boba/`, `/boba-studio/`,
`/boba-mcp/`). Чат и studio ожидают путь целиком, без срезания префикса: его
задаёт ключ `url_prefix` site.toml. Сервис boba-mcp слушает без префикса, а
префикс входит в его `public_url`, поэтому nginx срезает его сам. Nginx перед
приложениями должен уметь три вещи: пропускать веб-сокеты, не буферизовать
потоковые ответы и принимать заголовки крупнее дефолтных восьми килобайт.

### Конфигурация

```nginx
server {
  listen 443 ssl;
  server_name boba.example.com;

  ssl_certificate     /etc/nginx/tls/boba.example.com.crt;
  ssl_certificate_key /etc/nginx/tls/boba.example.com.key;

  large_client_header_buffers 4 32k;
  port_in_redirect off;

  location /boba/ {
    resolver 127.0.0.53 valid=5s;
    set $chainlit http://boba-chainlit.internal:8501;
    proxy_pass $chainlit;

    include /etc/nginx/conf.d/options/boba-headers.conf;
  }

  location /boba-studio/ {
    resolver 127.0.0.53 valid=5s;
    set $studio http://boba-studio.internal:8502;
    proxy_pass $studio;

    include /etc/nginx/conf.d/options/boba-headers.conf;
  }

  location /boba-mcp/ {
    resolver 127.0.0.53 valid=5s;
    set $mcp http://boba-mcp.internal:8650;
    rewrite ^/boba-mcp/(.*)$ /$1 break;
    proxy_pass $mcp;

    include /etc/nginx/conf.d/options/boba-headers.conf;
  }

  location ~ ^/\.well-known/(oauth-protected-resource|oauth-authorization-server|openid-configuration)/boba-mcp(/|$) {
    resolver 127.0.0.53 valid=5s;
    set $mcp http://boba-mcp.internal:8650;
    proxy_pass $mcp;

    include /etc/nginx/conf.d/options/boba-headers.conf;
  }
}
```

`conf.d/options/boba-headers.conf`:

```nginx
proxy_http_version 1.1;
proxy_cache_bypass $http_upgrade;

proxy_set_header Upgrade           $http_upgrade;
proxy_set_header Connection        "upgrade";
proxy_set_header Host              $http_host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host  $http_host;
proxy_set_header X-Forwarded-Port  $server_port;

proxy_buffering         off;
proxy_request_buffering off;

proxy_buffer_size       32k;
proxy_buffers           8 32k;
proxy_busy_buffers_size 64k;

proxy_read_timeout 86400s;
```

### Параметры

- **`proxy_http_version 1.1` и заголовки `Upgrade`/`Connection`.** По умолчанию
  nginx ходит к бэкенду по HTTP/1.0, где нет механизма Upgrade. Без этих
  строк веб-сокет чата не поднимется: приложение ответит ошибкой рукопожатия.
- **`proxy_cache_bypass $http_upgrade`.** Запрос на смену протокола не должен
  отдаваться из кэша.
- **`Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`.**
  Приложение строит абсолютные ссылки и редиректы по этим заголовкам. Без
  `X-Forwarded-Proto` редиректы уйдут на `http://` и войдут в цикл. `$http_host`
  вместо `$host`: первый передаёт заголовок как есть, второй отбрасывает порт.
  `X-Forwarded-Port` в примере равен порту, на котором слушает nginx. Если
  снаружи сайт открыт на другом порту — перед nginx стоит ещё один прокси или
  мультиплексор, и nginx слушает, например, 8443, а клиент приходит на 443, —
  в заголовок пишут внешний порт числом: `proxy_set_header X-Forwarded-Port 443;`.
- **`X-Real-IP`, `X-Forwarded-For`.** Адрес клиента для логов и ограничений.
- **`proxy_buffering off`, `proxy_request_buffering off`.** Чат отдаёт ответ
  модели потоком, и каждая порция должна доезжать сразу. С буферизацией
  ответ приходит рывками или застревает до конца хода. Выключенная
  буферизация запроса нужна, чтобы загрузка файла шла в приложение сразу.
- **`proxy_buffer_size 32k`, `proxy_buffers 8 32k`, `proxy_busy_buffers_size 64k`.**
  JWT входа несёт билет доменной аутентификации и едет тремя cookie общим
  объёмом около десяти килобайт. Дефолтные буферы рассчитаны на восемь
  килобайт заголовков ответа, и вход через SSO падает с 400 или 431.
- **`large_client_header_buffers 4 32k`.** То же самое для запроса от браузера.
  Стоит на уровне `server`; если на этом же адресе и порту несколько блоков
  `server`, директиву ставят в тот, что выбран по умолчанию (`default_server`):
  строку запроса nginx читает раньше, чем выбирает сервер по имени.
  Нужны обе директивы: поднять одну и оставить
  другую даёт ту же ошибку с другой стороны.
- **`port_in_redirect off`.** Запрос `/boba` без завершающего слэша nginx сам
  отвечает редиректом на `/boba/` и по умолчанию подставляет в адрес порт,
  на котором слушает. Если nginx стоит за другим прокси или stream-мультиплексором
  и слушает не 443, редирект уведёт клиента на закрытый снаружи порт.
- **`proxy_read_timeout 86400s`.** Веб-сокет чата и длинные ходы модели не
  должны обрываться по таймауту простоя.
- **`resolver` и `proxy_pass` через переменную.** Nginx резолвит имя из
  `proxy_pass` один раз при старте. Если адрес приложения сменился, он
  ходит на старый и отдаёт 502 до перезагрузки. С переменной имя резолвится
  на каждый запрос через указанный DNS с кэшем в пять секунд; в примере это
  локальный systemd-resolved, подставьте свой. Если приложение задано
  IP-адресом, пара `resolver`/`set` не нужна, `proxy_pass` пишется напрямую.
  Адрес в `proxy_pass` записан без пути, поэтому nginx передаёт приложению
  путь запроса целиком, вместе с префиксом. Для чата и studio это и нужно.
  Срезать префикс привычной записью `proxy_pass http://адрес/;` с переменной
  нельзя: путь из переменной nginx подставляет вместо всего пути запроса.
  Поэтому там, где префикс надо убрать, стоит `rewrite`.
- **Два `location` у boba-mcp.** Сервис слушает без префикса, поэтому первый
  блок префикс срезает строкой `rewrite`. Второй нужен клиентам MCP: метаданные
  авторизации они ищут от корня хоста, по пути
  `/.well-known/<документ>/boba-mcp`, и этот путь уходит в сервис как есть.
  Без второго блока клиент не находит сервер авторизации и не подключается.

### Диагностика

| Симптом | Причина | Что смотреть |
|---|---|---|
| 502 после смены адреса приложения | адрес закэширован при старте | пара `resolver`/`set` в `location` |
| Веб-сокет не поднимается | нет `Upgrade`/`Connection` или два заголовка `Connection` в блоке | `proxy_set_header` в этом `location` |
| Ответ модели приходит рывками | включена буферизация или gzip для пути | `proxy_buffering`, `gzip_types` |
| 400 или 431 после входа через SSO | заголовки не помещаются в буферы | `large_client_header_buffers`, `proxy_buffer_size` |
| Редиректы уходят на `http://` | нет `X-Forwarded-Proto` | заголовки в `boba-headers.conf` |
| Редирект на `/boba/` уходит с чужим портом | nginx слушает не 443 и подставляет свой порт | `port_in_redirect off` в `server` |
| Приложение видит всех клиентов как один адрес | `X-Real-IP` не передан или перед nginx ещё один прокси | `X-Real-IP`, `set_real_ip_from` |

## 14. Секреты, вход и роли

Секреты лежат в секции `[site]` файла site.toml каждого приложения; общий
конфиг подставляет их ссылками в рабочие секции. `auth_secret` и
`database_encryption_key` обязаны совпадать у chainlit и studio: chainlit
выдаёт cookie входа, studio её проверяет; оба приложения читают одну таблицу
соединений. `proxy_secret` и `[site.mcp_client].secret` обязаны совпадать у
chainlit и boba-mcp.

Рабочие секции, о которых идёт речь ниже (`[session]`, `[auth.*]`, `[roles]`),
лежат в общем конфиге пакета и одинаковы на всех машинах; site.toml даёт им
только значения.

### `auth_secret`

Куда подставляется: `[session].auth_secret`.

Что делает:

- подписывает JWT входа (HS256), который едет в cookie `access_token`;
- запечатывает kerberos-билет пользователя внутри этого JWT (ключ выводится
  из секрета через HKDF-SHA256, шифр Fernet);
- уходит в chainlit как `CHAINLIT_AUTH_SECRET` для его собственных сессий.

Требования: непустая строка. Формат не проверяется, но секрет должен быть
случайным и длинным, не короче 32 байт энтропии.

Сгенерировать:

```
openssl rand -base64 48
```

или

```
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Смена секрета: все выданные cookie становятся недействительными, пользователи
входят заново. Данные не теряются. Менять одновременно в обоих приложениях,
иначе studio будет отвергать cookie chainlit.

### `proxy_secret` и секрет клиента

Куда подставляются: `[auth.proxy].secret` у всех трёх приложений,
`[mcp_auth.boba].secret` и `[mcp_auth.boba].client_secret` у чата,
`[mcp.clients.boba-chat].secret` у boba-mcp.

Что делают. Секретом клиента чат представляется сервису boba-mcp как
зарегистрированный клиент `boba-chat`. Ключом `proxy_secret` он подписывает
утверждение «этот запрос идёт от такого-то пользователя с такими-то ролями»;
сервис проверяет подпись и исполняет инструмент от имени этого пользователя.
Тем же ключом подписывают вход внешние сайты (вход proxy ниже).

Сгенерировать: `openssl rand -hex 32` для каждого. Смена — одновременно в
site.toml чата и сервиса, затем перезапуск обоих; сессий пользователей она не
затрагивает.

### `database_encryption_key`

Куда подставляется: `[connections].encryption_key`.

Что делает: шифрует секреты сохранённых соединений пользователей (пароли,
токены, keytab) перед записью в таблицу соединений. Шифр Fernet, значение в
базе хранится с префиксом `enc:v1:`.

Требования: ровно 32 байта в стандартном base64 (44 символа с `=` на
конце). Проверяется при старте: другая длина или не-base64 останавливают
приложение с ошибкой `[connections].encryption_key: expected 32 bytes in
base64, got ...` — дальше сказано, что не так: `got 24 bytes` либо `got a value
that does not decode`. Алфавит именно стандартный, с `+` и `/`: ключ в
urlsafe-записи (с `-` и `_`, как печатает `Fernet.generate_key()`) отвергается.
Пустое значение при старте проходит, и ошибка `[connections].encryption_key is
not set` появляется позже, когда приложение открывает хранилище соединений.

Сгенерировать:

```
openssl rand -base64 32
```

или

```
python3 -c "import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

Смена ключа: сохранённые секреты соединений перестают расшифровываться,
инструмента перешифрования нет. Пользователям придётся заново ввести
пароли и ключи в своих соединениях. Ключ генерируется один раз при
установке и дальше только переносится между релизами.

### `generation`

Где лежит: `[session].generation` каждого приложения.

Что делает: поколение сессий. Значение попадает в metadata входа и в
токен, при чтении токена сверяется с текущим. Токен другого поколения
отвергается: ответ `401`, страница уходит на вход. Chainlit при этом сам
снимает устаревшую cookie в браузере; studio только отвечает `401`, cookie
заменит следующий вход.

Два режима:

- пустая строка: при каждом старте процесса генерируется случайное значение,
  рестарт приложения разлогинивает всех его пользователей;
- заданное значение: используется как есть и переживает рестарты; менять его
  вручную, чтобы разлогинить всех.

Chainlit выдаёт cookie входа, studio её проверяет. Если приложения должны
принимать токены друг друга, `generation` у них задаётся одинаковой строкой.
Пустое значение у обоих означает две независимые сессии: вход в чат не даёт
входа в studio. Токены партнёров, выпущенные напрямую по `auth_secret`,
поколения не несут и отвергаются: для них есть вход proxy.

### Токен входа (JWT)

Итог любого входа — один JWT в cookie с именем из `[session].cookie` (обычно
`access_token`). Токен состоит из трёх частей через точку: заголовок,
полезная нагрузка, подпись HS256 секретом `[session].auth_secret`. Первые две
части — обычный base64url, то есть **тело токена читается кем угодно без
всякого ключа**; подпись защищает от подделки, а не от чтения.

Поля верхнего уровня полезной нагрузки называются claims. Наши:

| Поле | Что значит |
|---|---|
| `identifier` | логин в нижнем регистре, ключ строки users |
| `display_name` | логин как набран, для интерфейса |
| `metadata` | всё, что вход знает о себе (таблица ниже) |
| `exp` | до какого момента токен годен, unix-время |
| `iat` | когда выпущен |
| `since` | когда начался первый вход этой сессии; по нему считается потолок продления. В токене парольной формы chainlit `/login` его нет до первого продления: началом сессии тогда считается это продление |

Внутри `metadata`:

| Ключ | Что значит |
|---|---|
| `provider` | каким провайдером выпущен вход: `KerberosAuth`, `LdapAuth`, `LocalAuth`, `ProxyAuth` |
| `principal` | принципал kerberos-входа |
| `roles` | роли, посчитанные при входе |
| `profiles` | профили, доступные входу |
| `profile` | профиль, выбранный входом для новых чатов; только у proxy с заголовком `selected` |
| `sso_ticket` | делегированный kerberos-билет под шифром |
| `generation` | поколение сессий, при котором выпущен вход |

Целиком токен выглядит так:

```json
{
  "identifier": "ivanov",
  "display_name": "Ivanov",
  "metadata": {
    "provider": "KerberosAuth",
    "principal": "ivanov@EXAMPLE.COM",
    "roles": ["analyst"],
    "profiles": ["default"],
    "sso_ticket": "gAAAAABm…",
    "generation": "3f9c1a…"
  },
  "exp": 1757500000,
  "iat": 1757496400,
  "since": 1757490000
}
```

Роли и профили лежат в токене, а не берутся из базы на каждый запрос: правки
`[roles]` и `[profiles.X].roles` действуют с нового входа, у kerberos — с
ближайшего обновления сессии.

Секретное в токене одно — `sso_ticket`, и он зашифрован Fernet на ключе,
выведенном из `auth_secret`: в теле токена видна только непрозрачная строка
`gAAAAAB…`, открыть её может лишь процесс с тем же секретом. Ничего другого
секретного в токен не кладётся. Настройки пользователя (`llm`,
`studio_profile`) в токен не едут — они живут в колонке `metadata` строки
users.

Cookie ставится с `HttpOnly`, то есть JavaScript страницы её не прочитает, но
владелец браузера видит её в devtools. Kerberos-билет делает токен длинным,
поэтому cookie больше 3000 символов режется на `access_token_0`,
`access_token_1` и так далее и собирается обратно при чтении; в браузере видны
несколько cookie вместо одной — это норма.

Посмотреть содержимое токена:

```
python3 -c "import base64,json,sys; p=sys.argv[1].split('.')[1]; print(json.dumps(json.loads(base64.urlsafe_b64decode(p+'='*(-len(p)%4))),indent=2,ensure_ascii=False))" <токен>
```

Токен отвергается в четырёх случаях: истёк `exp`, подпись не сходится с
`auth_secret`, тело не разбирается, поколение не совпадает с текущим
(см. `generation`). Во всех случаях ответ `401`, страница уходит на вход.
Причина названа в теле ответа studio (`sign-in token rejected as generation:
...`, `... as signature: ...`); chainlit на любую из них отвечает `Invalid
authentication token`. Cookie сервер снимает сам только в одном случае —
chainlit при чужом поколении; в остальных её заменяет следующий вход.

### Срок токена и продление сессии

Сроки задаёт секция `[session]` общего конфига, одинаковая у chainlit и studio,
потому что токен одного приложения принимает другое:

| Параметр | Что значит |
|---|---|
| `session_ttl_sec` | срок одного токена: `exp = iat + session_ttl_sec`; столько же живёт cookie (`Max-Age`) |
| `session_max_sec` | потолок сессии от первого входа: пока `now - since < session_max_sec`, токен перевыпускается без нового входа; не меньше `session_ttl_sec` |

Сколько осталось, любой клиент считает сам по телу токена, ключ для этого не
нужен: `exp - now` секунд до истечения токена, `since + session_max_sec - now`
до конца сессии. Отдельного маршрута, который отдаёт срок, нет: `/user` и
`/me` возвращают пользователя, а не сроки.

Продление устроено так. Сторож сессий в каждом процессе раз в
`[cluster].heartbeat_sec` обходит живые сокеты и, если до `exp` осталось
меньше 300 секунд, шлёт странице этого пользователя сигнал по шине. Страница
chainlit или studio по сигналу зовёт `POST /auth/refresh` с cookie и меткой
своего запроса (см. ниже). Для парольного и proxy-входа сервис перевыпускает
JWT: те же claims, новый `exp` и `iat`, прежний `since`. Для kerberos-входа
JWT так не перевыпускается — страница проходит повторный SPNEGO-обмен, чтобы
обновились билет и роли. Ответ `204` и новая cookie, живые сокеты пользователя
получают новый токен без переподключения.

Правила отказа, ответ `403`, страница уходит на вход:

- токен истёк больше 300 секунд назад (grace): вкладка, проспавшая сигнал,
  ещё успевает обменяться, закрытая — нет;
- с момента `since` прошло `session_max_sec` и больше: сессия исчерпана,
  нужен новый вход. Правило действует на парольный и proxy-вход; у kerberos
  каждый SPNEGO-обмен — новый вход с новым `since`, и потолком служит срок
  жизни доменной учётки и её билетов;
- у запроса нет метки своего запроса.

Сигнал идёт только открытым страницам через сокет. Сторонний сервис, который
держит токен сам, никакого сигнала не получает: он обязан следить за `exp` и
звать `/auth/refresh` заранее, пример в разделе про curl.

Проверить, что фронт и подключённые сервисы переживают истечение, проще на
коротком сроке. Удобнее всего делать это в отладке на хосте: общий конфиг она читает
прямо из пакета, и временная правка `[session]` в
`packages/apps/boba-<приложение>/conf/config.toml` действует с перезапуска
процесса (в git её не отправляют):

```toml
session_ttl_sec = 420
session_max_sec = 1800
```

Порог сигнала 300 секунд зашит в код, поэтому при `session_ttl_sec = 420`
сторож попросит обновление на 120-й секунде после выпуска; при сроке меньше
300 сигнал уйдёт сразу после входа, и настоящего истечения не увидеть.
`session_max_sec = 1800` через полчаса даёт сценарий «сессия исчерпана».
Правка требует рестарта обоих приложений, а при пустом `generation` рестарт
разлогинивает всех.

### Метка своего запроса (`x-boba-request`)

Маршруты, которые меняют сессию, требуют заголовок `x-boba-request: 1`; без
него ответ `403`. Это `/auth/refresh` у обоих приложений и `/auth/login`,
`/auth/logout` в studio; парольная форма chainlit `/login` и его `/logout` —
маршруты самого chainlit, метку они не проверяют. Значение постоянное, к
пользователю и секретам не привязано.

Это защита от подделки межсайтового запроса (CSRF). Браузер прикладывает cookie
входа к любому запросу на домен boba, кем бы он ни был порождён: чужой сайт
может отправить форму на `/auth/logout` или `/auth/login` с чужим паролем, и
запрос придёт с cookie пользователя. Атрибут `SameSite` этот путь закрывает не
всегда: chainlit работает с `cookie_samesite = "none"` ради виджета copilot в
`iframe`. Заголовок закрывает его независимо от cookie: форма и навигация
своих заголовков задавать не умеют, а `fetch` с нестандартным заголовком
браузер сначала проверяет preflight-запросом `OPTIONS` и без разрешения CORS от
boba основной запрос не отправляет. Поставить заголовок и получить cookie может
только скрипт со страницы самого boba или origin из списка `allow_origins`.
Отсюда же и требование к этому списку: `*` разрешает заголовок всем и защиту
обнуляет.

Вне браузера ограничений нет: curl и бэкенд ставят заголовок сами, и для них
он просто обязательная константа на маршрутах выше. На чтение данных метка не
нужна.

### Вход и запросы с токеном: примеры curl

Адреса: `B` — chainlit с префиксом, например `https://boba.company.ru/boba`,
`S` — api studio, например `https://boba.company.ru/boba-studio/api/v1`.
Cookie входа во всех примерах сохраняется в `cookies.txt` ключом `-c` и
отдаётся обратно ключом `-b`; это только удобство curl, сервер видит обычный
заголовок `Cookie`.

**Логин и пароль**, пользователь из `[auth.local]` или `[auth.ldap]`.
Chainlit принимает форму:

```bash
curl -s -c cookies.txt -X POST "$B/login" \
  -d "username=portal-bot" -d "password=$BOBA_PASSWORD"
```

Ответ `200` и `{"success":true}`, при неверном пароле — `401` и
`{"detail":"credentialssignin"}`. Studio принимает JSON и требует метку своего
запроса, без неё `403`:

```bash
curl -s -c cookies.txt -X POST "$S/auth/login" \
  -H "x-boba-request: 1" -H "Content-Type: application/json" \
  -d '{"username":"portal-bot","password":"'"$BOBA_PASSWORD"'"}'
```

Ответ `204`, cookie в заголовке `Set-Cookie`.

**Kerberos SSO**, доменная учётка с keytab и curl с GSSAPI. Билет получать
вручную не нужно: libkrb5 сам берёт TGT из keytab по `KRB5_CLIENT_KTNAME`.

```bash
KRB5_CLIENT_KTNAME=/etc/portal/portal-bot.keytab \
curl -s -c cookies.txt --negotiate -u : "$B/auth/sso"
```

Ответ `303` на страницу чата, cookie в этом же ответе. `401` с
`WWW-Authenticate: Negotiate` означает, что билет не выдан: проверить keytab,
`krb5.conf` и DNS до KDC. Отказ во входе — тоже `303`, но без cookie и на
страницу входа с причиной в адресе: `Location: .../login?error=sso_denied`.
Так отвечает сервис учётке, которой провайдеры не дали ни одной роли; поэтому
успех проверяют по наличию cookie, а не по коду. В studio тот же обмен на
`$S/auth/sso`.

**Доверенный заголовок (proxy)**, см. раздел ниже про подпись:

```bash
TS=$(date +%s)
SIG=$(printf 'portal-bot:%s:ops:general,search:search' "$TS" | openssl dgst -sha256 -hmac "$PROXY_SECRET" | awk '{print $NF}')

curl -s -c cookies.txt -X POST "$B/auth/proxy" \
  -H "X-Remote-User: portal-bot" \
  -H "X-Remote-Roles: ops" \
  -H "X-Remote-Profiles: general,search" \
  -H "X-Remote-Profile: search" \
  -H "X-Boba-Timestamp: $TS" \
  -H "X-Boba-Signature: $SIG"
```

Ответ `204`. В studio тот же маршрут `$S/auth/proxy`.

**Готовый JWT**, подписанный `auth_secret`. Так работает виджет copilot; секрет
наружу не отдавать, для партнёров есть proxy:

```bash
curl -s -c cookies.txt -X POST "$B/auth/jwt" -H "Authorization: Bearer $JWT"
```

Ответ `200` и `{"success":true}`; при чужой подписи `401` и `Invalid token`.
Маршрут есть только у chainlit. Он проверяет подпись и срок и выпускает
cookie с новым токеном из присланных `identifier`, `display_name` и
`metadata`; поколение он не сверяет. Поэтому ответ `200` ещё не значит, что
вход состоялся: если в `metadata` присланного токена нет текущего
`generation`, cookie выставится, а первый же запрос с ней получит `401`.
Рабочий способ получить такой JWT — взять токен действующего входа.

**Как отдавать токен дальше.** Маршруты ищут сессию в cookie, а если её нет —
в заголовке `Authorization: Bearer <токен>`; исключение — `/auth/refresh`
studio, он читает только cookie. В браузере работает только cookie, заголовок
удобен сервисам. Значение после `access_token=` и до `;` в `Set-Cookie` и
есть JWT:

```bash
T=$(awk '$6 ~ /^access_token(_[0-9]+)?$/ {print $6, $7}' cookies.txt | sort -V | awk '{printf "%s", $2}')
```

Команда собирает и цельную cookie, и чанки `access_token_0`, `access_token_1`
по порядку. Дальше либо файл cookie, либо заголовок вручную:

```bash
curl -s -b cookies.txt "$B/user"
curl -s "$B/user" -H "Cookie: access_token=$T"
curl -s "$B/user" -H "Authorization: Bearer $T"
```

Ответ `200` с пользователем и его `metadata`, `401` без сессии или с сессией
другого поколения. Если токен пришёл чанками, заголовок перечисляет их все:
`Cookie: access_token_0=…; access_token_1=…`.

Studio, пользователь, его роли, профиль и список доступных профилей:

```bash
curl -s -b cookies.txt "$S/me"
curl -s -b cookies.txt "$S/profiles"
curl -s -b cookies.txt -X PUT "$S/me/profile" \
  -H "Content-Type: application/json" -d '{"profile":"search"}'
```

Профиль, который входу не выдан, — `403` с перечнем выданных. Токен, выпущенный
chainlit, studio примет только при одинаковом `generation` у обоих приложений
(см. выше); иначе `401` с текстом `sign-in token rejected as generation`.

**Продление и выход.** Продление зовёт скрипт страницы по сигналу сервера,
руками оно нужно редко:

```bash
curl -s -b cookies.txt -c cookies.txt -X POST "$B/auth/refresh" -H "x-boba-request: 1"
```

Для парольного и proxy-входа это перевыпуск JWT, ответ `204` и новая cookie;
для kerberos это повторный SPNEGO-обмен, добавить `--negotiate -u :`.

Сервису, у которого есть только строка токена, файл cookie не нужен: токен
едет в заголовке `Cookie`, новый приходит в `Set-Cookie` ответа:

```bash
curl -s -i -X POST "$B/auth/refresh" -H "x-boba-request: 1" -H "Cookie: access_token=$T"
```

На вход цельный `access_token` принимается любой длины. В ответе токен длиннее
3000 символов приходит несколькими `Set-Cookie` с чанками `access_token_0`,
`access_token_1`, …; их значения склеиваются по порядку номеров. Звать
продление нужно до `exp` или не позже 300 секунд после него, иначе `403` и
вход заново. Выход снимает cookie:

```bash
curl -s -b cookies.txt -X POST "$B/logout"
curl -s -b cookies.txt -X POST "$S/auth/logout" -H "x-boba-request: 1"
```

Выход снимает cookie в браузере, но сам токен не отзывает: строка токена,
сохранённая где-то ещё, принимается до своего `exp`. Отозвать все выданные
токены разом можно только сменой `generation` либо `auth_secret`.

Не работают: `/auth/header` и OAuth chainlit — boba регистрирует в нём только
парольный callback и свои маршруты, и `/auth/header` отвечает `400` с текстом
`No header_auth_callback defined`.

### Провайдеры ролей и профилей

Роли и профили пользователя считаются при входе и уходят в токен вместе с
личностью. У каждого типа входа они задаются подсекциями
`[auth.<тип>.roles.<провайдер>]`: секция есть, провайдер подключён, роли всех
провайдеров складываются, исключение у любого из них отказ. Порог
`require_roles` действует на объединение.

| Провайдер | Кому доступен | Что делает |
|---|---|---|
| `local` | local, proxy | таблица `mapping` логин → роли и список `exclude` |
| `directory` | ldap | правила `samaccountname`, `member_of`, `dn` и `*_ex` по записи, которую вход получил своим bind'ом |
| `ldap` | kerberos, proxy | поиск записи под служебным bind'ом (`server`, `base_dn`, `bind_dn`, `bind_password`) и те же правила в `mapping`; kerberos ищет по UPN, proxy по sAMAccountName |
| `principal` | kerberos | правила `principal`, `sid` и `*_ex` по принципалу и SID из PAC |
| `header` | proxy | роли через запятую в заголовке `name` |

Профили: провайдер по ролям подключён у всех типов и настроек не имеет, он
выдаёт профили, чьи `[profiles.X].roles` пересекаются с ролями входа. У proxy
есть второй, `[auth.proxy.profiles.header]`: имена профилей через запятую в
заголовке `name` и, если задан `selected`, выбранный для новых чатов профиль в
отдельном заголовке. Имя, которого нет в `[profiles]`, отказ входа; выбранный
профиль обязан входить в выданный набор. Набор и выбор фиксируются в токене:
смена `[profiles.X].roles` действует после нового входа, у kerberos после
ближайшего обновления сессии.

Какой профиль получает новый чат, решается в одном порядке для чата и api:
выбор пользователя в интерфейсе, затем выбранный профиль из токена, затем
единственный выданный, затем профиль с `default = true`, если он выдан.
Если ни один шаг не сработал, чат отказывает, а api и страницы studio берут
первый из выданных. Для copilot, где селектора профилей нет, работают второй и
четвёртый шаги.

Пример для всех четырёх типов:

```toml
[auth.local]
    type          = "local"
    users         = "${site.local_auth.users}"
    require_roles = true
    [auth.local.roles.local]
        mapping = "${site.local_auth.roles}"

[auth.ldap]
    type             = "ldap"
    server           = "${site.ldap_url}"
    base_dn          = "${site.ldap_base_dn}"
    bind_dn_template = '${site.ldap_netbios}\{username}'
    [auth.ldap.roles.directory]
        member_of = "${role.ldap.memberof}"
        dn        = "${role.ldap.dn}"

[auth.kerberos]
    type             = "kerberos"
    principal_format = "{username}@${site.krb_realm}"
    [auth.kerberos.roles.ldap]
        server        = "${site.ldap_url}"
        base_dn       = "${site.ldap_base_dn}"
        bind_dn       = "${site.ldap_bind_user}"
        bind_password = "${site.ldap_bind_password}"
        [auth.kerberos.roles.ldap.mapping]
            member_of = "${role.ldap.memberof}"
```

### Разрешённые origin (CORS)

Файл `packages/apps/boba-chainlit/assets/.chainlit/config.toml` (в образе и
релизе — `app_root/.chainlit/config.toml`), ключ `allow_origins` в секции
`[project]`. Файл входит в образ при сборке, поэтому правка требует пересборки
образа чата. По умолчанию стоит `["*"]`. Запросы к chainlit идут с cookie
входа, и при `*` сервер подставляет в ответ origin любого запроса: чужой сайт
сможет ходить в chainlit от имени вошедшего пользователя. Перечислять только
свои адреса, схема и хост целиком:

```toml
allow_origins = ["https://boba.company.ru"]
```

Если виджет copilot встраивается на другой сайт, его адрес добавляется в тот
же список:

```toml
allow_origins = ["https://boba.company.ru", "https://portal.company.ru"]
```

Список действует на HTTP-запросы. Рукопожатие websocket проверке origin в
chainlit не подчиняется, поэтому список не заменяет остальные меры: вход по
cookie и `cookie_samesite`.

Middleware chainlit отвечает с `allow_credentials`, то есть перечисленные
origin получают и cookie, и любые заголовки, включая метку своего запроса.
Поэтому в списке только те сайты, которым разрешено действовать от имени
вошедшего пользователя: при `*` метка `x-boba-request` перестаёт защищать от
CSRF. Три домена — три строки списка, каждый со схемой и хостом, без пути.

У studio своего CORS-middleware нет: его api из браузера доступен только со
страницы того же origin, а межсайтовые запросы браузер отклоняет на preflight.
Список origin studio не читает.

### Вход по доверенному заголовку (proxy)

Для сайтов и сервисов, которые сами знают пользователя и хотят открыть ему
boba без пароля и без раздачи `auth_secret`. Бэкенд партнёра называет логин
заголовком и подписывает запрос общим секретом, boba выпускает обычную
сессию. Работает и в chainlit, и в studio.

Секция общего конфига; вход включён, пока `"${auth.proxy}"` стоит в списке
`[app].auth`:

```toml
[auth.proxy]
    type            = "proxy"
    path            = "/auth/proxy"
    secret          = "${site.proxy_secret}"
    max_skew_sec    = 60
    allowed_clients = "${site.proxy.allowed_clients}"
    require_roles   = true
    [auth.proxy.headers]
        user      = "X-Remote-User"
        timestamp = "X-Boba-Timestamp"
        signature = "X-Boba-Signature"
    [auth.proxy.roles.local]
        mapping = "${site.proxy.local_roles}"
    [auth.proxy.roles.ldap]
        server        = "${site.ldap_url}"
        base_dn       = "${site.ldap_base_dn}"
        bind_dn       = "${site.ldap_bind_user}"
        bind_password = "${site.ldap_bind_password}"
        [auth.proxy.roles.ldap.mapping]
            member_of = "${role.ldap.memberof}"
    [auth.proxy.roles.header]
        name = "X-Remote-Roles"
    [auth.proxy.profiles.header]
        name     = "X-Remote-Profiles"
        selected = "X-Remote-Profile"
```

Значения машины — в site.toml:

```toml
[site]
    proxy_secret = "..."

    [site.proxy]
        allowed_clients = ["10.20.30.40/32"]

        [site.proxy.local_roles]
            "portal-bot" = ["read"]
```

- **`secret`.** Отдельный ключ HMAC, не `auth_secret`. Генерация:
  `openssl rand -hex 32`. Живёт у партнёра и в boba, ротируется без разлогина
  остальных пользователей.
- **`allowed_clients`.** Сети CIDR, откуда принимается вход. Пустой список
  выключает фильтр. Адрес берётся из `X-Forwarded-For` или `X-Real-IP`,
  которые выставляет nginx, поэтому порт приложения должен быть закрыт для
  всех, кроме nginx.
- **Роли и профили.** Провайдеры `roles.local`, `roles.ldap`, `roles.header`
  и `profiles.header` описаны выше. Каталог только даёт роли: логин, которого
  в нём нет, входит с остальными провайдерами. Любую секцию можно не
  указывать.
- **Заголовки.** Логин, метка времени в unix-секундах и подпись. Подпись
  это HMAC-SHA256 в hex от строки `login:timestamp:roles:profiles:profile`,
  где `roles`, `profiles` и `profile` это значения заголовков ролей, набора
  профилей и выбранного профиля как есть или пустые строки, если заголовок не
  настроен или не прислан. Запрос, метка времени которого расходится с
  часами сервера больше чем на `max_skew_sec` в любую сторону, отвергается.

Вызов:

```bash
TS=$(date +%s)
SIG=$(printf 'portal-bot:%s:ops:general,search:search' "$TS" | openssl dgst -sha256 -hmac "$PROXY_SECRET" | awk '{print $NF}')

curl -s -c cookies.txt -X POST "$B/auth/proxy" \
  -H "X-Remote-User: portal-bot" \
  -H "X-Remote-Roles: ops" \
  -H "X-Remote-Profiles: general,search" \
  -H "X-Remote-Profile: search" \
  -H "X-Boba-Timestamp: $TS" \
  -H "X-Boba-Signature: $SIG"
```

Ответ `204` и cookie `access_token`, дальше как у любого входа. В studio тот
же маршрут под api: `{prefix}/api/v1/auth/proxy`. На PHP подпись считается
одной строкой:
`hash_hmac('sha256', "$login:$ts:$roles:$profiles:$profile", $secret)`.

Отказы: `401` подпись, окно времени или заголовки, `403` адрес вне сетей,
исключение по логину, ни одной роли либо профиль, которого нет в `[profiles]`.
Причина в теле ответа и в логе, например `signature does not match
HMAC-SHA256 of login:timestamp:roles:profiles:profile under
[auth.proxy].secret`, `timestamp ... is 601s away from the server clock ...,
max_skew_sec = 60`, `client ... is outside allowed_clients [...]`, `no role
came from any of the configured providers [...] while require_roles = true`.

У такого входа нет kerberos-билета: инструменты, работающие в базе от имени
пользователя, откажут так же, как при парольном входе.
