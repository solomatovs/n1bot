# pg-idx-vector: векторный индекс объектов PostgreSQL

Независимый индексатор поверх схемы `ix`. Читает только `ix.node`, `ix.tree` и surface-таблицы
`ix.pg_*`, пишет только в `ix.pg_idx_emb_e5_1024`. Со скрапером не связан ни вызовами, ни внешними
ключами: строки node, которых больше нет, убирает сам. Модель считает Python между очередью и
записью; SQL знает только текст и вектор.

```
schema/   DDL объектов, которыми владеет индексатор
run/      SQL шагов цикла, их выполняет worker.py
```

## Установка

`schema/00_pg_idx_emb_e5_1024.sql`: таблица и частичные HNSW-индексы по парам surface и aspect.
Предусловие: ядро `ix` из `docs/knowledge-schema.sql`, `docs/pg-meta-scraper/schema/00_surface.sql`
(значения `surface_e` в предикатах индексов), словарь аспектов из схемы любого индексатора.

## Запуск

Индексатор работает по всей базе `ix` сразу, источники ему не задаются: что скрапер положил
в `ix` из любых баз, то и индексируется. Порядок в цепочке: сначала `pg-meta-scraper` по каждому
источнику, затем этот индексатор один раз. Запускать можно как угодно часто, и до, и после
скрапера: он сам находит, чего не хватает, и доводит таблицу до структуры; параллельные
запуски не мешают друг другу.

```
.venv/bin/python docs/pg-idx-vector/worker.py --dsn "host=<хост ix> port=5432 dbname=<база ix> user=<роль> password=<пароль>" \
    --cache-dir compose/chainlit/models/fastembed
```

Роль в DSN должна иметь права на чтение `ix.node`, `ix.tree`, surface-таблиц `ix.pg_*` и на
запись в свою таблицу `ix.pg_idx_emb_e5_1024`. Схему таблицы создаёт `schema/*.sql` при установке
(идемпотентно), запускается той же ролью или владельцем схемы `ix`. Один запуск = один
проход до пустой очереди и prune; для регулярной работы ставится в планировщик.

## Воркер: worker.py

Готовый цикл на Python поверх провайдера проекта `boba.llm.embedding` (fastembed, ONNX на
CPU, модель `intfloat/multilingual-e5-large` из каталога `models/fastembed`, префикс
`passage:` подставляет fastembed). Запуск из venv проекта:

```
.venv/bin/python docs/pg-idx-vector/worker.py \
    --dsn "host=... dbname=... user=... password=..." \
    --cache-dir compose/chainlit/models/fastembed \
    --batch 64
```

Ключи: `--model` (по умолчанию `intfloat/multilingual-e5-large`), `--dim` (1024), `--batch`
(размер пачки очереди), `--chunk-tokens` (400) и `--chunk-overlap` (50). Воркер всегда идёт
до пустой очереди и заканчивает prune. Он читает
SQL-файлы пакета как есть и передаёт параметры словарём, держит одну сессию с
`lock_timeout` и `statement_timeout`, после каждой пачки и при любой ошибке снимает захваты
очереди, в конце делает prune. На стенде 435 текстов e5-large на CPU заняли 25 секунд.

## Чанки

Окно модели e5 это 512 токенов, и fastembed молча обрезает всё, что длиннее: без резки у
таблицы на триста колонок в вектор попали бы только первые из них. Поэтому текст аспекта
режется токенизатором той же модели (он лежит в том же кэше, что и веса) на окна по
`--chunk-tokens` с перекрытием `--chunk-overlap`, каждое окно кодируется отдельно, и у аспекта
получается несколько строк с `chunk_no`. Текст короче окна остаётся одним чанком без
перекодирования. Все чанки аспекта несут `content_hash`, md5 полного текста: по нему очередь
решает, что аспект не менялся. Запись набора чанков одного аспекта атомарна: один
statement удаляет чанки с номером не меньше нового числа и перезаписывает остальные.

Поиск считает ранг node по лучшему чанку: `min(emb <=> query)` по группе `(node_id, surface,
aspect)`. На стенде таблица с 300 колонками дала 9 чанков, и запрос по колонке из самого
конца списка нашёл именно последний чанк.

## Цикл воркера

Одна сессия к `ix`, `set lock_timeout`, `set statement_timeout`, autocommit:

1. `run/10_queue.sql` с параметром `%(batch)s`: аспекты `(node_id, surface, aspect, content,
   content_hash)`, у которых нет ни одного чанка или хэш чанков отличается от md5 полного
   текста. Каждый выданный аспект захвачен сессионным advisory-замком по `node_id`, занятые
   другим воркером пропущены. Пустой результат значит, что очередь пуста.
2. Текст каждого аспекта режется на чанки, `embed_documents` провайдера кодирует все чанки
   пачки одним вызовом, и на каждый аспект выполняется `run/20_write.sql` с именованными
   параметрами `%(node_id)s`, `%(surface)s`, `%(aspect)s`, `%(content_hash)s`, `%(chunk_count)s`
   и массивами `%(chunk_nos)s`, `%(contents)s`, `%(embs)s` (векторы строками вида `[0.1, ...]`).
   Если за время расчёта текст изменился, хэш уже другой, и следующая очередь выдаст аспект
   снова.
3. `run/90_unlock.sql` после записи пачки и при любой ошибке (finally). Обрыв сессии снимает
   захваты сам.
4. `run/30_prune.sql` в конце цикла: удалить чанки аспектов, которых больше нет, пропуская
   занятые. Порядок «сначала добавить, удалять последним» тот же, что у fts и trgm;
   поисковые запросы join'ят `ix.node`, сироты до ближайшего prune безвредны.

Несколько воркеров работают одновременно: захваты делят очередь без пересечений, запись
идёт `on conflict do update ... where content_hash is distinct from`, prune никого не ждёт.
Запрос при поиске кодируется `embed_query` того же провайдера (префикс `query:`).

## Описания от LLM: необязательны

Аспект `llm_description` читается из `ix.pg_llm_description`, которую создаёт пакет `pg-llm-describer`.
Если его не устанавливали, таблицы нет, и запрос с ней упал бы. Поэтому у шагов, которым она
нужна, два файла: базовый (`run/10_upsert.sql`) без описаний и вариант с суффиксом
`__llm` и заголовком `-- @requires ix.pg_llm_description`. Воркер перед запуском проверяет
`to_regclass` для каждой таблицы из `@requires` и берёт вариант, только если все они есть;
иначе базовый файл. Ничего включать руками не нужно: поставили describer, индекс при
следующем запуске подхватил описания; убрали таблицу, индекс продолжает работать без них,
а prune уберёт строки аспекта `llm_description`.

## Аспекты

| aspect | кто пишет |
|---|---|
| description | все surface |
| comment | у кого comment не пуст |
| columns | pg_table, pg_view |
| llm_description | у кого есть строка в `ix.pg_llm_description` (пакет pg-llm-describer) |

Текст тот же, что у `pg-idx-fts` (заголовок объекта, комментарий, для таблиц колонки с
типами), поэтому сниппет полнотекста и вектор описывают одно и то же. 

## Важно: дублирование определения аспектов

CTE `obj` и `aspect` в `run/10_queue.sql` и `run/30_prune.sql` этого пакета и в соседних пакетах
индексаторов это одна и та же логика, скопированная намеренно. Общих объектов в базе
(представлений, функций) по решению нет. При переносе на Python эти CTE должны стать одной
общей функцией, которая генерирует текст аспектов для всех индексаторов; до тех пор при
правке определения аспекта править все копии.

## Требования к схеме

Ядро `ix` (`ix.node`, `ix.tree`) и surface-таблицы `ix.pg_*` скрапера. Свою таблицу пакет
создаёт сам в `schema/`: без внешнего ключа на `ix.node`, со ссылками на словари `ix.surface`
и `ix.pg_idx_aspect`. Расширение `vector` (halfvec, hnsw) должно быть установлено.
