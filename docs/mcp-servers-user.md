# Пользовательские MCP-серверы aid

Панель `/mcp` позволяет пользователю добавлять HTTP и SSE серверы, менять адрес и имя, выбирать OAuth-вход, задавать Bearer-токен и дополнительные заголовки, выключать и удалять свои подключения. Сохранение не проверяет доступность сервера: подключение и его состояние читаются отдельно.

Единственный источник серверов — таблица `mcp_servers` в схеме приложения. Секции `[mcp.servers.*]` и список `mcp` в профиле чата больше не используются. Существующие объявления нужно перенести вручную. Автоматического переноса и изменения рабочих данных при обновлении кода нет.

## Платформа

В `[server]` обязательны `public_url` — публичный адрес чата в браузере — и `sandbox_port` — порт единственной песочницы MCP Apps. Порт песочницы публикуется отдельно; схема и хост совпадают с `public_url`. Он должен отличаться от порта чата и его origin. Настройки TLS обоих слушателей общие.

В CORS чата нельзя разрешать `*`, `null` или origin песочницы. Приложение MCP работает во внутреннем iframe с непрозрачным origin. Страница песочницы и её сообщения защищены токеном процесса. После загрузки страницы токен удаляется из её адреса; во внутреннее приложение он не передаётся. Access log песочницы не содержит query с токеном.

Поддержку MCP Apps сервер объявляет при инициализации расширением `io.modelcontextprotocol/ui`. Для серверов редакции 2025-11-25 также принимается объявление приложения в `_meta.ui.resourceUri` инструмента: так работают официальные примеры этой редакции. Настройки `apps` в записи сервера нет.

Необязательные сроки новых серверов задаются моделью `McpDefaultsConfig`; значения по умолчанию — 10 секунд на подключение и 60 секунд на вызов. Секция `[mcp_servers]` содержит ключ шифрования и необязательные сроки новых записей. Например:

```toml
[mcp_servers]
connect_timeout_sec = 15
call_timeout_sec = 120
```

При правке подключения его сроки сохраняются. Изменение секции влияет на новые записи. Отдельных полей сроков в форме нет.

## Имена и секреты

Имена уникальны во всей таблице: до 64 латинских букв, цифр, дефисов и подчёркиваний, без `__` и конечного `_`. Имя `chat` принадлежит встроенным инструментам чата.

URL принимает `http` и `https`, включая внутренние адреса. Запрос выполняет сам aid: право добавлять серверы тем самым разрешает пользователю направлять запросы во внутреннюю сеть, доступную aid. Это осознанная политика этой реализации.

Логин, пароль, query и fragment в URL запрещены. Секреты задаются отдельными полями. Заголовки `Authorization`, `Mcp-Session-Id`, `Mcp-Protocol-Version`, `Content-Type`, `Accept` принадлежат транспорту и формой не принимаются.

Токен и значения заголовков шифруются `SecretCipher` ключом `[mcp_servers].cipher`. Форма правки получает только признак сохранённого токена и имена заголовков. Пустое поле сохраняет прежний секрет; удаление строки заголовка удаляет заголовок. Смена ключа шифрования без переноса данных делает существующие секреты нечитаемыми.

## Выдача администратором

Личная выдача (`grants.tgt_kind = 'users'`) даёт пользователю право редактировать запись. Выдача через роль (`tgt_kind = 'roles'`) даёт доступ только для чтения. Проверка выдачи выполняется перед выдачей конфигурации клиенту, в том числе для уже закэшированного подключения. Выключенная запись видна в панели, но клиенту не выдаётся.

Кнопка «Параметры подключения» у сервера роли открывает форму просмотра: поля серые и заблокированы, сохранения и удаления нет. Форма не возвращает значений секретов. Бэкенд независимо проверяет личную выдачу перед правкой, выключением и удалением; прямой запрос к API не обходит этот запрет.

Пример сервера без авторизации и его выдачи роли; замените `aid`, адрес и имя роли своими значениями:

```sql
begin;

insert into aid.mcp_servers (name, data)
values ('jira', '{
  "endpoint": {
    "transport": "streamable-http",
    "service": {"scheme": "https", "host": "mcp.example.com", "path": ""},
    "path": "/mcp",
    "auth": {"auth": "none"}
  },
  "limits": {"connect_timeout_sec": 10, "call_timeout_sec": 60}
}'::jsonb);

insert into aid.grants (src_kind, src_kind_id, tgt_kind, tgt_kind_id)
select 'mcp_servers', s.id, 'roles', r.id
from aid.mcp_servers s cross join aid.roles r
where s.name = 'jira' and r.role = 'analysts'
on conflict do nothing;

commit;
```

Секретные значения в SQL нельзя записывать открытым текстом: записи с секретами создаёт хранилище с `SecretCipher`. Роли должны соответствовать ролям входа пользователя.

## Открытые чаты

Набор серверов фиксируется при запуске агента: включённые личные и ролевые серверы плюс `chat`. Добавление, правка, выключение, удаление и переподключение своего сервера помечают агентов пользователя на перезапуск перед следующим ходом. Изменение списка инструментов записывает существующий механизм delta истории агента.

При Postgres-шине событие `McpServersChanged` передаётся в область пользователя на остальные экземпляры aid; они также сбрасывают устаревшие подключения и помечают своих агентов. При локальной шине доставка ограничена одним процессом.

Выдача роли напрямую через SQL события не создаёт. Она появляется в новом чате; ролевой набор открытой вкладки сохраняется и при восстановлении процесса, и при правке личных серверов. Текущий агент не опрашивает таблицу перед каждым ходом.

stdio и интерфейс выдачи серверов ролям в форму не входят. Серверы со способами входа local/proxy могут храниться в таблице и выдаваться администратором.


## OAuth и описание инструментов

В форме выбранный способ входа отмечен явно, в том числе при просмотре
подключения, выданного через роль. При выборе «Вход через OAuth» в форме
появляется кнопка входа. Для личного подключения она сохраняет настройки,
включает сервер и открывает его страницу авторизации; отдельно нажимать
«Сохранить» и «Включить» не требуется. Если вход не удался после сохранения,
повторная попытка использует созданную запись.

После входа браузер возвращается на страницу, с которой начата авторизация,
включая адрес текущего чата, параметры запроса и фрагмент. Адрес сохраняется
в состоянии конкретной попытки OAuth и проверяется относительно public_url
приложения, в том числе его URL-префикса.

AID узнаёт адрес авторизатора через стандартные метаданные OAuth MCP.
Страница может принадлежать внутреннему или внешнему авторизатору, который
объявлен сервером. OAuth-проверка использует штатный McpToolServer:
он согласует версию MCP и учитывает выбранный транспорт и заголовки.
Ручного запроса initialize и фиксированной версии протокола в OAuth нет.
Если сохранённая авторизация уже действует, повторный вход в браузере
не требуется. Токены каждого пользователя хранятся отдельно в зашифрованном
виде.

«Отключить OAuth» удаляет сохранённые credentials пользователя и закрывает
его подключение. Сервер остаётся включённым, но показывает «Требуется вход».
Просмотр карточки и переподключение без токенов не запускают регистрацию
OAuth; новый вход начинается кнопкой «Войти через OAuth».

Имя OAuth-клиента берётся из `[UI].name` в конфигурации Chainlit и передаётся
в `client_name` как при регистрации, так и в документе метаданных клиента.

Для Client ID Metadata Document адрес документа должен соответствовать
требованиям CIMD, включая HTTPS; это проверяет валидатор MCP SDK. При
локальном HTTP-запуске AID этот способ не предлагается, и SDK использует
динамическую регистрацию, если её поддерживает авторизатор.

Каждый инструмент в списке — отдельная раскрывающаяся строка. В свёрнутом
виде видны исходное имя вызова, например ch_column_describe, и описание.
Нажатие раскрывает полную карточку tools/list как форматированный JSON,
включая описания, inputSchema, outputSchema и метаданные. Строки раскрываются
независимо друг от друга.
Поле title в самом JSON сохраняется как его прислал MCP; UI не использует
его вместо имени инструмента. Чтобы проверить новые overrides после SIGHUP,
нажмите «Переподключить» в карточке сервера и откройте инструменты.
