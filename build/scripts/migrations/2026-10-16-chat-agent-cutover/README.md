# Переход с dev на чат с процесс-агентом

Приложение ветки dev хранило беседу треда в чекпойнтах langgraph, а вложения и
файлы итогов — строками `elements`. Новое приложение хранит беседу в истории агента
(`history_records`), вложения вопроса — ссылками `resource_link` в этой истории, файлы
итогов — в `rawOutput` итога вызова. Переход делается в отдельную новую базу тремя
скриптами; старая база при этом только читается, поэтому отдельного отката нет: если
что-то не так, новую базу удаляют и повторяют.

| шаг | скрипт | где работает | что делает |
|---|---|---|---|
| 1 | `dump.sh` | старая база, только чтение | копия таблиц приложения поштучно |
| 2 | `restore.sh` | новая пустая база | накатывает копию одной транзакцией и сверяет число строк |
| 3 | `migrate.sql` | новая база | переводит беседы и оценки, приводит таблицы к новому виду, удаляет ненужное |

## Какие таблицы копируются и что с ними происходит

Список таблиц в `dump.sh` выведен из кода: в шапке скрипта указано, какой компонент
пользуется какой таблицей. Таблицы, которых в старой базе нет (компонент не
развёрнут: например скраперы Oracle или studio), `dump.sh` пропускает с сообщением.

| таблицы | кто пользуется | создаёт ли приложение при старте | что делает `migrate.sql` |
|---|---|---|---|
| чат: `users`, `threads`, `feedbacks` | чат (boba-runtime) | да, если нет; существующие оставляет | `threads.meta.agent_session` каждому перенесённому треду; оценкам — id шагов новой ленты; у `users` — умолчание `created_at`, ключ `meta.llm` удаляется |
| чат: `elements` | чат dev | нет, новое приложение её не читает | читает `mime` вложений вопросов и удаляет таблицу |
| чат: `connections`, `roles`, `grants` | соединения (boba-connection-broker) | да, если нет; `roles` пополняет из `[roles]` | ничего: формат тот же |
| чат: `agent_user_settings`, `agent_chat_settings` | настройки агента | да | ничего (в базе dev их нет) |
| `checkpoints.*` | dev: чекпойнтер langgraph | нет | переводит в историю агента и удаляет вместе со схемой |
| `agent_history.history_records` | агент (boba-history-postgres) | агент — при первом обращении | создаёт определением из `history_records.sql`, если её нет, и пишет перенесённые сессии |
| `kb.*` | база знаний (boba-db-pgvector) | да, своими миграциями | ничего |
| `describer.*` | инструмент описаний | да, при первом обращении | ничего |
| `ix.*` | ix-core и индексаторы | индексатор при своём старте | ничего |
| `automation.*`, `catalog.*` | studio | да | ничего |
| `live.*` (шина) | чат, studio | да | не копируются: в них состояние работающих процессов |

Не копируются и не нужны новому приложению: журналы workflow (`workflows`,
`workflow_runs`, `workflow_drafts`), шаги старого chainlit (`steps`), `mcp.users`,
таблицы `public`.

## Изменения схемы между dev и новым приложением

| изменение | откуда | кто его делает |
|---|---|---|
| беседа треда — в `history_records` вместо чекпойнтов langgraph | `fbb096b4` (хранилище истории), `ac91dfc2`, `ca557bea` (чат без langgraph) | `migrate.sql`: перевод, удаление чекпойнтов |
| тред находит сессию агента по `threads.meta.agent_session` | `ce5e9b5a` | `migrate.sql` |
| вложения вопроса — `resource_link` вместо строк `elements`; таблица `elements` не читается | `1060bd4a`, `52552b6b`, `10f82e16`, `19142b51` | `migrate.sql`: ссылки в вопросах, удаление `elements` |
| адрес журнала вызова в итоге обязан нести идентификатор вызова | `6f15fdfc` | `migrate.sql`: неполный адрес не переносится, заметка |
| id шага ответа считается только по воспроизводимым ответам агента | новый чат на ACP | `migrate.sql`: перевод `feedbacks.for_id` |
| `users.meta.llm` (семплинг по профилям) больше не читается | `e5cab81a` | `migrate.sql`: ключ удаляется |
| таблицы `agent_user_settings`, `agent_chat_settings` | `ce5e9b5a` | приложение при старте |
| шина удаляет события неизвестных видов | `10f82e16` | приложение при старте (шина не копируется) |
| workspace пользователя у сервиса boba-mcp по id из логина | `791b8674` | файлы, не база: `../2026-10-05-workspace-to-mcp.sh` |

Определения остальных таблиц (`kb`, `ix`, `describer`, studio, соединения, `users`,
`threads`, `feedbacks`) в коде dev и нового приложения совпадают.

## Подключение

Все скрипты подключаются стандартными переменными libpq: `PGHOST`, `PGPORT`,
`PGDATABASE`, `PGUSER`, `PGSSLMODE` и т. д. Пароль в командную строку не
передаётся: он берётся из `~/.pgpass` или из файла, названного в `PGPASSFILE`
(права `0600`, строка `хост:порт:база:пользователь:пароль`). Kerberos работает из
кэша билетов, как у `psql`. `pg_dump` и `pg_restore` должны быть не старше сервера.

Имена схем старой базы, если они не по умолчанию, задаются для `dump.sh`
переменными окружения `CHAT_SCHEMA` (`chainlit`), `HISTORY_SCHEMA` (`agent_history`),
`CHECKPOINTS_SCHEMA` (`checkpoints`), `KB_SCHEMA` (`kb`), `DESCRIBER_SCHEMA`
(`describer`), `IX_SCHEMA` (`ix`), `STUDIO_SCHEMA` (`automation`), `CATALOG_SCHEMA`
(`catalog`). Схемы в новой базе называются так же; их имена в конфиге нового
приложения должны совпадать.

## Порядок действий

1. Остановить чат, studio, сервис boba-mcp и индексаторы: копия снимается со
   стоящей базы, иначе `restore.sh` найдёт расхождение в числе строк.
2. Снять копию:
   ```sh
   PGHOST=… PGUSER=… PGDATABASE=boba ./dump.sh /backup/cutover-2026-10
   ```
   В каталоге появятся `tables.dump`, `prelude.sql`, `extensions.txt`,
   `functions.txt`, `counts.tsv`. Сообщения `skipped …` перечисляют таблицы
   неразвёрнутых компонентов.
3. Создать новую пустую базу (администратором, если у роли приложения нет прав):
   ```sh
   createdb -O boba-svc boba_v2
   ```
   Расширения из `extensions.txt` (`vector`, `pg_trgm`, `btree_gin`, `unaccent`)
   `restore.sh` создаёт сам; если у роли нет на это прав, их заранее создаёт
   администратор: `psql -d boba_v2 -c 'create extension vector'` и т. д.
4. Накатить копию:
   ```sh
   PGHOST=… PGUSER=… PGDATABASE=boba_v2 ./restore.sh /backup/cutover-2026-10
   ```
   Скрипт откажет, если в базе уже есть таблицы. Ошибка откатывает всё.
5. Перевести:
   ```sh
   PGHOST=… PGUSER=… PGDATABASE=boba_v2 psql -v checkpoints_schema=checkpoints \
        -v history_schema=agent_history -v chainlit_schema=chainlit \
        -v chat_url=https://chat.example.com/boba -f migrate.sql
   ```
   `chat_url` — `[agent].public_url` нового чата: из него строятся ссылки на
   вложения вопросов. В выводе — заметки перевода (вложения вне каталога треда,
   неполные адреса журналов), перенесённые и оставшиеся без шага оценки, итог и
   строка `The migration is committed.` Повторный запуск ничего не меняет.
6. Перенести workspace пользователей к сервису boba-mcp скриптом
   `../2026-10-05-workspace-to-mcp.sh` (карта `select id, identifier from chainlit.users`).
7. Направить конфиги нового чата, boba-mcp и индексаторов на новую базу
   (`site.pg_database = "boba_v2"`) и запустить. На старте приложение само создаёт
   таблицы шины и настроек агента и применяет свои миграции на месте.
8. Проверить: список тредов, старый тред с вложением, с итогами инструментов, с
   оценкой ответа, с прерванным ответом.

Если что-то не так — удалить новую базу (`dropdb boba_v2`) и повторить с шага 3:
старая база не менялась.

## Сверка определения истории с кодом

Таблицу `history_records` агент создаёт сам при первом обращении, а перенос пишет
в неё раньше, поэтому `migrate.sql` создаёт её определением из `history_records.sql`.
Тест `TestCutoverTable` в `packages/infra/history/boba-history-postgres/tests`
проверяет, что это определение совпадает с тем, что создаёт хранилище агента.
