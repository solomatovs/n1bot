# Слияние истории dev с базой работающего чата

Переход 2026-10-16 (`../2026-10-16-chat-agent-cutover`) рассчитан на новую пустую
базу: он копирует базу ветки dev и переводит её в раскладку нового чата. Здесь
задача другая: чат нового выпуска уже работает в своей базе, в ней есть свои
треды, а беседы dev и треды, которые чат записал ранним выпуском, в ней не
видны. Скрипты этого каталога дописывают в работающую базу всё, что было в dev,
и приводят историю ранних выпусков к виду, который читает текущий.

Что бывает в базе работающего чата и что с этим делают скрипты:

| что | где лежит | что делает слияние |
|---|---|---|
| треды, пользователи, роли, соединения dev, беседы dev в чекпойнтах langgraph | отдельная база dev (`chainlit.*`, `checkpoints.*`) | `stage.sh` переводит копию dev скриптами перехода 2026-10-16 и кладёт её в целевую базу схемами `cutover_*`; `merge.sql` дописывает её в таблицы чата |
| история ранних выпусков нового чата: записи без вида `kind`, итоги инструментов не в виде `CallToolResult`, таблица `history_records` | `boba.session_records`, `boba.history_records` | текущий выпуск их не читает: такую базу пересоздают переносом из dev, `verify.sql` останавливается на таких записях |
| сессии без владельца | `boba.session.owner` пустой | `normalize.sql` пишет туда логин пользователя треда |
| таблицы, которых текущий выпуск не создаёт и не читает | `boba.history_records`, `aid.agent_user_settings` | `cleanup.sql` удаляет их после сверки |
| таблица записей истории под прежним именем `history` | `boba.history` | `rename.sql` переименовывает её в `session_records` при смене выпуска |

Схемы целевой базы — как у текущего выпуска: `aid` — чат, `boba` — история
агента, `mcp` — сервис boba-mcp и его плагины, `ix` — индекс. Другие имена
передаются переменными psql `aid_schema`, `boba_schema`, `mcp_schema`,
`ix_schema`.

## Скрипты

| шаг | скрипт | где работает | что делает |
|---|---|---|---|
| 0, если записи истории лежат в `history` | `rename.sql` | целевая база | переименовывает `history` в `session_records` вместе с ключом и ссылкой на `session` |
| 1, если есть база dev | `stage.sh` | база dev (только чтение), новая рабочая база, целевая база | копия dev → `dump.sh`, `restore.sh`, `migrate.sql` перехода 2026-10-16 в рабочей базе → схемы `cutover_aid`, `cutover_boba`, `cutover_mcp`, `cutover_ix` в целевой базе; рабочая база удаляется |
| 2, если был шаг 1 | `merge.sql` | целевая база | дописывает схемы `cutover_*` в таблицы чата и удаляет их |
| 3 | `normalize.sql` | целевая база | владельцы сессий, время тредов по последней записи |
| 4 | `verify.sql` | целевая база, ничего не меняет | сверка: у каждой записи вид `kind`, у результата инструмента — исход `status` и итог `CallToolResult`; останавливается со списком расхождений |
| 5, после проверки | `cleanup.sql` | целевая база | сверка ещё раз и удаление `history_records` и `agent_user_settings` |
| по месту | `playground.sql` | рабочая база чат-бота (`createdb -O boba-svc playground`), под суперпользователем | `adusers` создают свои схемы и объекты в `public` |
| по месту | `connections.sql` | целевая база | удаляет соединение пользователей или переводит postgres- или clickhouse-соединение на другую базу |

`merge.sql` пишет в базу, разложенную текущим выпуском: у тредов должна
быть колонка `updated_at`, её заводит старт чата; иначе скрипт
останавливается до изменений.

Каждый шаг идёт одной транзакцией и останавливается до изменений, если данные
не те, что он ожидает. Повторный запуск любого шага ничего не дублирует:
проверено повтором всей цепочки на копии.

### Как `merge.sql` дописывает копию

- Пользователи — по логину (`identifier`). Логин, который в целевой базе уже
  есть, остаётся своей строкой, и треды, настройки агента треда и гранты копии
  переходят на её id. id копии, занятый другим логином, останавливает слияние.
- Роли — по имени.
- Треды, оценки ответов, настройки агента треда — по своему id; строка с уже
  занятым id не трогается.
- Сессии истории — сессия, которой в целевой базе нет, переносится со всеми
  записями; существующая не трогается.
- Соединения с грантами, база знаний (`kb_*`), описания (`node`, `edge`) и
  индекс `ix` — группами и только в пустые таблицы: если в целевой базе в группе
  уже есть строки, группа пропускается с заметкой в выводе. Регистры `ix`
  (`surface`, `aspect` и прочие) не переносятся, их ведут индексаторы целевой
  базы; значение копии, которого в них нет, останавливает слияние.

Секреты соединений в копии зашифрованы ключом `[connections]` чата dev и
переносятся как есть, поэтому ключ (`keys.encryption` site.toml) у целевого чата
должен быть тем же.

## Подключение

Как у скриптов перехода 2026-10-16: стандартные переменные libpq (`PGHOST`,
`PGPORT`, `PGUSER`, `PGDATABASE` …), пароль — из `~/.pgpass` или `PGPASSFILE`.
`stage.sh` создаёт рабочую базу из шаблона с расширениями `vector`, `pg_trgm`,
`unaccent`, `btree_gin` и накатывает в неё копию, поэтому его запускает
администратор кластера; все три базы — на одном сервере.

Если `/dev/shm` сервера мал (у контейнера docker по умолчанию 64 МБ),
параллельные воркеры запросов падают с `could not resize shared memory
segment`; тогда параллельность выключают на время скриптов:
`PGOPTIONS='-c max_parallel_workers_per_gather=0 -c max_parallel_maintenance_workers=0'`.

## Имя таблицы записей истории

Выпуски до 2026-10-24 держат записи истории агента в таблице `history`,
текущий — в `session_records`. Скрипты этого каталога пишут в
`session_records`, поэтому базу выпуска с `history` сначала переименовывают:

```sh
PGDATABASE=aid psql -f rename.sql
```

Прежний выпуск после переименования истории не видит, а текущий без него
заводит пустую `session_records`. Поэтому `rename.sql` запускают при смене
выпуска: чат, агент и служба агента остановлены, затем переименование, затем
запуск нового выпуска. Пустую `session_records`, которую новый выпуск успел
завести, скрипт заменяет старой таблицей; если в ней уже есть записи —
останавливается до изменений. Повторный запуск ничего не меняет.

Тот же старт нового выпуска заводит тредам время последней активности
`threads.updated_at` — временем создания треда, и список тредов пошёл бы по
созданию. Поэтому после первого старта ещё раз выполняют `normalize.sql`: он
сдвигает время каждого треда ко времени последней записи его сессии.

```sh
PGDATABASE=aid psql -f normalize.sql
```

## Порядок действий

Чат и boba-mcp целевой базы могут работать, если это выпуск, который читает
`session_records`: скрипты дописывают строки и не меняют таблиц, которые
читает работающий выпуск.

1. Резервная копия целевой базы и базы dev (`pg_dump -Fc`); если записи
   истории в базе ещё в `history` — `rename.sql` при смене выпуска (раздел
   выше).
2. Если есть база dev — копия dev в целевую базу:
   ```sh
   SOURCE=boba STAGE=merge_stage TARGET=aid TEMPLATE=boba_stand_template \
   CHAT_URL=http://127.0.0.1:8501/boba ./stage.sh /backup/merge-2026-10
   ```
   `CHAT_URL` — буква в букву `[agent].public_url` целевого чата (см. README
   перехода 2026-10-16, шаг 5): из него строятся ссылки на вложения вопросов.
3. Слить:
   ```sh
   PGDATABASE=aid psql -f merge.sql
   ```
   В выводе — сколько строк каждой таблицы было в копии и сколько добавлено,
   и итог по группам.
4. Назначить владельцев сессий и сверить:
   ```sh
   PGDATABASE=aid psql -f normalize.sql
   PGDATABASE=aid psql -f verify.sql
   ```
   `verify.sql` выводит число тредов, тредов с сессией и без неё (тред без
   бесед в dev сессии не получает), сессий, записей, сессий без владельца (у
   треда нет пользователя) и сессий без треда (тред удалён в dev, а чекпойнты
   остались).
5. Открыть в чате несколько старых тредов: с инструментами, вложениями,
   вопросами, канвасом.
6. Удалить старые таблицы:
   ```sh
   PGDATABASE=aid psql -f cleanup.sql
   ```
7. Соединения пользователей, которые смотрят на удаляемые базы, — удалить или
   перевести на другую базу:
   ```sh
   PGDATABASE=aid psql -v remove=pg-solomatovs -v repoint=pg-krb-delegate \
        -v dbname=playground -f connections.sql
   ```
   Меняется только открытое поле базы — `dbname` у postgres, `database` у
   clickhouse; зашифрованные поля профиля остаются как были.

Отката у шагов нет: базу возвращают из резервной копии шага 1.
