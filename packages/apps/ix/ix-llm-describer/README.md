# ix-llm-describer: описания объектов от LLM

Независимый пакет поверх схемы `ix`. Читает `ix.node`, `ix.tree`, `ix.edge`, `ix.pg_meta_edge` и
surface-таблицы скрапера, пишет только в `ix.llm_description`. Со скрапером и индексаторами не
связан ни вызовами, ни внешними ключами. Модель зовёт Python через порт проекта
`boba.chat.generation.StructuredGenerator` (`boba-llm`), SQL знает только текст.

```
schema/   DDL таблицы ix.llm_description
prompt/   шаблоны свёртки длинного материала и json-схема ответа
describe.py описание одного объекта: промпт поверхности, бюджет, свёртка
run/      SQL шагов цикла
worker.py оркестратор
```

## Запуск

Описатель работает по всей базе `ix` сразу, источники ему не задаются: описываются объекты
всех пар «поверхность, аспект», у которых есть и объявление аспекта класса `describer_input`,
и промпт в `ix.surface_prompt`. Сейчас это таблицы и представления PostgreSQL, страницы и
записи блога Confluence. Пара с объявлением, но без промпта пропускается с предупреждением в
логе. Подписка задаётся в конфиге: `classes = ["describer_input"]`. Порядок в цепочке: `pg-meta-scraper` по каждому
источнику, затем описатель, затем `ix-fts` и `ix-vector`, чтобы описания
попали в поиск. Роль профиля читает `ix.*` и пишет в `ix.llm_description`.

Настройки берутся из одного файла конфига, секция [ix.llm_describer]. Конфиг приложения на dev-стенде лежит в `compose/apps/ix-llm-describer/conf.toml`
(каталог вне git, в нём креды). Одним файлом можно запускать и несколько приложений:
каждое читает только свою секцию.

База задаётся подсекцией `[ix.llm_describer.postgres]` — профилем boba-db-postgres: host, dbname,
`auth` с методом (`password`, `certificate`, `kerberos_keytab`, `kerberos_password`),
`options` с `lock_timeout` и `statement_timeout` сессии, `pool` с размерами пула. Подсекция
`[ix.llm_describer.krb]` даёт krb5.conf и каталог кэшей билетов для kerberos-профиля. Соединения
берутся из AsyncPostgresPool, воркер async.

```
.venv/bin/boba-ix-llm-describer --config ../../compose/apps/ix-llm-describer/conf.toml
```

Схема хранения задаётся полем `db_schema` секции: в sql-файлах она
стоит плейсхолдером `{schema}`, имя берётся из конфига, а квотирует его psycopg.

Провайдер выбирается ключом `provider` секции: `openai` (`base_url`, `api_key`, `model`) или
`local` (`model_dir`, например `compose/chainlit/models/onnx-genai/qwen3-4b-int4`). Остальные
поля секции: `max_tokens`, `temperature`, `tool_choice` (auto по умолчанию: deepseek в
thinking mode через роутер проекта другого не принимает), `batch` и обязательный
`max_input_chars`. Воркер всегда идёт до пустой очереди и заканчивает prune.

`max_input_chars` это бюджет входа модели в знаках: свойство модели, а не объекта, поэтому
он живёт здесь, а не у поверхности. Знаки, а не токены, потому что у удалённой модели
локального токенизатора нет. Материал короче бюджета уходит одним вызовом, длиннее идёт
через свёртку (ниже).

## Что уходит в модель

Материал собирает не описатель, а объявление владельца: у скрапера PostgreSQL это аспект
`meta_describer_input` таблиц и представлений. Пример для `dm.orders`:

```
Table dm.orders
Comment: customer orders, one line per position
Columns:
  id bigint not null default nextval('dm.orders_id_seq'::regclass)
  customer_id bigint not null
  amount numeric not null -- line amount in order currency
  status dm.order_status not null default 'open'::dm.order_status
  ...
Foreign keys:
  FOREIGN KEY (customer_id) REFERENCES dm.customers(id)
Referenced by:
  dm.order_items: FOREIGN KEY (order_id, line_no) REFERENCES dm.orders(id, line_no) ON DELETE CASCADE
Indexes:
  orders__open (created_at) where (status = 'open'::dm.order_status)
  orders_pkey (id) unique
```

Для view вместо ключей и индексов блок `Reads:` с таблицами, которые она читает. Данные
таблиц в модель не идут никогда, только структура. Что в тексте участвует: имя и вид,
комментарий, оценка строк (если таблица анализировалась), граница партиции, колонки с
типом, not null, default и комментарием, внешние ключи наружу и внутрь, индексы. Комментарии
индексов и внешних ключей стоят в той же строке после `--`, как у колонок: отдельными
объектами описания они не становятся.

## Промпт

Что говорить модели, решает владелец поверхности, а не описатель. Строка в
`ix.surface_prompt` на пару «поверхность, аспект»: `system_prompt` (роль, правила, язык,
объём, запрет выдумывать) и `user_template` с подстановкой `{input}`, куда встаёт материал
объекта. Скрапер PostgreSQL кладёт свои строки файлом `schema/50_prompts.sql`, индексатор
Confluence своим. Таблица и страница объясняются модели по-разному, и общего промпта
на всё нет.

В пакете остаются только вещи про способ разговора, одинаковые для всех поверхностей:

- `schema.json`: json-схема ответа (`SchemaSpec`: name, description, body); модель отвечает
  вызовом функции с этой схемой, воркер берёт поле `description`.
- `answer.md`: правило ответа вызовом функции схемы, подстановка `{function}`. Описатель
  дописывает его к системному промпту любой поверхности, поэтому владельцу не нужно знать
  контракт ответа. Без него модель на проходе выжимки отвечала обычным текстом.
- `part.md`: шаблон выжимки одного куска длинного материала, подстановка `{input}`.
- `reduce.md`: шаблон сведения выжимок в описание, подстановка `{parts}`.

Отпечаток `indexer_hash` считается на каждую пару: модель, бюджет входа, строка промпта
пары и четыре файла пакета. Правка промпта Confluence переводит в очередь только страницы, а
таблицы PostgreSQL остаются как есть. Смена материала объекта меняет `input_hash`, и
переописывается только он.

## Свёртка длинного материала

Страница Confluence бывает на двести тысяч знаков, и одним вызовом она в модель не
влезет. Если материал длиннее бюджета, он режется по структуре markdown: сначала по
заголовкам, потом по абзацам, и только абзац длиннее бюджета режется по знакам. Куски
набираются жадно, поэтому их столько, сколько нужно по объёму. Каждый кусок получает
выжимку шаблоном `part.md`, затем один вызов шаблоном `reduce.md` сводит выжимки в описание.
Системный промпт на обоих проходах берётся у поверхности, так что модель остаётся в своей
роли. В `llm_description` ложится только итог, отчёт цикла считает такие объекты в
`folded`.

На данных стенда при бюджете 24000 знаков одним вызовом описываются 1780 объектов из 1838,
свёрткой 58, самый длинный режется на 9 кусков.

## Цикл воркера

1. `run/10_queue.sql` с `%(batch)s` и тремя массивами пар: поверхности, аспекты и отпечатки.
   Соединение с ними отсекает пары без промпта. В очередь идут объекты без описания или с
   другим `input_hash` или отпечатком своей пары, с сессионными advisory-захватами по
   `node_id`, чтобы два воркера не описывали одно и то же.
2. На каждый объект описание промптом его пары: один вызов или свёртка. Ответ
   проверяется по схеме, `run/20_write.sql`.
3. `run/90_unlock.sql` после пачки и при любой ошибке.
4. `run/30_prune.sql`: удалить описания объектов, для которых больше нет входа: node удалён
   или поверхность перестала отдавать аспект класса `describer_input`.

## Как описание попадает в поиск

Текст структуры объекта описатель не собирает сам: его отдаёт владелец поверхности аспектом
класса `describer_input` (у скрапера это `meta_describer_input`), а воркер при старте читает
объявления этого класса из `ix.surface_aspect` и подставляет их вместо `{sources}` в
`run/10_queue.sql` и `run/30_prune.sql`.

В обратную сторону описатель сам владелец аспекта: значение `llm_description` класса
`description` он добавляет в словарь `ix.aspect` при `upgrade`, а объявления в
`ix.surface_aspect` кладёт в начале каждого цикла (`run/05_declare.sql`) для каждой поверхности,
у которой есть вход. Индексаторы `ix-fts` и `ix-vector` подписаны на класс
`description` и подхватывают описания следующим прогоном (вес в fts задаётся в его конфиге),
`ix-trgm` нет, там только `ident` и `words`. Никаких вызовов между пакетами. На стенде запрос «где хранятся позиции
заказов» до описаний не находил ничего в полнотексте, после них отдаёт `order_items` и
`orders` по аспекту llm_description; «бронирование комнат без пересечений по времени» находит
`bookings` через вектор описания.

## Как добавить поверхность

Описатель не меняется. Владелец поверхности объявляет аспект класса `describer_input` с
материалом в `ix.surface_aspect` и кладёт строку промпта в `ix.surface_prompt` для той же
пары. Накат владельца проверит, что у промпта есть роль модели и подстановка `{input}`.
