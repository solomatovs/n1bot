# pg-meta-scraper: снятие каталога PostgreSQL и Greenplum в граф ix

Пакет SQL-файлов для общего загрузчика `boba.ix_core.scrape`. Обвязка на Python
выполняет файлы по порядку имён, передаёт массивы OID словарём по именам из заголовков и
держит одну сессию. В текст SQL она не заглядывает и ничего в нём не подменяет.
Своё у пакета только источник (`worker.py`): сессия только на чтение с таймаутами,
ворота файлов по `server_version_num` и признаку Greenplum, `COPY TO STDOUT` на запрос.
Проверено на PostgreSQL 9.0–19 и Greenplum 6.24.1, 7.0.0-b2 (стенд в
`tests/stand/`).

```
schema/   DDL объектов, которыми владеет скрапер: значения surface_e и aspect_e, словари, pg_edge, surface-таблицы, объявления аспектов
scrape/   запросы к источнику, один файл на таблицу каталога, результат в raw_<name>
layout/   запросы к своей базе: raw_* -> stage_* -> ix
```

Схема пакета накатывается его же командой; ядро `ix` ставится до этого пакетом
`ix-core`:

```
.venv/bin/boba-ix-core upgrade --config ../../compose/apps/ix-core/conf.toml
.venv/bin/boba-pg-meta-scraper upgrade --config ../../compose/apps/pg-meta-scraper/conf.toml
```

Схема хранения задаётся полем `db_schema` секции: в sql-файлах она
стоит плейсхолдером `{schema}`, имя берётся из конфига, а квотирует его psycopg.

Команда идемпотентна: файлы `schema/*.sql` применяются по порядку имён, каждая команда
отдельной транзакцией, повторный запуск ничего не ломает. Без накаченного ядра команда
отказывает с указанием, что запустить.

## Аспекты поверхностей

Скрапер как владелец поверхностей `pg_meta_*` объявляет, какие тексты из них извлекаются:
`schema/01_aspect_values.sql` добавляет значения в `ix.aspect_e`, `schema/40_aspects.sql`
кладёт строки словаря `ix.aspect` и по объявлению в `ix.surface_aspect` на каждую пару
«поверхность, аспект» — запрос, возвращающий `node_id` и `content`. Индексаторы и описатель
читают эти объявления по классам и ничего про `pg_meta_*` не знают; добавить аспект или
поверхность значит добавить строки здесь.

| aspect | класс | поверхности |
|---|---|---|
| meta_name | ident | все |
| meta_path | ident | table, column, view, index, sequence, routine |
| meta_words | words | все |
| meta_description | description | все |
| meta_comment | description | все |
| meta_columns | description | table, view |
| meta_describer_input | describer_input | table, view |

Схема в теле объявления пишется удвоенной, `{{schema}}`, чтобы после наката в строке остался
плейсхолдер для потребителя; накат проверяет каждое тело по контракту.

## 0. Воркер: worker.py

Готовый прогон одного источника на Python, ровно по шагам ниже, с повторами при изменении
каталога во время чтения и при занятом `ix`:

Настройки берутся из одного файла конфига, секция [ix.meta_scraper]. Конфиг приложения на dev-стенде лежит в `compose/apps/pg-meta-scraper/conf.toml`
(каталог вне git, в нём креды). Одним файлом можно запускать и несколько приложений:
каждое читает только свою секцию.

База задаётся подсекцией `[ix.meta_scraper.postgres]` — профилем boba-db-postgres: host, dbname,
`auth` с методом (`password`, `certificate`, `kerberos_keytab`, `kerberos_password`),
`options` с `lock_timeout` и `statement_timeout` сессии, `pool` с размерами пула. Подсекция
`[ix.meta_scraper.krb]` даёт krb5.conf и каталог кэшей билетов для kerberos-профиля. Соединения
берутся из AsyncPostgresPool, воркер async.

```
.venv/bin/boba-pg-meta-scraper --config ../../compose/apps/pg-meta-scraper/conf.toml [--source pg-18]
```

Источники перечислены в секции списком `sources`, у каждого `name` и профиль `postgres`
того же вида, что у базы ix (у старых серверов в `auth` парольного профиля указывается
`require_auth = ["scram-sha-256", "md5"]`). Без
`--source` снимаются все по порядку, с `--source <имя>` только один. Один прогон это один
источник, одна база одного сервера. Роль источника читает только каталог, ей хватает
`pg_catalog` и права подключения к базе; роль профиля ix пишет в `ix.node`, `ix.tree`,
`ix.edge`, `ix.pg_meta_edge` и surface-таблицы.

Адрес источника для `raw_source` (host, port, database) берётся из его профиля, поэтому host
должен быть каноническим именем, а не одним из алиасов. `attempts` (3) число попыток. Итог
в логе: имя источника, planned и applied по каждой операции apply.

Воркер потоковый: имена колонок запроса берутся пробой `select * from (запрос) q limit 0`,
сами данные источник отдаёт `copy (запрос) to stdout (format text)` с параметрами, и блоки
байт уходят в `COPY ... FROM STDIN (format text)` на стороне `ix` без разбора в Python;
сверка по xmin тоже идёт потоком во временную таблицу и сравнивается `except` на сервере.
Сессия источника фиксирует представление значений, чтобы текст не зависел от настроек
сервера: `timezone = 'UTC'`, `datestyle = 'ISO, YMD'`, `intervalstyle = 'postgres'`,
`extra_float_digits = 3`, `bytea_output = 'hex'`; массивы, `jsonb`, `bytea`, `timestamptz`
проходят байт в байт (`tests/test_copy_formats.py`). В памяти Python только текущий блок
и массивы OID для параметров следующих волн; каждая попытка открывает обе сессии заново, и временные таблицы
неудачной попытки исчезают вместе с сессией.

## 1. Прогон одного источника

Две сессии: одна к источнику, одна к своей базе с `ix`. Порядок:

1. Источник: `show server_version_num`, `select version()`. Greenplum распознаётся по слову
   `Greenplum` в `version()`.
2. Источник: `set lock_timeout` и `set statement_timeout` из полей `lock_timeout` и
   `statement_timeout` секции (lock_timeout только с 9.3), `set default_transaction_read_only
   = on`. Каждый запрос отдельной транзакцией в autocommit, без общей транзакции.
3. Источник: файлы `scrape/`, объявленные в `PgSource.files` моделями `ScrapeFile`, по
   волнам. Для каждого имени выбирается единственный вариант, чьи ворота (`min_version`,
   `max_version`, `only`/`unless` по вкусу `gp`) подходят под сервер. Плейсхолдеры в
   файлах именованные, в стиле psycopg: `%(rels)s::oid[]`; значения передаются словарём
   по именам `params` объявления. Результат целиком сохраняется как строки `raw_<name>`;
   по `collect` объявления из результата собирается массив OID для следующих волн.
4. Источник: после последнего файла ещё раз все запросы сверки `<файл>.verify.sql` с
   теми же параметрами.
   Для каждой таблицы множество строк сверки (ключ и `row_xmin`) сравнивается
   с проекцией результата шага 3 на те же колонки: какие именно, задаёт сам запрос
   сверки. Расхождение значит, что каталог
   изменился во время чтения: прогон повторяется с шага 3, после трёх неудач ошибка.
5. Своя база, одна сессия в autocommit: `layout/00_raw_schema.sql` (temp-таблицы),
   `insert into raw_source values (scheme, host, port, database)`, `copy raw_<name> from
   stdin` для каждой таблицы шага 3 в порядке колонок результата, затем `10_stage.sql`,
   `20_nodes.sql`, `30_tree.sql`, `40_edges.sql`, `45_surfaces.sql`. Эти шаги читают только
   temp-таблицы сессии, `ix` не трогают, и транзакция им не нужна.
6. Та же сессия (её `lock_timeout` задан в `postgres.options`): `layout/48_lock.sql` в
   autocommit: это
   сессионный advisory-замок на scope источника, он держится через всю транзакцию.
7. Та же сессия: `begin isolation level repeatable read;` `50_apply.sql`, `commit;`,
   затем `55_unlock.sql`. Последний файл apply возвращает сводку planned/applied: delete
   и insert для node, tree, edge, pg_edge и каждой из двенадцати surface-таблиц.
   `55_unlock.sql` выполняется всегда, и после commit, и после ошибки (finally);
   закрытие сессии тоже снимает замок.
8. Ошибка на шагах 6–7 (`lock timeout` или `could not serialize`, SQLSTATE 55P03 и
   40001) значит, что scope занят или `ix` менял другой сеанс; транзакция откатилась
   целиком, прогон повторяется с шага 3. Неравенство planned и applied в сводке это
   ошибка пакета.

Temp-таблицы исчезают с сессией, ничего постоянного, кроме строк в `ix`, прогон не
оставляет.

## 2. Контракт файлов scrape

В файле `scrape/<имя>.sql` лежит только запрос выборки, рядом в `scrape/<имя>.verify.sql`
запрос сверки (колонки ключа и `row_xmin`, те же фильтры и параметры). Всё остальное
объявляет `PgSource.files` в `worker.py`:

```python
ScrapeFile(
    name="constraint",                       # имя таблицы: raw_constraint
    wave=3,                                  # порядок выполнения
    query="3_constraint.sql",                # файл запроса, сверка в 3_constraint.verify.sql
    params=("rels", "types"),                # какие массивы OID нужны: %(rels)s::oid[]
    collect=Collect(name="constraints", column="oid"),   # массив из колонки oid результата
    min_version=(90200,),                    # server_version_num, с которой вариант применим
    max_version=(109999,),                   # и по которую
    only="gp",                               # только Greenplum; unless="gp" — только PostgreSQL
)
```

Варианты одного имени различаются суффиксом `__…` файла и воротами; подходит ровно один.
Все варианты отдают одинаковые колонки, поэтому raw-таблица одна. Массивы: `schemas` из
namespace, `rels` из class, `types` из type, `procs` из proc, `attrdefs` из attrdef,
`constraints` из constraint, `triggers` из trigger, `statistics` из statistic_ext. Пустой
массив это `{}`. Волна 4 (`depend`, `description`) ждёт массивов волны 3.

Что ещё нужно знать обвязке о данных: последняя колонка каждого результата это
`row_xmin` текстом; векторы каталога уже развёрнуты в обычные массивы с индексацией
с единицы; выражения (default, generated, предикаты индексов, CHECK) приходят текстом
из `pg_get_expr` и `pg_get_constraintdef`; имена владельцев из `pg_get_userbyid`;
`pg_exttable` в Greenplum 7 не читается (это view), внешние таблицы там приходят через
`foreign_table`.

## 3. Контракт файлов layout

| файл | где выполняется | что делает |
|---|---|---|
| `00_raw_schema.sql` | до COPY, autocommit | `create temp table raw_<name>` под каждый scrape-файл и `raw_source` |
| `10_stage.sql` | в транзакции | temp `stage_node`, `stage_tree`, `stage_edge` |
| `20_nodes.sql` | autocommit | адреса всех node из `raw_*`; ключ (kind, oid, subid) → address |
| `30_tree.sql` | autocommit | родитель каждого node |
| `40_edges.sql` | autocommit | все рёбра; позиционные с role, side, ordinal, is_key |
| `45_surfaces.sql` | autocommit | temp `stage_pg_<surface>`: свойства node по видам из `raw_*` через `stage_node`, с комментариями |
| `48_lock.sql` | autocommit, до begin | `pg_advisory_lock` на хэш адреса базы источника |
| `50_apply.sql` | в транзакции, единственный | замок на срез `ix` по scope, затем на каждую таблицу два statement'а: delete лишних и изменившихся, insert недостающих; промежуточные множества это CTE, temp-таблиц три (apply_log, scope_node, node_map); сводка |
| `55_unlock.sql` | autocommit, после commit или ошибки | `pg_advisory_unlock_all` |

Адрес node это jsonb: scheme, host, port, database, schema и один из table, view,
sequence, index, function+args, type, statistics; column, constraint, trigger добавляются
к адресу владельца. Ключ node это address. Направление ребра: src зависит от tgt.
Позиционные строки `ix.pg_meta_edge` (`role`, `side`, `ordinal`, `is_key`) только у рёбер, у
которых в каталоге есть позиция в списке колонок. `role` называет список: index,
constraint, partition_key, distribution_key, trigger, statistics; `side = 1` только у
целевых колонок FK. У одного ребра может быть несколько таких строк: таблица,
партиционированная и распределённая по одной колонке, или FK на ту же колонку.

Surface node это двенадцать таблиц `ix.pg_<surface>` с ключом `node_id`, DDL в
`schema/20_pg_meta_surfaces.sql`. Строка surface сравнивается целиком: изменившаяся удаляется и
вставляется заново, неизменившаяся не трогается, поэтому полей `updated_at` и
`content_hash` у них нет. Что в них лежит: имена, владелец, вид, комментарий у всех;
у таблицы ещё tablespace, persistence, граница партиции, оценка строк и страниц,
для Greenplum распределение и хранение; у колонки тип, not null, текст default (у
generated-колонки это выражение), identity, generated; у индекса метод, флаги, имена
колонок, выражение, предикат; у sequence параметры (с PostgreSQL 10); у функции вид,
язык, аргументы, тип результата, volatility, security definer; у constraint'а вид, полное
определение, действия FK; у триггера timing, события, row level, enabled; у типа вид,
базовый тип домена или подтип range, метки enum. Размеры через `pg_relation_size`,
статистика обращений, статистика колонок, права и тела функций и view не снимаются.

`50_apply.sql` берёт `for update` на весь срез (node, tree, edge, pg_edge, surface по id), поэтому два
загрузчика одного источника друг друга дождутся или один упадёт по `lock_timeout`, а
загрузчики разных источников не пересекаются. Обновлений нет: surface следует из
address; изменившийся родитель или позиционная строка это удаление плюс вставка.

## 4. Замки, соединения и параллельные прогоны

Общая таблица замков PostgreSQL имеет `max_locks_per_transaction × (max_connections +
max_prepared_transactions)` слотов на весь сервер, по умолчанию 64 × 100 = 6400. Каждое
отношение, которое транзакция тронула, занимает слот до коммита. Temp-таблицы считаются
так же, как обычные: сама таблица, её toast и каждый индекс это по слоту. Когда слоты
кончаются, любой сеанс получает `ERROR: out of shared memory, HINT: You might need to
increase max_locks_per_transaction`.

Что это значило для пакета, измерено на стенде при 50 параллельных загрузчиках:

| вариант apply | замков в транзакции | 50 параллельно на дефолтах |
|---|---|---|
| temp-таблицы на каждое промежуточное множество, стадии в той же транзакции | 636 | 15 из 50 упали с out of shared memory |
| промежуточные множества в CTE, стадии в той же транзакции | 296 | помещается около 20 |
| CTE, стадии в autocommit до транзакции (текущий) | 161 | 50 из 50 прошли, 2 с на все, 1,2 с на прогон, deadlock 0 |

Отсюда правила:

- Стадии (`10`–`45`) выполняются в autocommit: их замки живут один statement.
  В транзакции только `50_apply.sql`, и он держит около 160 слотов: stage-таблицы,
  таблицы `ix` с индексами и каталоги.
- Минимум соединений это один воркер, который обходит источники по очереди: ему хватает
  одного соединения к `ix` и одного к текущему источнику, и таблицу замков он не
  исчерпает никогда. Параллельность это выбор, а не необходимость.
- Если прогоны идут параллельно, их число не должно превышать
  `max_locks_per_transaction × max_connections / 160` минус то, что занимают остальные
  сеансы сервера. На дефолтах это около 40. Больше даёт либо `max_locks_per_transaction`
  (нужен перезапуск сервера), либо меньшее число воркеров.
- Разные источники друг другу не мешают: их scope не пересекаются, замки `for update`
  берутся только на свои строки. 50 источников, одновременно переключённых с одного
  состояния на другое (259 удалений и 53 вставки node у каждого), прошли за 3 секунды
  без ошибок.
- Почему замок на scope берётся до `begin`, а не внутри транзакции. Замки `for update`
  внутри транзакции защищают только строки, которые уже есть. Если два загрузчика одного
  scope стартуют вместе, первый вставляет новые node и коммитит, второй дожидается его
  строк, но они не менялись, ошибки сериализации нет, а вставленные первым строки в
  repeatable read снимке второго невидимы, и `on conflict do nothing` в этом режиме их
  молча пропускает (документированное поведение). Второй коммитит своё состояние плюс
  чужие невидимые строки: на стенде это давало scope из полного gp-7 и 282 строк pg-18,
  при равенстве planned и applied и всех инвариантах. Advisory-замок до `begin`
  гарантирует, что второй откроет транзакцию, а значит и снимок, уже после коммита
  первого. Ожидание замка ограничено `lock_timeout`.
- Один источник в двух сеансах одновременно: побеждает первый, остальные ждут
  advisory-замок не дольше `lock_timeout`, потом получают 55P03 и откатываются, не начав
  транзакцию. Запускать один источник параллельно нет смысла, но и повредить он ничего
  не может.

Проверка консистентности (стенд `tests/stand/cons/`, тесты `tests/test_scrape_stand.py` и `tests/test_scrape_storm.py`): каждый набор данных
загружен один раз в чистую базу и свёрнут в канонический отпечаток без host и id;
после любой последовательности прогонов отпечаток scope обязан совпасть с эталоном
того набора, который был применён последним, а инварианты структуры (у каждого node
ровно одна строка tree и одна строка surface нужного вида, корень только база,
дерево без циклов, рёбра внутри одного источника) дать ноль. Прогнано: подмены базы под
тем же адресом pg-18 → gp-7 → pg-9.0 → gp-6 → pg-15 → pg-18 на фоне десяти других
источников; обрывы перед commit, посреди apply, в стадии и `pg_terminate_backend`
посреди apply; шесть раундов по 100 одновременных сессий на 50 scope (два набора данных
на scope) с процессом, который каждые 100 мс убивал или отменял три случайных
сессии. Итог: ни одного смешанного scope, ни одного нарушения инвариантов, deadlock 0,
контрольный проход после шторма привёл все 50 scope к эталону.

## 5. Требования к схеме ix

- `ix.node (id, surface ix.surface_e, address jsonb unique)`; поле url раскладка не
  заполняет. Индекс `gin (address jsonb_path_ops)` обязателен: по нему `50_apply.sql`
  находит срез источника через `@>`.
- `ix.tree (id, node_id, parent_id null, unique (node_id, parent_id))`.
- `ix.edge (id, node_src_id, node_tgt_id, surface, weight, unique (node_src_id, node_tgt_id))`.
- FK из tree и edge на node с `on delete cascade`.
- Остальное создаёт сам пакет в `schema/`: значения `surface_e`, словарь, `pg_meta_edge_role_e`,
  `pg_edge`, двенадцать surface-таблиц.

## 6. Что не снимается

- Рёбра generated-колонки на исходные колонки на PostgreSQL 12–14 и Greenplum 7: в
  `pg_depend` их нет, есть только текст выражения в `raw_attrdef.expr`.
- Тела plpgsql-функций: каталог их не разбирает, рёбер функция → таблица нет.
- Соответствие колонок view колонкам таблиц.
- Зависимость view от типа через литерал, внешние адреса external и foreign tables.
- Размеры отношений (`pg_relation_size` берёт замок на таблицу), статистика обращений и
  колонок, права, тела функций и определения view: по решению не снимаются.
- Параметры sequence на версиях ниже 10: их нет в каталоге, только в самой sequence.
