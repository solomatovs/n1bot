# cfl-indexer: Confluence в граф ix

Скрапер Confluence: идёт по спейсу страница за страницей и на каждом объекте обновляет
node, tree, surface-строку и текст, который SQL добыть не может (markdown страницы,
текст вложения, OCR), в общий `ix.ix_fts`. Оригиналы — HTML страницы и файлы вложений —
не хранятся, только их хэши.

Остальное делают общие индексаторы по объявлениям аспектов: `ix-fts` выводит `title`,
`path`, `card` и выравнивает веса, `ix-trgm` и `ix-vector` берут свои классы. Поэтому
здесь нет ни модели эмбеддинга, ни весов, а аспект, объявленный описателем или другим
потребителем, попадает в индексы сам, без обхода Confluence.

```
schema/        DDL: значения surface_e и aspect_e, словари, поверхности cfl_*, объявления
run/           SQL шагов обхода: node, tree, surface-строки, текст node, рёбра, чистка
confluence.py  чтение Confluence: спейс, списки, тело в markdown, вложения, комментарии
documents.py   вердикт по вложению и текст его файла роутером boba-doc из потока скачивания
store.py       запись в ix одним соединением: node, tree, surface-строки, ix_fts, чистка
worker.py      конфиг, обход спейса, процесс на спейс, CLI
```

## Установка

Ядро ставится пакетом `ix-core`, дальше схема этого пакета своей командой:

```
.venv/bin/boba-ix-core upgrade --config ../../compose/apps/ix-core/conf.toml
.venv/bin/boba-cfl-indexer upgrade --config ../../compose/apps/cfl-indexer/conf.toml
```

Конфиг приложения на dev-стенде лежит в `compose/apps/cfl-indexer/conf.toml` (каталог
вне git, в нём креды). Пути в конфиге пишутся от `${env.base}` — каталога, где лежит
файл. Секция `[ix.cfl_indexer]`: база ix (`db_schema`, `postgres`, `krb`), список
`sources` — по записи на сервер Confluence с именем, `spaces` и endpoint
(`confluence.profile` — web-профиль с auth или без, `confluence.body_format`,
`confluence.dump` — дамп HTTP-обмена), `parallel_spaces` — сколько процессов спейсов
идёт одновременно, `list_limit` — окно списков страниц, вложений и комментариев, `progress_every` — через сколько объектов спейса писать в лог
счётчики, вложения (`attachments` — маски имён и media-type), таблица `doc` с
настройками чтения файлов (`spool_memory_limit` — до скольких байт zip и pdf держатся
в памяти, дальше временный файл ридера; `text_encodings`) и вложенная `doc.ocr` —
union по `provider`: `off` либо `rapidocr` (`models_dir`, `language`, `text_score`,
`threads`). Модели эмбеддинга и весов полнотекста в этой
секции нет: векторы считает `ix-vector` по своей секции `[ix.vector]`, веса — `ix-fts`
по `[ix.fts]`.

```toml
[[ix.cfl_indexer.sources]]
    name = "cwiki"

    [ix.cfl_indexer.sources.spaces]
        masks    = ["ATTIC", "BVAL"]
        type     = "global"
        archived = false

    [ix.cfl_indexer.sources.confluence.profile]
        scheme = "https"
        host   = "cwiki.apache.org"
        port   = 443
        path   = "/confluence"
```

## Какие спейсы обходить

Выбор спейсов источника задаёт таблица `spaces`: `masks` — ключи или glob-маски,
`type` — `global`, `personal` или `any`, `archived` — брать ли архивные спейсы.

Маска без glob-символов это ключ спейса как есть: список спейсов с сервера не
запрашивается, и спейс читается по адресу, даже если в списке его не видно.
Маска со звёздочкой разворачивается обходом `/rest/api/space`: подходят спейсы, у
которых ключ или название целиком совпали с маской (без учёта регистра), с учётом
`type` и `archived`. Поэтому `masks = ["*"]` — это «все доступные спейсы», а
`masks = ["DWH*", "Каталог данных"]` — отбор по ключу и по названию.

Архивные спейсы читаются штатно: обход идёт списком контента спейса, а не поиском,
которому архив невиден. Брать их или нет — решает `archived`.

## Запуск

```
.venv/bin/boba-cfl-indexer run --config ../../compose/apps/cfl-indexer/conf.toml [--source cwiki] [--space DEV] [--reindex]
```

`--source` ограничивает прогон одним сервером, `--space` — одним спейсом (при
нескольких источниках вместе с `--source`). `--reindex` на один прогон отключает
отсечение по версии и хэшу параметров: всё перечитывается и переиндексируется без
правок конфига и кода; вектор при этом всё равно пересчитывает только аспекты, чей
текст изменился.

## Процесс на спейс

Родитель читает конфиг, собирает пары «источник, ключ спейса», проверяет, что
`ix_fts` накачен, и раздаёт спейсы процессам: по одному спейсу на процесс,
`parallel_spaces` процессов одновременно. Процесс умирает вместе со спейсом, и всё,
что он успел набрать — арены glibc, сессии onnxruntime — возвращается системе.
Родителю нужны только отчёты.

Внутри процесса спейса нет ни очередей, ни семафоров: один event loop, одно
соединение к ix, один http-клиент, и всё идёт друг за другом. Спейс, потом страницы и
блог-записи списком без тел; на каждой — тело, вложения одно за другим, комментарии;
после обхода ссылки в рёбра и чистка. Разбор html блокирует цикл, и это не беда: в
процессе больше ничего не крутится. Единственный поток — ридер файла вложения: тело
http-ответа уходит в пипу, ридер читает её конец в рабочем потоке, цикл только качает
чанки.

В памяти живёт один объект за раз: страница списка отпускается до запроса следующей,
html тела превращается в markdown и выбрасывается, файл вложения идёт на диск чанками
и разбирается с диска, увиденные node и ссылки копятся в temp-таблицах сессии базы, а
не в списках. Отчёт спейса несёт пик RSS его процесса (`rss=` в строке `progress:` и в
итоге), по нему видно, копит ли обход память.

Ошибка внутри спейса (Confluence, база) прерывает его, спейс попадает в отчёт с
`error`, остальные спейсы идут дальше. Процесс, упавший не своей ошибкой, роняет
прогон целиком с `IndexerWorkerError`.

## Что делает обход

1. `GET /space/{key}` — node спейса, `cfl_space`, аспекты `title`, `words`, `card`.
2. Списки `space/{key}/content/page` и `/blogpost` с версиями, предками, метками и
   историей, без тел. На каждом объекте: node по адресу, tree по последнему предку,
   отметка «увиден» в temp-таблице сессии.
3. Версия из списка сравнивается с версией в surface-строке; совпала вместе с
   `indexer_hash` — тело не запрашивается. Иначе запрашивается ответ с телом
   `body.view`: `content_hash` = sha256 сырых байт этого ответа, в индекс идёт
   markdown. Вложения и комментарии обходятся всегда, у каждого своя версия;
   перезалитый без изменений файл (тот же sha256) обновляет строку, текст не трогает.
4. Транзакция: surface-строка и текст node в `ix_fts` (`body`, у вложений ещё `ocr`).
   Остальные аспекты и все триграммы с векторами появятся на ближайшем прогоне общих
   индексаторов.
6. Вложения страницы: из раскрытия списка, при усечении — полным списком. Node, tree
   под страницей и surface-строка пишутся всегда, так что файл находится по имени и
   пути; текст — только у взятых. Берётся ли файл, решают маски `attachments` и
   `doc.ocr.provider` (картинки без OCR не качаются); вид, который роутер boba-doc не
   знает по media-type и имени, остаётся метаданными. Байты идут из http прямо в ридер
   формата через пипу, sha256 считается по дороге; ридер сам решает, держать файл в
   памяти или во временном файле. У картинки текст идёт аспектом `ocr`, у остального —
   `body`. Файл, который не скачался или не разобрался, считается в `failed`
   отчёта и не останавливает спейс; команда завершается с ошибкой, если такие были.
7. Комментарии страницы: `content/{id}/child/comment` с телами — у страницы нет
   признака, что комментарии менялись, поэтому список читается на каждом обходе
   (один запрос на страницу). Node под страницей, `cfl_comment` с местом (inline или
   footer), автором и датами, текст — markdown тела, `card` — «Comment by …».
8. Ссылки: из тела каждой перечитанной страницы снимаются ссылки на другие страницы
   (по id, по заголовку, макросом `ri:page`) и копятся в temp-таблице сессии. После
   обхода они разрешаются в node — по id через адрес сервера, по заголовку через
   `cfl_page` этого спейса — и становятся рёбрами `edge` с поверхностью
   `cfl_page_link`; прежние рёбра перечитанных страниц снимаются, страницы без
   изменений свои рёбра сохраняют. Внешние ссылки и ссылки на себя отбрасываются.
9. Конец спейса: node спейса, которых прогон не видел, удаляются вместе со строками
   индексов; рёбра ушедших node снимает каскад.

## Аспекты

| aspect | класс | поверхности | что это |
|---|---|---|---|
| title | ident | space, page, blogpost, attachment | заголовок, имя файла или спейса как есть |
| path | ident | page, blogpost, attachment | `DEV/Заголовок` |
| words | words | space, page, blogpost, attachment | слова заголовка, как у pg |
| labels | description | page, blogpost | метки через пробел |
| card | description | все | карточка: вид, путь, метки, начало текста |
| body | description | page, blogpost, attachment, comment | полный текст, пишет индексатор |
| ocr | description | attachment | текст с картинки или скана |
| describer_input | describer_input | page, blogpost | страница целиком для описателя |

Аспект `describer_input` объявлен ради того, чтобы `ix-llm-describer` работал по
страницам Confluence, не зная о них: он подписан на класс, а не на поверхности.
Написанные им описания попадают в индексы обычным прогоном `ix-fts` и `ix-vector`.

Объявления в `surface_aspect` нужны не только самому индексатору: описатель и другие
потребители объявят поверх них свои аспекты (`describer_input`, `llm_description`).

## Адреса

Частями, как у postgres: спейс `{scheme, host, port, space}`, страница и блог-запись
`{scheme, host, port, content}`, вложение и комментарий добавляют `attachment` или
`comment`; Confluence под префиксом пути (`/confluence` у cwiki.apache.org) несёт ещё
`path` — это другой сервер на том же хосте. Ссылка для человека собирается из адреса; область спейса для чистки —
`space_key` поверхностей.

## Тесты

`tests/` — интеграционные: заглушка Confluence из `boba.stand.confluence` (граф,
полнотекст, отсечение по версии и хэшу, вложения, комментарии, ссылки, чистка) и живой
спейс стенда. Прогон в тестах идёт в потоке, потому что процессы спейсов ходят в
заглушку, которую обслуживает event loop теста. Тест на потоковость (`-m load`) кормит
индексатор спейсами с сотнями pdf и картинок и сверяет пик RSS процессов спейсов: он не
должен расти с объёмом спейса, а RSS родителя — с числом спейсов. Нужны `[ix_stand]`
и, для картинок, `[doc_stand]` с `ocr_models_dir` в `stand.toml` рядом с конфигом
приложения.
