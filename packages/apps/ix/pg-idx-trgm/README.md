# pg-idx-trgm: триграммный и btree-индекс имён объектов PostgreSQL

Независимый индексатор поверх схемы `ix`. Читает только `ix.node`, `ix.tree` и surface-таблицы
`ix.pg_*`, пишет только в `ix.pg_idx_trgm`. Со скрапером не связан ни вызовами, ни внешними
ключами: строки node, которых больше нет, убирает сам.

```
schema/   DDL объектов, которыми владеет индексатор
run/      SQL шагов цикла, их выполняет worker.py
```

## Установка

`schema/10_pg_idx_trgm.sql`: таблица `ix.pg_idx_trgm` с индексами. Колонка `aspect` ссылается на
словарь ядра `ix.aspect`, значения в него добавляют владельцы поверхностей.

Схема пакета накатывается его же командой; ядро `ix` ставится до этого пакетом
`pg-ix-core`:

```
.venv/bin/boba-ix-core upgrade --config ../../compose/apps/pg-ix-core/conf.toml
.venv/bin/boba-pg-idx-trgm upgrade --config ../../compose/apps/pg-idx-trgm/conf.toml
```

Схема хранения задаётся полем `db_schema` секции: в sql-файлах она
стоит плейсхолдером `{schema}`, имя берётся из конфига, а квотирует его psycopg.

Команда идемпотентна: файлы `schema/*.sql` применяются по порядку имён, каждая команда
отдельной транзакцией, повторный запуск ничего не ломает. Без накаченного ядра команда
отказывает с указанием, что запустить.

## Запуск

Индексатор работает по всей базе `ix` сразу, источники ему не задаются: что скрапер положил
в `ix` из любых баз, то и индексируется. Порядок в цепочке: сначала `pg-meta-scraper` по каждому
источнику, затем этот индексатор один раз. Запускать можно как угодно часто, и до, и после
скрапера: он сам находит, чего не хватает, и доводит таблицу до структуры; параллельные
запуски не мешают друг другу.

Настройки берутся из одного файла конфига, секция [ix.idx_trgm]. Конфиг приложения на dev-стенде лежит в `compose/apps/pg-idx-trgm/conf.toml`
(каталог вне git, в нём креды). Одним файлом можно запускать и несколько приложений:
каждое читает только свою секцию.

База задаётся подсекцией `[ix.idx_trgm.postgres]` — профилем boba-db-postgres: host, dbname,
`auth` с методом (`password`, `certificate`, `kerberos_keytab`, `kerberos_password`),
`options` с `lock_timeout` и `statement_timeout` сессии, `pool` с размерами пула. Подсекция
`[ix.idx_trgm.krb]` даёт krb5.conf и каталог кэшей билетов для kerberos-профиля. Соединения
берутся из AsyncPostgresPool, воркер async.

```
.venv/bin/boba-pg-idx-trgm --config ../../compose/apps/pg-idx-trgm/conf.toml
```

Роль профиля должна иметь права на чтение `ix.node`, `ix.tree`, surface-таблиц `ix.pg_*` и на
запись в свою таблицу `ix.pg_idx_trgm`. Схему таблицы создаёт `schema/*.sql` при установке
(идемпотентно), запускается той же ролью или владельцем схемы `ix`. Один запуск = один
проход до пустой очереди и prune; для регулярной работы ставится в планировщик.

## Воркер: worker.py

```
.venv/bin/boba-pg-idx-trgm --config ../../compose/apps/pg-idx-trgm/conf.toml
```

Крутит `run/10_upsert.sql` пачками до applied = 0, затем `run/20_prune.sql`; креды только в конфиге.

## Цикл воркера

1. `run/10_upsert.sql` с параметром `%(batch)s` (размер пачки): вставить недостающие строки и обновить
   те, у которых `content` отличается от вычисленного. Возвращает planned и applied;
   повторять, пока applied не станет 0.
2. `run/20_prune.sql`: удалить строки `pg_trgm`, для которых аспекта больше нет (node удалён,
   поверхность сменилась, у аспекта path сменился вид объекта). Возвращает число удалённых.

Порядок намеренно такой: сначала добавить, удалять последним. Переименованный или
пересозданный объект это новый node и удалённый старый; при таком порядке он всё время
находится по новому имени, а строки старого node висят до prune. Они ссылаются на
`node_id`, которого нет, и поисковый запрос, который join'ит `ix.node` ради адреса, их не
видит. Обратный порядок делал бы объект ненаходимым на всё время между prune и upsert,
для векторного индекса это минуты. Условие, которое отсюда следует: поисковые запросы
всегда join'ят `ix.node`, сироты в индексных таблицах допустимы до ближайшего prune.

Каждый шаг это одна транзакция в autocommit; `statement_timeout` и `lock_timeout` сессии
задаёт `postgres.options` секции. Вставка идёт `on conflict do update ... where content is distinct from`, поэтому
два воркера одного индекса не мешают друг другу: строку запишет один, второй увидит
совпадение. Воркер догоняет структуру частыми запусками; между прогоном скрапера и
воркером индекс отстаёт, изменённые node получают новый content после upsert, удалённые
исчезают из выдачи сразу (через join с `ix.node`) и из таблицы после prune.

## Откуда берутся аспекты

Индексатор не знает ни поверхностей, ни происхождений. Он подписан на классы аспектов
(`classes` в секции конфига, для триграмм это `ident` и `words`) и при старте цикла читает
объявления своих классов из `ix.surface_aspect` — таблицы ядра, в которую пакет-владелец
поверхности кладёт по строке на пару «поверхность, аспект» с запросом, возвращающим
`node_id` и `content`. Воркер склеивает тела объявлений в один `union all` с колонками
`surface`, `aspect`, `node_id`, `content` и подставляет его в `run/10_upsert.sql` и
`run/20_prune.sql` вместо `{sources}`. Новая поверхность подхватывается без правок здесь:
её пакет объявляет свои аспекты классов `ident` и `words`.

## Аспекты

С объявлениями скрапера PostgreSQL в таблицу попадают:

| aspect | класс | кто объявляет |
|---|---|---|
| meta_name | ident | все поверхности pg_meta_* |
| meta_path | ident | pg_meta_table, pg_meta_column, pg_meta_view, pg_meta_index, pg_meta_sequence, pg_meta_routine |
| meta_words | words | все поверхности pg_meta_* |

Как строится текст: `meta_path` это `schema.table`, `schema.table.column`,
`schema.routine(args)`; `meta_words` это имя, разрезанное по CamelCase, подчёркиваниям и
дефисам, в нижнем регистре, ё заменена на е.

## Требования к схеме

Ядро `ix` (`ix.node`, `ix.aspect`, `ix.surface_aspect`) и объявления хотя бы одного владельца
поверхностей. Свою таблицу пакет создаёт сам в `schema/`: без внешнего ключа на `ix.node`, со
ссылками на словари `ix.surface` и `ix.aspect`.
